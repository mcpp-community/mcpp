## 0. 范围

本规范规定 `mcpp test` 作为测试运行器的行为：

- 它如何认出一个测试程序实现了测试协议；
- 它向程序陈述什么、从程序读取什么；
- 它以哪些记录报告结果，以及保存的运行是什么形式。

mcpp 实现协议的运行器一侧，**不实现、不要求任何测试框架**。

## 1. 原则

- **协议是契约，框架是实现。** 任何实现协议的程序都由同一套规则服务，与其语言或框架无关，例如：
  - mtest 的 C++ 库（L3）；
  - GoogleTest 适配器（L1）；
  - Bash、Python 适配器；
  - C ABI；
  - 只含头文件的 C 写出器（openkal-musl 的探针）。

  引擎**禁止**含有任何框架名或框架特有的分支。
- **未实现协议的程序是一个用例。** 它以退出状态判定（协议 P1.1），并且**不得**收到协议的任何变量（P1.2）。
- **程序的退出状态仍决定其结论。** 报告中失败的用例使程序失败，即使它以 0 退出；有 `begin` 而无 `end` 的用例失败（P5.4）。
- **只增不改。** 记录与存储的字段只增加；新含义由 feature 宣告（docs/50 §4），已发布名字的含义不变。

## 2. 程序与协议 已实现(mcpp >= 2026.11.8.1)

- 程序实现协议的条件是以下之一：
  - 其入口陈述 `test-protocol = 1`；
  - 其文件或其链接自的目标文件携带标记 `mtest-protocol=1`（P2.3）。

  携带标记而不写 `program` 事件的程序视为未实现协议。
- mcpp 向实现协议的程序陈述协议的变量（P2.1）：
  - 总是给出 `MTEST_PROTOCOL`、`MTEST_MODE`、`MTEST_REPORT`、`MTEST_TMPDIR`；
  - 适用时给出 `MTEST_SELECT`、`MTEST_SEED`。

  变量名属于协议，不属于某个框架。对其他程序，这些变量**必须**从其环境中移除（P2.2）。
- 框架**可以**在其入口陈述 `test-guide = "<文件>"`（P2.5）；`mcpp test --guide` 写出它。

## 3. 列出、选择与各部分

1. **列出（P3）已实现。** `mcpp test --cases` 以 `list` 模式运行每个实现协议的程序，报告其用例而不运行。
2. **选择（P4）已实现。** `--case <模式>` 把每个程序中匹配的用例写成 `MTEST_SELECT`。在列出的用例之下的名字选中该用例（P3.4）。
3. **各部分（mcpp >= 2026.11.10.1）。**
   - `[test] split` 决定一个程序以几个进程运行：
     - `"file"`（缺省）：用例分布在其多个文件中时，每个文件一个进程；
     - `"case"`：每个用例一个进程；
     - `"none"`：一个进程。
   - 每个进程是程序的一个**部分**，名为 `<程序>/<文件主名>`（`"case"` 时为 `<程序>/<用例>`）。
   - `--cases` 的记录**必须**写出 `"file"` 划分的各部分（`parts`：`name`、`file`）。
   - 每个部分的运行记录**必须**写出 `part_of`。

## 4. 报告

1. **事件（P5、P6、P10.2）已实现。** mcpp 读取以下事件，其余事件与字段**必须**被忽略（P5.4）：
   - `program`、`case`、`begin`、`failure`、`end`、`missing`、`done`；
   - `metric`（mcpp >= 2026.11.10.1）；
   - `usage`（mcpp >= 2026.11.10.1）。
2. **用例的属性（mcpp >= 2026.11.10.1）。**
   - `case` 事件与 `begin` 事件给出的 `kind`、`tags` 与 `bounds`（P3.4、P6.5）属于该用例；
   - `metric` 事件属于其 `id` 所指的用例（P6.1）；
   - `usage` 属于程序（P10.2）。
3. **随写随读（P5.1；mcpp >= 2026.11.10.1）。**
   - 报告是程序逐事件追加的 NDJSON。`--message-format json` 下，mcpp **必须**在程序运行期间读取它，并在每个用例开始与结束时各写一条 `case` 记录（§5.2）。
   - 只读取完整的行。程序结束后读取其余行，再按 P5.4 收尾。

## 5. 测试流记录（docs/50 §8）

1. **程序记录** 已实现。每个程序（部分）一条：
   - 状态、退出码、用时；
   - `protocol`；
   - `cases`：每个用例的 `id`、`status`、`duration_ms`、`reason`、`failures`，以及陈述时的 `kind`、`tags`、`metrics`、`bounds`（后四者 mcpp >= 2026.11.10.1）；
   - `missing`、`listed`；
   - `part_of`、`parts`、`usage`（mcpp >= 2026.11.10.1）。
2. **用例记录（mcpp >= 2026.11.10.1）。** `{"case": {...}}`，先于其程序的记录：
   - `member`、`test`、`id`、`event`；
   - `begin` 带 `t_ms`，从运行开始计；
   - `end` 带 `cases` 中一个用例的全部字段。
   - 一个用例结果在 mcpp 中只有一种形状。
3. **feature（docs/50 §4）。** 这三项以 `test-` 为前缀，都建立在 `test-protocol` 之上；客户端按需门控：

| feature | 宣告的含义 |
|---|---|
| `test-protocol` | §2、§3.1、§3.2、§5.1 的程序记录与用例结果（2026.11.8.1） |
| `test-parts` | §3.3（2026.11.10.1） |
| `test-case-stream` | §4.3、§5.2（2026.11.10.1） |
| `test-metrics` | §4.2，§5.1 的 `kind`、`tags`、`metrics`、`bounds`、`usage`，§6 的相应字段（2026.11.10.1） |

## 6. 运行存储（协议 P12）已实现(mcpp >= 2026.11.9.1)

- 一次运行以协议 P12 的存储形式保存在 `[test] store`（缺省 `target/mtest`）：
  - `index.ndjson`；
  - `runs/<id>/run.json`；
  - `runs/<id>/programs.ndjson`；
  - `runs/<id>/cases.ndjson`。

  任何按 P12 读取存储的工具都可以读取它。
- `run.json` 的 `commit` 与 `group` 在 CI 中取 `GITHUB_SHA` 与 `GITHUB_RUN_ID`；一个 CI 运行的各个作业因此是一组（P12.2）。
- `cases.ndjson` 每个用例一行：
  - `program`、`id`、`status`、`ms`、`reason`；
  - `failures`，含陈述时的 `expected`、`actual`；
  - 陈述时还有 `kind`、`tags`、`started_ms`、`metrics`、`bounds`（mcpp >= 2026.11.10.1）。
- `programs.ndjson` 每个进程一行：
  - 程序报告时带 `usage`，`source` 为 `program`（mcpp >= 2026.11.10.1）；
  - mcpp 在一次构建中构建全部测试程序，不写逐个程序的 `build_started_ms`。

## 7. 兼容性

- 所有新增均为字段或记录种类的增加。`case` 记录的唯一顶层键是 `case`，只按已知键分派的客户端会跳过它。
- `--list` 的 `main` 含义不变：`--list` 不构建程序，不列出用例；程序的各部分由 `--cases` 的 `parts` 给出。
