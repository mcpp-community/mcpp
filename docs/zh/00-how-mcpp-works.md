# 00 —— mcpp 的运转方式

**读者:**任何人,在读别的之前。其余每一章都假定读过这一章。

**本章回答的那一个问题:**有哪些活动部件,以及出问题时是哪一个在出问题。

mcpp 是三样东西合在一个程序里 —— 构建系统、包管理器、工具链供给者。这不常见,
也正是「从命令参考读起的人只看到一串动词、无处安放」的原因。本章是模型。它不写
任何字段、任何旗标;那些在参考章节里,而本章让它们可读。

下一章:[01 —— 快速开始](01-getting-started.md) 把一个程序跑到屏幕上。

## 五个名词

本套文档讲的全部内容,就是五样东西以及它们之间的缝。

### 包(package)

一个带 `mcpp.toml` 的目录。它声明名字、版本、由什么构建、依赖什么。它的身份是
`(namespace, name)` 这一对 —— 不是它的目录,也不是它的文件名 —— 所以来自不同
namespace 的两个 `cmdline` 可以共存。

包同时是其余一切的单位:被发布的单位、被缓存的单位、声明 feature 的单位,以及
构建程序所归属的单位。

参考:[03 —— mcpp.toml 工程文件指南](03-mcpp-toml.md)。

### 图(graph)

一次构建是一张图。源产出目标文件,目标文件产出产物,而 C++20 模块接口会在源与源
之间加边 —— 一个单元必须先于 import 它的那个单元被编译。这个次序由 mcpp 扫描源
算出;manifest 里不写它。

有两样东西是**扩展这张图**而不是待在图外面的:**构建程序**(`build.mcpp`)声明
额外的边,**规则包**为一整类工程供给这些声明。两者都往同一张图里加节点;都不是
构建前脚本。

参考:[30 —— 构建程序](30-build-mcpp.md)。

### 工具链(toolchain)

mcpp 使用的编译器是**它自己安装并钉住的载荷**,不是在机器上找到的程序。这是大多数
其它构建系统没有的性质,而它决定了很多别的形状:构建可复现,因为编译器本身是被
解析出来的一部分;工程可以**声明**它需要哪个编译器,而不是写在 README 里让人照做。

参考:[20 —— 工具链管理](20-toolchains.md)。

### 目标(target)

产物运行的那台机器。它由三元组命名,而且它不是宿主:在 Linux 上的一次构建可以产出
Windows 可执行文件、裸机镜像,或者给 GPU 的一个目标文件。一切以「它在哪里运行」为
条件的东西都挂在目标上,而 manifest 说「只在那里」不需要第二份 manifest。

参考:[21 —— 目标三元组](21-the-target-triple.md)。

### 索引(index)

包从哪里来。索引里存的是**描述符** —— 一个包的身份、它有哪些版本、每个版本的源码
或产物从哪里取。描述符是数据;mcpp 是读它的那个程序。

参考:[11 —— 发布一个库到 mcpp-index](11-publishing-a-library.md)。

## 一次构建从头到尾做了什么

```
  mcpp.toml ──▶ 解析 ──▶ 供给 ──▶ 扫描 ──▶ 编译 ──▶ 链接
     │           │         │         │        │        │
     包       索引 +     工具链     图的边   工具链    产物
              版本      + 工具

              ╰──── 第一次构建跨过的三道缝 ────╯
```

**第一道缝 —— 从 manifest 到解析结果。** manifest 点名的东西变成一组确切的版本。
这里失败是索引或版本约束的事,而且还没有编译过任何东西。

**第二道缝 —— 从解析结果到环境。** 解析出来的东西变成磁盘上的载荷:工具链,以及
任何包声明过的工具。这里失败是下载、某平台没有这样的载荷、或者版本下界的事。

**第三道缝 —— 从源到图。** 源被扫描 `import`,边被算出。这里失败点名的是一个模块,
不是一个文件。

编译与链接在这三道缝之后,所以「它编不过」其实是四种相当不同的处境。

## 状态落在磁盘的哪里

mcpp 写的东西没有一样是隐藏的,而每个存储回答的是不同的问题。

| 存储 | 作用域 | 存什么 | 由什么清空 |
|---|---|---|---|
| `target/<triple>/<fingerprint>/` | 单个工程 | 目标文件、模块接口、产物 | `mcpp clean` |
| 构建缓存 | 整台机器 | 编译过的依赖与 `std` | `mcpp cache gc` |
| 包存储 | 整台机器 | 工具链载荷与被声明的工具 | 包管理器 |
| `mcpp.lock` | 单个工程,进版本库 | 一次解析产生的结果 | `mcpp update` 重写 |

`mcpp self env` 打印这几样在本机的位置。

构建目录名里的那个指纹,正是两种配置互不打架的原因:debug 构建、release 构建与
交叉构建各占一个目录,谁也不让谁失效。

## 一次失败是关于哪个名词的

这个模型买到的最有用的一件事。一条消息点名一个名词,而名词点名章节。

| 消息里出现 | 名词 | 去哪里看 |
|---|---|---|
| 包名、版本,或「没有候选」 | 索引 | [11](11-publishing-a-library.md)、[04](04-dependencies.md) |
| 下载、载荷,或版本下界 | 工具链 | [20](20-toolchains.md)、[23](23-the-project-environment.md) |
| 三元组,或「不支持的目标」 | 目标 | [21](21-the-target-triple.md) |
| 某个模块读不到或没有人提供它 | 图 | [30](30-build-mcpp.md) |
| 工程自己某个文件里的编译或链接错误 | 一个都不是 | 编译器自己的消息 |

最后一行是有用的那一行:当编译器报的是代码本身的错误时,mcpp 的任何部件都没有
参与,读 mcpp 的文档不会有帮助。

## 本章有意不写什么

一切操作性的东西。manifest 的字段、旗标,以及 `mcpp build` 之外的命令,都刻意不在
这里出现 —— 一份既想当模型又想当参考的文档,两样都不是。每个名词那一节点名了拥有
它的章节。
