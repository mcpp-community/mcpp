# 陈述的闭包、单一读者与六项功能:十四项缺陷的收敛设计

**日期：** 2026-11-27 · **版本：** v3（已实施于 mcpp 2026.11.27.1；实施中的改动见 §13） · **基线：** mcpp 2026.11.26.1（`main` a5450eaf） ·
**相关规范：** SPEC-002（目标侧）、SPEC-004（清单语义）、SPEC-012（面向人的输出）、SPEC-013（平台）、SPEC-014（打包）

本文把 2026-11-27 仍开着的十四项缺陷与六项功能请求放在一起设计。它们分属运行期搜索、子进程环境、清单读写、扫描、
缓存、路径与命令行七个子系统，但缺陷只有四个共同原因；六项功能请求各自落在一个已有机制上，不新增机制。

## 0. 结论

**四条规则。**

- **规则一（陈述的闭包）。** 一次构建在链接期、加载期与子进程中看到的，是依赖图陈述的东西；环境中所有已安装内容的并集
  只对陈述了自己环境的工程生效。`docs/23` 已为构建程序的 `PATH` 写下这条规则，本文把它用于另外两条通道。
- **规则二（单一读者）。** 一件事实——清单里有哪些依赖项、一个源文件声明哪个模块、一个产物叫什么——只有一个读取或
  命名的实现，其他位置调用它。
- **规则三（知道即拒绝）。** 规划或链接已经掌握的矛盾，在那一步拒绝并给出补救，不留给编译器、加载器或运行期。
- **规则四（身份与拼写、归属分开）。** 打开文件与启动程序使用给定的拼写；规范路径只用于比较与键。按内容寻址的条目，
  其归属是使用者的集合，不是写入者一人。

**缺陷（十四项）。**

1. 宿主工具的存储条目包含它从自身目录加载的每个图内共享对象；现在只发布可执行文件一个（#535，§4.1）。
2. 一条不变量：镜像的每个 `DT_NEEDED` 在加载期解析到的，是链接期为它读取的那个文件。找不到、被并集视图顶替、链接与
   加载各取一份，是它被违反的三种形式，校验对三者同样拒绝。两侧的输入都已存在：链接的输入记录与校验的搜索闭包
   （#535、#537，§4.1）。
3. mcpp 启动的三种子进程——构建程序、测试程序、`mcpp run` 的程序——的 `PATH` 由同一个函数组成：依赖图陈述的工具的
   目录，工程陈述的环境的 `bin`，mcpp 启动时的 `PATH`，在每个宿主上相同。陈述的工具目录已为运行器查找按计划算出
   （#926，§4.2）。
4. 环境的并集视图（库的 `subos/default/lib`、测试子进程的环境 `bin`）只对陈述了环境的工程进入搜索路径；对未陈述的工程，
   依赖并集才能满足的名字先以弃用项报告，再按弃用表的日期移除（§4.1、§4.2，决定 D1）。
5. `mcpp add` 在基表已有点号键时写点号键；mcpp 的 TOML 读者报告重新打开点号键所建之表的表头（#964，§4.3）。
6. 源文本的「代码文本」（去掉注释与字面量）只有一个实现；模块冲突检查与扫描器共用它（#963，§4.3）。
7. 「一份清单的全部依赖项」只有一个枚举；加载、编辑与发布归一化共用它，`[feature-deps.*]` 因此不再被发布遗漏
   （#962，§4.3）。
8. 依赖包的共享库以限定名命名，名字由对象目录已在使用的同一个规整函数给出（`libcompat_sdl3.so`）；根包自己的产物保持
   目标名（#975，§4.3）。
9. 依赖图替换了 C 库而没有 C++ ABI 的供给者时，目标侧解析以已有的 `layer-requirement` 拒绝，给出两个补救（#898，§4.4）。
10. 链接后的检查读出共享镜像的 `DF_STATIC_TLS` 与 TLS 段大小，超出该行的界限即报告最大的 TLS 符号（#907，§4.4）。
11. 直接执行的产物以 `#!` 指名一个不存在的解释器时，执行之前给出原因与一行 `help:`（#621，§4.4）。
12. 路径依赖与宿主工具的缓存条目记录每一棵使用它的源码树；一棵树被编辑只撤下自己的名字，名字为空才删除条目。两处
    实现合为一个函数（#1025 第 1 项，§4.5）。
13. home 的路径不再被规范化为物理路径；规范化只出现在比较与键中，由一项只减不增的检查守住（#1024，§4.6）。
14. 两项原因未定的缺陷（#1008、#1015）先测量，不设计（§4.13）。

**功能（六项）。**

15. 条件预处理块中的 `import` 不再被拒绝：该单元的导入取自编译器的依赖扫描，机制是已有的 `MCPP_SCANNER=p1689` 路径按
    单元使用。头单元仍然拒绝（#1026，§4.7）。
16. `exports` 中不含通配符的条目是精确名，必须有定义，否则链接失败；渲染方式与 `start` 相同，是行的数据（#982，§4.8）。
17. `mcpp add --build` 把依赖写入 `[build-dependencies]`。一个包是不是构建插件，引擎已经从它的源文件得出（导入只存在于
    构建程序中的模块），不为此新增清单键，也不按名字段推断；写错表的条目由已有的弃用项报告并给出这条命令
    （#993，§4.9）。
18. `[profile.<name>]` 接受 `dialect_cxxflags`，含义与 `[build] dialect_cxxflags` 相同；`cflags`、`cxxflags` 的作用域写进
    SPEC-004（#1025 第 2 项，§4.10）。
19. 命令补全在 mcpplibs.cmdline 中实现为内建行为，mcpp 一侧是一次升级与若干回调（#794，§4.11）。
20. feature 的 `description` 进入示例，并由一项测试核对三个来源一致（#1018，§4.12）。

不在本文之内：`mcpp doc`（#399，已标记 todo）、LLVM 的 ok 镜像（#880）、Clang 的反射行（#215）、上游缺陷登记册
（#1027）、备忘类条目（#558、#973）。

第 10 节的十三项决定已按建议定下。第 12 节是定下之后的自审：它修改了其中两项建议本身（共享库名字的拼法、构建插件的
陈述），并补上了六处 v1 没有写到的约束。

## 2. 实测与代码事实

### 2.1 运行期搜索路径

`mcpp.runtime.search`（`src/runtime/search.cppm`）是搜索顺序唯一的决定处。它给每个目录一个来源，顺序是不可变性递减：

| 来源 | 含义 | 序 |
|---|---|---|
| `Payload` | 工具链载荷的目录，安装后不变 | 0 |
| `Package` | 包以 `[runtime]` 陈述的目录 | 1 |
| `Artifact` | 产物自己的目录（`$ORIGIN`） | 2 |
| `SubosFarm` | `<subos>/lib`：该环境中全部已安装内容的并集视图，任何一次安装都会改写 | 3 |
| `HostDefault` | 宿主加载器的缺省目录，仅当产物由宿主加载器运行 | 4 |

- 并集视图在目标是本机时进入闭包（`runtime_search_closure`，`src/build/plan.cppm`），并作为 RPATH 的最后一项写进产物
  （`ldRuntimeFallback`，`src/build/flags.cppm`）。链接期同一个视图经 `--sysroot=<subos>` 生效。
- 模块的注释写明它为何存在：只存在于环境中的库（`libGL`）曾经能链接而不能启动。它没有区分「工程陈述的环境」与
  「机器上的缺省环境」。
- 运行期闭包的校验（`src/build/runtime_validation.cppm`）把每个 `DT_NEEDED` 对着这份闭包解析，结果写入
  `.mcpp-runtime-verdicts.json` 并发布到 `resolution.json`。只在缺失时拒绝。
- 链接已经记录它读取的文件：链接行带 `--dependency-file=$out.d`（`f.linkReport`，`src/build/flags.cppm`）。
- 宿主工具的存储条目由一次 `stage_file(produced, ctx.binOut)` 发布（`src/build/prepare/features.cpp`），只有可执行文件。

### 2.2 子进程的 `PATH`

| 子进程 | 现状 | 位置 |
|---|---|---|
| 构建程序 | 工程陈述了环境时，该环境的 `bin` 在前；未陈述时与 mcpp 启动时的 `PATH` 逐字节相同 | `src/build/build_program.cppm`；`docs/23` §2 |
| 测试程序 | 工具链所在环境的 `bin` 在前，不论工程是否陈述环境；Windows 上整段被编译掉 | `src/build/execute.cppm`（`sandboxBin`） |
| `mcpp run` 的程序 | 只设置运行期库路径（`compute_run_env`） | 同上 |

依赖图陈述的工具所在的目录已经按计划算出：`ctx.xlingsDepBinDirs`（`src/build/prepare/plan.cpp`），含依赖构建出的程序
（`rootTools`）、被覆盖的载荷与每个包的 `[xlings.workspace]` 条目；条目按 `toolPurpose` 取舍，运行层（`when = "run"`）
在会运行的动词下属于它。它现在只被运行器的查找读取。

`docs/23` §2 对构建程序写明了规则：把共享目录放在每个工程前面，会使一次构建看到的东西取决于这台机器上还装过什么；
陈述才使它出现。

### 2.3 同一事实的多个读者

| 事实 | 读者 | 差异 |
|---|---|---|
| 源文本中的代码 | `strip_noncode`（`src/modgraph/scanner.cppm`）；片段拆分的读者（`modules/buildopt/src/source.cppm`）；`declared_module_roots` 等四个按行匹配的函数（`modules/manifest/src/mangle.cppm`） | 前两者去掉注释与原始字符串；第三组不处理，注释中自述了这一限制 |
| 清单的依赖表 | 加载器（`modules/manifest/src/toml.cppm`）；编辑器 `upsert_dependency_text`（同文件）；发布归一化（`src/publish/normalize.cppm`） | 归一化只遍历 `dependencies`、`build-dependencies`、`dev-dependencies`；编辑器只认 `dependencies` 与 `dev-dependencies` |
| TOML 的表 | mcpp 的读者（`modules/libs/src/toml.cppm`）；编辑器写出后用同一个读者复核 | 读者接受 TOML 1.0 禁止的重复定义，复核因此通过 |
| 库的文件名 | 静态库在 `obj/<拥有者>/` 下（#896 之后）；共享库 `place(target_output(...))` 放在 `bin/` | 共享库的名字只取目标名 |
| 条目属于哪棵源码树 | `replace_tree_siblings`（`src/build/prepare/dependency_cache.cpp`）；`tool_store::write_entry`（`modules/buildmcpp/src/tool_store.cppm`） | 同一规则写了两遍 |

编辑器对非缺省命名空间总是写 `[<表>.<ns>]` 表头，代码注释称之为规范的命名空间子表；它不检查基表中是否已有 `<ns>.` 开头的
点号键。

### 2.4 规划时已知而未拒绝

- 目标侧的报告为没有供给者的层打印「—」后继续；拒绝码中有 `layer-requirement`（包所要求的层没有被给出）与
  `layer-ordering`，没有覆盖「替换了 C 库而 C++ ABI 无人供给」。
- C++ 运行时的契约按角色决定（`src/build/distribution.cppm`）：共享库角色在 ELF 上的缺省是与工具链的共享运行时耦合，
  原因写在注释中。#907 的镜像没有 `libstdc++.so` 的 `DT_NEEDED`，说明那一行或那份清单给了共享库角色另一种契约；
  是哪一种未测定。
- `start` 的要求已有渲染：`start_link_flags` 以 `--defsym` 把未定义的入口变成链接错误（`src/build/ninja_backend.cppm`）。
  `exports` 渲染为版本脚本、Mach-O 的导出列表或 PE 的 `.def`，条目是模式，不要求定义。

### 2.5 路径

`absolute_home`（`src/home.cppm`）以 `weakly_canonical` 处理 home。以 `MCPP_HOME=<符号链接>/home` 运行 `mcpp self env`，
home、xlings、配置与缓存的路径全部以物理路径打印（2026.11.26.1，Linux）。`src/` 与 `modules/*/src/` 的非测试代码中共有
约九十处 `canonical(` 调用，其中 `src/build/` 四十处（含 `prepare/` 二十五处）、`src/toolchain/` 十一处、`src/pack/` 十处。
`contains_path` 已经用 `std::filesystem::equivalent` 比较身份。

### 2.6 扫描

- 规划期的词法扫描在遇到条件块内的 `import` 时拒绝（`if_depth > 0`），遇到头单元时拒绝。
- 扫描器自己的注释写明：它是这门语言的第二个读者，第一个是编译器，两者不一致时以编译器为准。
- 规划期已有另一条扫描路径：`MCPP_SCANNER=p1689` 时 `scan_packages_p1689` 以编译器的依赖扫描代替词法扫描
  （`src/modgraph/p1689.cppm`，`src/build/prepare/scan.cpp`）。它是整次构建的开关。
- 构建期每个单元的编译器扫描（`.ddi`）与 `scan_overrides` 的陈述逐次核对。

### 2.7 profile 的编译词

`state.profileCflags` 与 `state.profileCxxflags` 只追加给根与被选中的成员（`src/build/prepare/graph.cpp`，注释写明这是
有意的）。`[build] dialect_cxxflags` 到达标准库模块的预编译、扫描与每个单元，但 `[profile.<name>]` 不接受这个键。
SPEC-004 §9 没有写出 profile 的 `cflags`、`cxxflags` 的作用域。

## 3. 概念与取舍

### 3.1 四条规则各自的来由

规则一来自 `docs/23`：它已经是构建程序 `PATH` 的规则，理由写在那里。并集视图本身不是缺陷——它是「环境是我的根」的
运行期一半——缺陷在于它对从未陈述过环境的工程同样生效，而缺省环境为这台机器上的每个工程共享。#535 的「开发机通过、
干净机器失败」、#537 的「链接一份、加载另一份」与 #926 的「Linux 上碰巧能找到」是这同一件事在三条通道上的表现。

规则二来自扫描器自己的注释与 #963、#962、#964、#975、#1025 第 1 项：每一项都是第二个实现与第一个不一致。

规则三是 `AGENTS.md` §2 的「做得更少不沉默」在时间上的一半：拒绝不仅要有原因与补救，还要发生在掌握事实的那一步。

规则四把两类混淆分开。路径的规范形式是身份，不是地址；内容摘要是身份，不是归属。

### 3.2 不采用的方案

| 方案 | 不采用的原因 |
|---|---|
| 为每个计划建一个只含陈述内容的目录，RPATH 与 `PATH` 指向它 | 陈述的库目录与工具目录已经是按计划算出的列表（`Package` 来源、`xlingsDepBinDirs`）；再建目录是同一份事实的第二种表示，并且在 Windows 上需要链接或复制 |
| 宿主工具一律静态链接其依赖 | 依赖以何种形态被消费由消费者陈述（#519）；引擎替工具改写它，会让同一个包在工具中与在程序中形态不同而无处陈述 |
| 在 `[build] ldflags` 中出现宿主目录时告警 | 判据落在拼写上而不是事实上；规则三要的比较（同一 soname 的两个文件）两侧输入都已存在 |
| 只在冲突时给共享库加限定名 | 产物的名字会随闭包中其他包而变，增加一个依赖就改名 |
| 让 `cxxflags` 到达图中每个单元 | 会把 `-Werror`、`-D` 之类的词送进索引中的第三方包，并使每个依赖按 profile 各编译一份；「整图的编译词」已有拼写 |
| 在词法扫描器中对条件求值 | 第三个不完整的预处理器实现；工具链内建宏只有编译器知道 |
| 为构建插件新增一个包级的陈述键 | 引擎已经从源文件得出这一事实（导入 `mcpp.core` 的包被记为构建插件），feature 的 `rule_module` 是它已有的陈述；再加一个键是同一事实的两种拼写。消费侧的 `host-module` 是边上的请求，不是包的性质 |
| 引擎按包名第二段是 `mplugin` 判定构建插件 | 把一个索引的命名约定写进引擎；该规则在提出时已有例外（冻结的旧名、`mcpp.plugins`、同目录的 `mcpp.platforms`），私有索引不必遵守 |
| 命令补全保留「生成各 shell 的完整脚本」作为可选后端 | 一个概念两套机制；每种 shell 一份命令行解析的副本 |
| 把 home 的规范化保留为一个开关 | 两种路径语义并存；给定拼写在每个宿主上都可用，规范形式只在比较时需要 |

### 3.3 设计准则与本方案的对应

| 视角 | 准则 | 本方案中的体现 |
|---|---|---|
| 架构 | 机制在引擎，事实在数据 | 精确名的渲染、TLS 界限、库的前后缀都是行或包的数据；消息指名能力而不指名包 |
| 收敛 | 一个概念一种拼写，一个机制一处实现 | 不新增机制：搜索来源、链接输入记录、`xlingsDepBinDirs`、`MCPP_SCANNER=p1689`、`start_link_flags`、`dialect_cxxflags`、`layer-requirement`、弃用表都是已有的 |
| 封闭 | 宿主与环境只在数据或陈述允许处进入 | 并集视图只对陈述了环境的工程生效；缺省环境不再是每个工程的隐含输入 |
| 稳定 | 结果是陈述的函数，不是历史的函数 | 另一棵源码树的编辑、另一个工程的安装、home 的另一种拼写都不改变本次构建 |
| 兼容 | 已发布的键与行为经弃用表移除 | 四处行为变化各有弃用标识与日期（§6）；不改名任何已发布的键 |
| 用户体验 | 拒绝给出原因与补救 | 六处新的拒绝或报告，每处一行 `help:`，补救是命令时写出完整命令 |
| 简洁 | 删除多于增加 | 删去两份重复的条目清理、四个按行匹配函数各自的缺陷、测试子进程的平台分支 |

## 4. 设计

### 4.1 运行期库：不变量、发布、核对（#535、#537）

**不变量。** 镜像的每个 `DT_NEEDED` 在加载期解析到的文件，就是链接期为它读取的那个文件。现有的校验只检查了它的一种
违反形式（加载期找不到）。弃用表中已有同类的先例：`undeclared-cxx-runtime`——链接行上出现而没有包声明的 C++ 运行时，
2027.1 移除。本节把同一要求从 C++ 运行时推到每一个共享对象。

**发布。** 宿主工具是一个镜像，与其他镜像相同：它的存储条目是可执行文件，加上它的链接从子构建的 `bin/` 读取的每个图内
共享对象（来自子构建计划的共享链接单元，与链接输入记录一致）。它们由同一个发布步骤放入条目，条目的有效性判断包含
它们。工具的 RPATH 中已有 `$ORIGIN`，不需要新的搜索项。

**核对。** 校验为每个 `DT_NEEDED` 记录它解析到的文件及其来源；链接输入记录给出链接读取的共享对象。两侧按规范路径比较，
不同时再比较内容摘要，仍不同即拒绝，原因标记 `runtime-closure`。加载期找不到的既有拒绝取同一标记，它此前没有标记。
比较的结果随校验的判定一起缓存，判定的指纹包含链接输入记录，没有变化的镜像不重新比较。消息的形状（包名为示意）：

```
error: [runtime-closure] libgbm.so.1 is linked from one file and loaded from another
         linked  /usr/lib/x86_64-linux-gnu/libgbm.so.1          ([build] ldflags: -L/usr/lib/x86_64-linux-gnu)
         loaded  <home>/registry/subos/default/lib/libgbm.so.1  (subos_farm)
       help: declare the package that provides it instead of a host directory: [xlings.workspace] "xim:mesa" = "<version>"
```

核对适用于每个带动态段的镜像：程序、共享库、测试、宿主工具。校验本来就跳过的交叉目标不在其内。它同时覆盖 #535 中被
并集视图悄悄顶替的情形：图内包构建的共享对象在链接期来自 `bin/`，加载期若来自别处即是不一致。

**并集视图的范围。** 按规则一，`SubosFarm` 只在工程陈述了环境（`[xlings] subos`）时进入闭包与 RPATH；链接期的
`--sysroot` 用同一条规则、同一个日期，否则会出现能链接而校验拒绝的中间状态。对未陈述的工程：

- 陈述的库目录仍然在闭包中：`Payload`、`Package`（`[runtime]`）、`Artifact`，以及图中各包的 `[xlings.workspace]` 条目所
  安装载荷的库目录——后者与 `xlingsDepBinDirs` 同源，按计划算出，来源记为 `Package`。
- M1 若表明还需要这些载荷所声明依赖的闭包，该闭包取自提供者：存储回收已经按它计算引用集合，mcpp 经提供者的端口查询，
  不重算。
- 只有并集视图能满足的 soname 由校验报告，补救是陈述该包，或以一行 `[xlings] subos = "default"` 显式陈述使用共享的缺省
  环境——后者之后的行为与此前完全相同。
- 过渡经弃用表：标识 `implicit-default-environment`，自实施版本起为未陈述工程中每个仅由并集视图满足的 soname 报告一次，
  移除月份不早于 2027.3，由 M12 的用量确定。

陈述了环境的工程行为不变：环境是它的陈述，并集是它自己的。

### 4.2 子进程的 `PATH`（#926）

mcpp 启动三种子进程：构建程序、测试程序、`mcpp run` 的程序。它们的 `PATH` 由一个函数组成，三段依次是：

1. 依赖图陈述的工具的目录（`xlingsDepBinDirs`）；
2. 工程陈述的环境的 `bin`，仅当工程陈述了环境；
3. mcpp 启动时的 `PATH`。

- 测试与运行的程序经运行契约的环境（`run_contract_env`）得到它；快速路径随构建记录这份值，与契约中的其他变量相同。
- 构建程序此前只有第 2、3 段。加入第 1 段之后，构建程序以裸名调用的工具若被依赖图陈述，取陈述的那一份。这是陈述的
  含义，也是一处行为变化，记入 §6。
- Windows 上不再有被编译掉的分支。llvm 在环境 `bin` 中登记的 `cl`、`link`、`lib`、`rc` 垫片不是陈述的工具，不在第 1 段
  （#726 保持修复）。该变量在 Windows 上不区分大小写，函数读写进程中既有的那个键。
- 载荷的程序不在自身 `bin/` 下、而由索引以别名提供时（`[xlings.workspace] program =` 已能解析这种名字），第 1 段取别名
  解析到的目录；`when = "run"` 的条目是否全部在列表中，与 #926 的两个包一起由 M2 核对。
- 测试子进程现有的「环境 `bin` 在前」是第 2 段的无条件形式，改为有条件，经 `implicit-default-environment` 过渡。mcpp
  自己的测试所调用的 `ninja`、`patchelf` 在 mcpp 的清单中陈述为测试层的工具。

### 4.3 单一读者（#964、#963、#962、#975）

**代码文本（#963）。** 「去掉注释与字面量之后的源文本」只有一个函数，取 `modules/buildopt/src/source.cppm` 的实现
（它处理原始字符串、数字分隔符与续行），放在扫描器、buildopt 与 `mcpp.pm.mangle` 都能导入的最低一层包中。
`strip_noncode` 与 `mangle.cppm` 的四个按行匹配函数改为在它的结果上匹配。`mangle.cppm` 注释中关于注释与字符串的
限制说明随之删除。

**依赖项的枚举（#962）。** `modules/manifest` 提供一个枚举：给定清单，产出每个依赖项及其所在的表——`dependencies`、
`build-dependencies`、`dev-dependencies`、每个 `feature-deps.<feature>`、每个 `target.<选择器>` 下的同名表。加载器的
校验、`mcpp add` 与 `mcpp remove` 的编辑、发布归一化都经它遍历。归一化按依赖项的身份改写，不按 TOML 键的形状，
「键以包自身名字开头」的情形（`hanim.core`）因此与其他项同路径；它在归一化中的具体成因在实施时读出（§9）。

**依赖的写法（#964）。** 编辑器的规则：目标表中已有以 `<ns>.` 开头的点号键，或已有 `<ns>` 这个键时，新项写为该表下的
点号键 `<ns>.<name> = …`；已有 `[<表>.<ns>]` 表头时写进该节；两者都没有时写点号键。读者一侧，表头重新打开一个由
点号键建立的表是 TOML 1.0 的错误；由于旧版 `mcpp add` 写出过这种文件，读者先以弃用项报告
（`reopened-dotted-table`，`help:` 给出等价的点号键写法），编辑器在下一次编辑该表时改写为合法形式，到期后拒绝
（决定 D4）。

**共享库的名字（#975）。** 依赖包的共享库文件名与 SONAME 取规整后的限定名。对象目录已经用
`sanitize(qualified_package_name(…))` 区分包（`obj/compat_sdl3/`），共享库用同一个函数，得到 `libcompat_sdl3.so`、
`libmcpplibs_mwrap_sdl3.so`；前后缀仍是行的数据。根包与被选中成员自己的产物保持目标名；目标陈述了 `soname` 时以陈述
为准。两个包陈述了同一个 `soname` 时规划拒绝（`soname-collision`），指出两个包。静态库不变：它们已经在
`obj/<拥有者>/` 下。这是文件名的变化，进入 CHANGELOG；mcpp 同时控制链接与搜索路径，链接与加载不受影响，打包的清单随
名字变化。

### 4.4 知道即拒绝（#898、#907、#621）

**C++ ABI 无供给者（#898）。** 目标侧解析在依赖解析之后进行一次。那时已知：`c-abi` 的供给者是否来自依赖图、`c++-abi`
有无供给者、计划是否编译 C++（任一 C++ 单元或标准库模块）。三者为「是、无、是」且清单没有陈述 `cxx_runtime` 时，
以 `layer-requirement` 拒绝，请求者是根包。消息的形状：

```
error: [layer-requirement] the graph supplies the C library (musl, openkal-musl@0.28.0) and no package supplies the C++ ABI
       the host's C++ library is built against another C library
       help: add a dependency that provides mcpp:c++-abi, or state [build] cxx_runtime = "host-coupled"
```

补救指名能力而不指名包：哪个包提供它是索引的事实，引擎不写包名，也不为一条消息遍历索引。

**共享镜像的静态 TLS（#907）。** 链接后的 ELF 检查（运行期校验所用的同一个读者）读出动态段的 `DF_STATIC_TLS` 与
`PT_TLS` 的大小。共享库角色的镜像带有该标志且 TLS 段超过该行的界限时报告，列出最大的 TLS 符号及其所属对象；界限是
C 库的数据，不是引擎的常数。带该标志的镜像在进程启动时随程序加载没有问题，失败只发生在 `dlopen` 时；链接时不知道
镜像将如何被加载，因此缺省是经 `diag::degraded` 报告而不是拒绝；陈述了精确导出名的镜像（§4.8，由宿主按名字进入）
超界时拒绝，标记 `static-tls-image`。界限的取值在测定之后确定（§9）。产生该镜像的运行时契约若是某一行的
缺省，修正那一行的数据是同一轮的工作。

**`#!` 的解释器（#621）。** 采用已有实现，改两处：补救行用 `help:`；命令写出本次构建所用的工具链，而不是占位符。
`docs/20` 中「mcpp 尚未解释」的那句话随之改写。

### 4.5 缓存条目的归属（#1025 第 1 项）

条目旁的 `source` 记录写入者一棵树。改为记录每一棵使用它的树：

- 命中一个带树的条目时，把本树加入记录（已在其中则不写）。
- 以新摘要写入条目时，在同包同树的其他摘要的条目中撤下本树；记录为空的条目删除。
- 记录以替换写入（`write_replacing`），两个进程同时命中不丢失名字。
- 这条规则只有一个函数，路径依赖的缓存与宿主工具的存储都调用它；它放在两者都依赖的包中（§7）。
- 已删除的检出留下的名字不再被撤下，条目落到按最后使用时间的回收（`[cache] unused_days`），这是既有的兜底。
- 记录是条目旁的新文件 `users`，每行一棵树。旧的 `source` 只读不写，读作第一棵树。原因是新旧版本的 mcpp 会共用一个
  home（自举版本与刚构建出的版本即是如此）：旧版本在新条目中找不到它认识的 `source`，既不会删除新条目，也不会覆盖
  新记录。旧版本写出的条目仍按旧规则被旧版本删除，这一点在旧版本退出使用之前不变。

`--cache local` 不把宿主工具移出共享存储：这是存储的性质（工具按内容与目标寻址，跨工程共享），写进 `docs/09`。

### 4.6 路径的拼写（#1024）

- **规则。** 用户与环境给出的路径（`MCPP_HOME`、`MCPP_TOOLCHAIN`、参数、工作目录、`mcpp` 自己的位置）在打开文件与启动
  程序时保持给定的拼写，只做绝对化与词法归一。规范路径只用于判断两个路径是否同一对象，以及需要与拼写无关的键。
- **home。** `absolute_home` 改为 `absolute` 加 `lexically_normal`。`contains_path` 等比较已经使用 `equivalent`。
- **其余约九十处。** 每一处归为「身份」或「地址」。身份的调用改经一个命名函数（放在 `mcpp.home` 或 `mcpplibs.os.fs`
  已有的路径工具旁），地址的调用去掉规范化。
- **检查。** `.github/tools/check_path_identity.sh` 统计该命名函数之外的 `canonical(` 与 `weakly_canonical(`，逐文件
  对照一份只减不增的基线，做法与 `check_waits.sh` 相同。
- **键。** 以路径为输入的键（描述性计划的工作目录、条目的 `source` 记录）继续用给定拼写的词法归一形式：两种拼写得到
  两个键，多一个缓存条目，不产生错误结果。
- **比较失败时。** 规范化在受限环境中会失败（上级目录不可访问）。身份函数失败时退回词法比较，并经 `diag::degraded`
  报告一次，说明哪一项判断是在没有身份的情况下作出的。
- **进程层。** 报告的第 3 节（以别名路径启动的工具仍报拒绝访问）指向进程层按规范路径启动镜像，属于 mcpplibs.os 与
  openkal-windows；在那里以替身环境测定后另行记录，不在 mcpp 中绕过。

### 4.7 条件 `import`（#1026）

词法扫描在一个单元中遇到处于条件块内的 `import` 时不再拒绝，而是把该单元标记为「导入由编译器回答」：

- 该单元的导入集合取自编译器的依赖扫描，传入该单元实际的编译词（含 `defines`、`dialect_cxxflags` 与目标的条件配置）。
- 规划期已有的实现（`src/modgraph/p1689.cppm`）只构造 GCC 的命令；构建期的 dyndep 边已经为 GCC 与 Clang
  （`clang-scan-deps`）构造同一种扫描。两处合为一个命令构造函数，规划期与构建期共用。
- 工具链不提供依赖扫描的行保持拒绝，消息说明原因；各行的可用性由 M11 测定。
- 模块声明仍由词法扫描读取；声明本身处于条件块内时，同样取编译器的结果。
- 扫描结果随它读过的文件一起缓存：扫描写出的依赖文件列出该单元包含的头文件，条件可能取决于其中定义的宏，其中任何
  一个变化都使结果失效。只按源文件与编译词缓存是不够的。
- 不新增开关。作者对扫描结果的显式覆盖已有 `scan_overrides`，整次构建改用编译器扫描已有 `MCPP_SCANNER`。
- 头单元仍然拒绝，消息不变；`scan_overrides` 与 `MCPP_SCANNER=p1689` 不变。
- 构建期的 `.ddi` 核对对这些单元照常进行，规划期与构建期出自同一个读者。

代价是每个这样的单元在规划期多一次预处理。它只发生在含条件导入的单元上；一个工程有多少这样的单元，以 #421 中的
工程为例是 17 个（共 322 个接口单元）。

### 4.8 宿主调用的名字（#982）

`exports` 的条目分两种：含通配符的是模式，行为不变；不含通配符的是精确名，表示「宿主按这个名字进入镜像」，必须有定义。

- 渲染是行的数据，与 `start` 同一机制：ELF 上沿用 `start_link_flags` 的做法（未定义即链接错误）；Web 行渲染为
  `-sEXPORTED_FUNCTIONS`，名字的前缀规则在该行的数据中；PE 与 Mach-O 各自的拼写在实施时测定（§9）。
- 精确名是链接器层面的符号名。C++ 的名字由陈述者写出修饰后的形式，或以 `extern "C"` 导出。
- Android 的 `JNI_OnLoad`、`ANativeActivity_onCreate` 由定义它们的入口包（`main = { from = … }` 所指的包）在自己的
  目标上陈述；应用不重复陈述。一个名字在闭包中只被陈述一次，重复陈述相同的名字不是错误。
- 这适用于每一个没有程序起点的镜像：Android、Web、Python 扩展（`PyInit_*`）、插件式共享库。
- 兼容：现有清单中不匹配任何符号的精确名此前被无声忽略，此后是链接错误。经弃用表过渡（`unmatched-exact-export`），
  先报告后拒绝；只在部分目标上有定义的名字移到条件表 `[target.<选择器>…]` 下。
- 到期之后的失败来自链接器。mcpp 以已有的「失败之后追加说明」的做法（协程限制的提示即是）补一行，指出该名字来自
  `exports`。

### 4.9 `mcpp add --build`（#993）

引擎已经知道一个包是不是构建插件：它的单元导入只存在于构建程序中的模块（`mcpp.core`）时，规划把它记为构建插件，并在
构建程序的配置下规划（`src/build/prepare/host_graph.cpp`）；feature 的 `rule_module` 是同一事实已有的陈述。因此：

- **不新增清单键或描述符键。**「这个库供构建程序使用」已经由源文件回答，再要包陈述一次是同一事实的两种拼写。消费侧的
  `host-module` 是一条边上的请求，不是包的性质，不借用它的名字。
- **`mcpp add --build`。** 与 `--dev` 对称，写入 `[build-dependencies]`。编辑器的布尔 `dev` 换成表的枚举，与 §4.3 的
  枚举同源。
- **写错表的条目。** 构建插件被写进 `[dependencies]` 时，弃用表已有 `host-module-in-dependencies`（2027.1 移除）：现在
  按构建依赖读取并告警，到期拒绝。它的补救行改为写出完整的命令：`mcpp remove <包>`，然后 `mcpp add --build <包>`。
- **`mcpp add` 不猜。** 它只有描述符，没有源文件；不带 `--build` 时写入 `[dependencies]`，由上一条在第一次规划时指出。
- **命名约定。** `<owner>.mplugin.<name>` 留在索引中，是给人读的约定，由索引自己的检查维护。引擎不读名字。

### 4.10 profile 的整图编译词（#1025 第 2 项）

- `[profile.<name>]` 接受 `dialect_cxxflags`，含义、到达范围与 `[build] dialect_cxxflags` 相同（标准库模块的预编译、
  扫描、每个单元），在 `[build]` 的同名键之后追加。工作空间层的 profile 同样接受。
- SPEC-004 §9 增加一条：profile 的 `cflags`、`cxxflags` 是根位置的键，到达根包与被选中成员的单元；`opt`、`debug`、
  `ndebug`、`dialect_cxxflags` 与 `ldflags` 到达整张图。`docs/04` §2.9 写明同一事实。
- `-p <成员>` 与 `--workspace` 下同一个库的编译词不同，是这条规则的直接结果，文档以一个例子说明；需要整图一致的词
  写进 `dialect_cxxflags`。
- C 单元没有对应的键，本设计不增加。整图一致之所以是 C++ 单元的要求，是因为 BMI 与标准库模块必须以相同的方言编译；
  C 单元之间没有这种耦合，包的 C 编译词是包自己的。SPEC-004 写明这一点。
- 使用新键的清单陈述 mcpp 的下限：旧版本对未知的 profile 键只告警并忽略，没有下限的清单会被缺一半配置地构建。

### 4.11 命令补全（#794，mcpplibs/cmdline#9）

设计在 cmdline 中，mcpp 是使用者。cmdline 一侧（六个讨论点已定）：

| 层 | 内容 |
|---|---|
| 事实 | 选项与位置参数上的可选值集合、文件或目录提示、候选回调；命令的隐藏标记；位置参数的可重复标记 |
| 引擎 | 一个纯函数：命令树与光标前的词 → 候选与一个指令。它与解析共用同一个「这个词是什么」的归类函数 |
| 入口 | 一个隐藏命令，结果按固定文本协议打印；走 `--help`、`--version` 的路径，返回「已处理、不是错误」 |
| 适配器 | bash、zsh、fish、PowerShell 各一段静态脚本，只依赖程序名与入口名 |

- 开启是一个函数：`app.completion()`；带参数的形式决定是否自动加可见的 `completions <shell>` 子命令与入口的名字。
  缺省关闭，升级不改变行为。
- 现有导出的签名全部保留；`App::completions(Shell)` 与 `generate_completions` 的输出从完整脚本变为适配器；三个生成器
  分区删除。
- 可选值集合同时用于解析校验、帮助文字与候选。
- 入口不联网、不写文件；回调的行为由应用负责。

mcpp 一侧：升级 cmdline；`app.completion({.command = ""})`，脚本由 `mcpp self completion [shell]` 写到
`<home>/config/shell/`；为包名（本地索引缓存）、目标、工具链、profile、成员提供回调；独立安装器修改 shell 配置是显式
选择；三个以描述中的「(internal)」标识的命令改用隐藏标记。入口在解析处返回，不应触发 home 的初始化，由 §8 的用例断言。
入口的启动耗时设预算并在 CI 中测量（§9）。

## 6. 兼容性

行为变化与各自的过渡：

| 变化 | 影响 | 过渡 |
|---|---|---|
| 并集视图只对陈述了环境的工程生效（库、链接期的 `--sysroot`、测试子进程的 `PATH`） | 未陈述环境而依赖缺省环境中内容的工程 | 弃用表 `implicit-default-environment`：先逐项报告，到期移除；一行 `[xlings] subos = "default"` 保持原行为 |

| 条目的使用者记录改用新文件 `users` | 新旧版本共用的 home | 旧的 `source` 只读不写；旧版本不删除新条目 |

| `[profile.<name>] dialect_cxxflags` | 旧版本忽略该键 | 使用它的清单陈述 mcpp 的下限 |
| 读者报告重新打开的点号键表 | 旧版 `mcpp add` 写出的清单 | 弃用表 `reopened-dotted-table`：先报告，编辑器在下次编辑时改写，到期拒绝 |
| 三个新弃用项的移除月份 | — | 不早于 2027.3（弃用版本之后至少两个整月），由 M12 的用量确定 |
| 依赖包的共享库改用限定名 | 以 `--linkage shared` 打包的产物清单；按文件名引用依赖共享库的脚本 | CHANGELOG；陈述了 `soname` 的目标不变 |
| 精确的 `exports` 名必须有定义 | 列出不存在的精确名的清单 | 弃用表 `unmatched-exact-export`：先报告，到期为链接错误 |
| 链接与加载不一致即拒绝 | 以宿主 `-L` 链接而由环境满足加载的工程（#537 的构造） | 无过渡：这是此前未被发现的错误产物 |
| C++ ABI 无供给者即拒绝 | 此前在标准库模块预编译处失败的构造 | 无过渡：失败提前，并带补救 |
| home 不再规范化 | 输出中的路径与给定拼写一致；以路径为键的条目多出一个拼写 | 无过渡：旧条目按最后使用时间回收 |
| cmdline 的 `completions(Shell)` 输出改变 | 已安装旧脚本的用户继续可用；新脚本是适配器 | cmdline 的版本说明 |

不变的：没有已发布的清单键被改名或移除；`scan_overrides`、`MCPP_SCANNER`、`[xlings] subos`、`host-module` 的现有含义
不变；陈述了环境的工程的搜索路径不变。

## 10. 已定的决定

十三项按建议定下。D3 与 D10 的内容经自审修改（§12），表中是修改后的结论。

| 编号 | 事项 | 结论 |
|---|---|---|
| D1 | 并集视图的范围 | 只对陈述了环境的工程生效：库的搜索路径、链接期的 `--sysroot`、测试子进程的 `PATH` 三处同一规则、同一日期，经 `implicit-default-environment` 过渡 |
| D2 | 宿主工具的共享依赖 | 发布进条目，不改写依赖的形态 |
| D3 | 共享库的命名 | 依赖包用规整后的限定名（与对象目录同一个函数），根包保持目标名；陈述的 `soname` 优先，重复即拒绝 |
| D4 | 重新打开的点号键表 | 经 `reopened-dotted-table` 先报告后拒绝；编辑器在没有既有形式时写点号键，并在下次编辑时修复非法形式 |
| D5 | 静态 TLS 超界 | 降级报告；陈述了精确导出名的镜像拒绝 |
| D6 | `--cache local` 与宿主工具 | 不改行为，写进文档 |
| D7 | 路径的键与检查 | 键按给定拼写；身份比较容忍失败并报告；检查用只减不增的基线 |
| D8 | 条件导入 | 缺省启用，不加开关 |
| D9 | 精确的导出名 | 同一个键，经 `unmatched-exact-export` 先报告后成为链接错误 |
| D10 | 构建插件 | 不新增陈述键；`mcpp add --build`；写错表的条目由已有的 `host-module-in-dependencies` 处理，日期 2027.1 |

**仍然存在的风险。**

1. D1 的实现量取决于 M1。若陈述的载荷目录不足以满足加载，需要提供者给出依赖闭包的查询，这是跨仓库的工作。

   先修这些包再发布。
5. 共享库改名没有过渡期。按文件名引用依赖共享库的外部脚本会在升级后失败，只有 CHANGELOG 告知。

**#1015 的测量（§4.13）。** 在 mcpp 2026.11.27.1 与 clang 23.1.3 上按报告的三个单元（`c` 一个文件，`b` 导入 `c`，
`main` 导入 `b`）复现：编辑 `c` 的函数体（长度不变）之后的构建编译 `c` 与 `b`，下一次无编辑的构建编译 `main`，再往后
不编译。第二次构建之前 `ninja -n -d explain` 的解释：

```
ninja explain: recorded mtime of obj/main.o older than most recent input
  /tmp/m1015/target/x86_64-linux-gnu/<fp>/pcm.cache/c.pcm
```

`ninja -t deps obj/main.o` 列出的 `c.pcm` 与 `b.pcm` 是绝对路径：clang 按 `-fprebuilt-module-path=<构建目录>/pcm.cache`
找到它们，依赖文件照此书写；而图中 `c` 的边以相对路径 `pcm.cache/c.pcm` 声明这个输出。同一个文件在 ninja 中是两个
节点：第一次构建中 `c` 的边重写了相对节点，`b.pcm` 的内容不变而被保留，`main.o` 因此不重编；绝对节点没有产生它的边，
ninja 在构建开始时读过它的时间，之后不再读，于是下一次构建才发现它比 `main.o` 新。原因成立，GCC 的依赖文件以相对的
`gcm.cache/…` 书写，不受影响。路径是绝对的有它的原因（`compile_commands.json` 的 `directory` 是工程根，clangd 在那里
解析该路径），因此不改编译命令，也不改写依赖文件（只有经执行器的边才能改写，且生成头文件的节点本是绝对路径）：
写出 BMI 的每条边（编译、两段式的预编译、拆分调度的 BMI 边、`std` 与缓存条目的暂存）把绝对拼写一并声明为隐式输出，
ninja 由此知道两个拼写由同一条边写出（SPEC-018 §1 第 6 条）。修复后同一构造中，编辑之后的构建编译 `c`、`b` 与
`main`，其后无编辑的构建不编译（e2e 1176，在 macOS 与 Windows 以缺省的 clang 运行）。#1008 本轮未测量。

本地验证（Linux x86_64，GCC 16.1、LLVM 23.1.3）：

- 条件导入：宏未定义时条件块中的 `import` 不进入图，定义后进入；头单元仍被拒绝（e2e 1172）。
- 两个短名相同的包以共享形态链接，得到 `libacme_util.so` 与 `libbeta_util.so`，程序运行；陈述同一 `soname` 被拒绝（e2e 1167）。
- 链接读 `a/libfoo.so`、运行路径给出 `b/libfoo.so` 的构建被拒绝并指名两个文件（e2e 1168）；#537 的构造（宿主
  `/usr/lib` 的 zlib 链接，`xim-x-zlib` 载荷加载）同样被拒绝。
- 4096 字节 initial-exec TLS 的共享镜像被报告，陈述精确导出名时被拒绝（e2e 1169）；未定义的精确导出名被报告（e2e 1170）。
- 两棵内容相同的树共用一个条目，一棵被编辑后另一棵的条目保留，两棵都编辑后旧条目被删除（e2e 1171）。
- 重新打开的点号键表被读取、报告，`mcpp add` 之后的清单被 Python 的 `tomllib` 接受（e2e 1173）。
- 依赖图提供 C 库而无 C++ ABI、导入 `std` 的计划在编译之前被拒绝（e2e 1174）。
- `mcpp __complete` 每次约 1 ms，读取配置的候选（工具链、包）约 20 至 40 ms；不创建 home，不写入配置；隐藏命令不被补全；工具链与包的候选由用例自己写出的存储条目与索引副本核对（e2e 1175）。
