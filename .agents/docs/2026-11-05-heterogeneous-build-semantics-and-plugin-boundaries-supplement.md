# 异构构建语义与插件边界补充方案（mcpp#885、mcpp#887）

**读者：** review 本轮生态设计及实现 mcpp、规则插件和计算库的维护者。

**本文回答的问题：** 通用构建机制如何承载异构与多后端需求，并据此划分缺陷、优化和责任。

**范围之外：** GPU 算法、运行时调度策略、厂商工具参数的完整设计，以及尚未实现能力的使用手册。

**状态：** D1–D10 的方向已获用户同意；实验细化待评审，见 §16 与

本文不是实现完成记录，不直接采纳 #887 的补丁。

## 1. 提议结论与交付边界

1. mcpp 核心继续持有通用构建图、依赖与作用域、产物身份、兼容性和执行契约。
   计算模型、设备目标值域、工具调用和设备链接流程由插件与相应包承担。
2. island 继续作为优先接入范式。它的施工范围可以是一组单元或一个组件，
   不预设为一个源文件或一个 kernel。扩大施工范围的可行性与代价需要验证。
3. 不因缺少某种现成插件就新增核心构建模式。核心扩展需要一个现有通用契约
   无法表达的具体反例，并说明插件侧组合不能满足需求的原因。
4. 多后端的源码选择、同产物共存、同实现多设备目标和运行时协作分别建模。
   使用一个厂商的工具或设备，不隐式启用以该厂商命名的另一套源码实现。
5. #887 先拆分为规则解析缺陷、目标与工具请求的语义缺口，以及独立的缓存调查。
   最终语法由这些关系和现有兼容性共同决定，不能由临时补丁反推。
6. 当前不能宣称全部 HPC 场景已被覆盖。本方案给出覆盖判据与实施顺序，
   不把架构可表达、驱动展开或局部控制等同于实际 GPU、多节点运行验证。

本文作为 #885 的补充设计接受 review，不自动改变其已有发布验收条件。
本轮没有因本文新增核心字段、插件 API、发布版本或 #887 的修复完成声明。
是否将相应实现纳入 #885 当前交付，由 review 明确，避免设计讨论隐式扩大发布范围。

## 2. 设计依据与不变量

现行 SPEC-007 区分配置、施工和校验。插件规划动作，施工通过具有输入输出的
action 执行；本方案要求新增工具参数和厂商知识由插件承担。核心现有设备兼容性
比较仍含模型知识，见 §14.5，不能将目标边界误写为当前实现已经完全满足。
SPEC-004 分别定义字段作用域、
来源和条件，条件不能改变字段本身的作用域。SPEC-002 约束目标侧与运行时兼容性。

本方案保留以下不变量：

| 编号 | 不变量 | 实现后果 |
|---|---|---|
| I1 | 一个源码单元具有明确的编译所有者，一个输出具有唯一生产者 | 插件不能因 glob 匹配次序夺取核心已经分类的 `.cpp` 或 `.cppm` |
| I2 | 选择一种实现不隐式选择另一种实现 | SYCL 的 NVIDIA 目标不能独立导致 `.cu` 源码进入构建 |
| I3 | 工具依赖来自声明及请求 | store 中碰巧存在某工具不使它自动成为本次构建的输入 |
| I4 | 配置只依赖声明的输入 | 不根据未声明的 GPU、工具路径或施工结果改变图 |
| I5 | 请求、编译计划和实际产物分别可判定 | 声明两个目标不等于已经生成两个镜像 |
| I6 | 影响构建的有效输入进入相应身份与失效链 | 修改目标、规则源码、工具或已声明输入不能错误复用旧结果 |
| I7 | ABI 与运行库约束在实际组合范围内成立 | C 函数入口不能自动证明两套 C++ 运行时安全共存 |
| I8 | 运行策略保持独立 | 节点数、设备选择与回退策略不隐式改变无关编译输入 |

I8 的独立性取决于实际用途。节点数若参与代码生成就是构建输入；仅作为启动参数时，
不应因此使同一程序重新编译。配置分类依据是影响，而不是参数名字。

## 3. 语义关系与最小表达

### 3.1 五种关系

| 关系 | 含义 | 现有承载点 | 责任 |
|---|---|---|---|
| 实现选择 | 本次包含工程中的哪些实现 | feature、源码条件、现有 accelerator 成员选择 | 工程声明；核心按契约选择 |
| 设备代码要求 | 某一实现需要生成的目标与可移植形式 | accelerator 的目标描述及插件选项 | 目标分工为核心传递结构、插件解释值域；当前比较器的遗留见 §14.5 |
| 构建供给 | 哪个编译器、设备库和工具满足计划 | 依赖、toolchain、payload、按需 provision | 包与插件提供；工程可覆盖策略 |
| 产物事实 | 实际包含的镜像、ABI、资源和运行依赖 | 产物核验、兼容性及打包元数据 | 插件或工具测量；核心保存和核对通用契约 |
| 执行策略 | 设备选择、回退、进程及节点分配 | 应用、runner、run_under、执行配置 | 应用或执行适配层 |

这些关系是分析模型，不是五个拟新增的 manifest 字段。先使用现有通道，
表达不了再提出最小的通用扩展，不为每个计算框架增加一套配置语言。

### 3.2 请求具有归属

以 #887 为例，语义上的请求是“SYCL 实现生成 NVIDIA 目标的设备代码”。
NVIDIA 是这条请求的设备目标，CUDA 工具包是完成施工所需的供给，
二者都不等于工程中另一个 CUDA 源码实现被选择。

推荐继续评估既有的“实现名称与其目标集合”的结构。核心按名称精确识别实现成员，
保留目标集合的归属；插件只解释自己负责的目标值。通用解析和模型知识分开。

`sycl+{sm_89}`、混合 SPIR-V 的写法和厂商别名均属于待评审候选，
本文不把它们宣布为已实现的规则接口。目标值域、别名、缺省形式、非法输入诊断
与既有版本字段的含义需一起定稿。编译器和工具包的具体版本继续由工具链、依赖
与锁记录约束，不借设备目标字符串增加第二套包版本选择机制。

### 3.3 简洁性的判据

同一个事实只声明一次，由它派生需要的配置。选择目标后，插件据此请求工具并生成
编译和设备链接参数；工程无需再重复声明“为了这个目标安装哪些规则内部工具”。
项目主动选择的库、运行时和部署策略仍由工程声明，不能被规则的工具默认值覆盖。

输入的便利写法不削弱内部结构。集合应有明确的等价、重复和顺序规则；
命令 argv 仍保持顺序，不能把所有列表都按集合排序。
归一化变化需要兼容性与缓存迁移说明，不在本补充设计中直接改变既有构建身份。

### 3.4 平台与计算实现的正交关系

平台描述宿主对象及程序的构建、运行约定，计算实现描述特定设备施工。一个项目
可以在同一平台上使用多个实现，同一种实现也可以有适用于不同平台的工具与运行库。
openkal-platform 不是替 CUDA、SYCL 新增的一种互斥计算后端。

正交不等于任意组合均可运行。插件与包仍需声明支持的宿主 ABI、驱动接口和运行
依赖；已有原生设备驱动不能未经适配就视作 openkal 内部可用。核心核对通用目标侧
及产物契约，平台包和计算插件分别承担适配。本文没有 openkal 加任意 GPU 后端的
端到端验证，不由多后端源码示例推导出这一支持结论。

## 4. island 的覆盖判据

### 4.1 三个独立层次

| 层次 | 判据 | 不能据此推出的结论 |
|---|---|---|
| 图的表达能力 | 能声明所需输入、动作、依赖、输出与消费关系 | 任意源码无需修改即可接入 |
| 程序语义 | ABI、内存、异常、设备链接及资源生命周期保持 | 性能、调试和增量构建代价相同 |
| 开发与工程成本 | 源码迁移、接口数量、调试、IDE、增量和跨包复用成本可接受 | 全部 HPC 工作负载已获验证 |

当前实现的设备单元路径、架构上的 island 边界与 `mcpp.tools.island` 辅助工具
分别描述不同范围。辅助工具的限制不能自动升级为核心构建图的限制。

### 4.2 施工范围

优先让插件在一个组件内组织多个翻译单元、设备链接、宿主对象和资源封装，
以明确的接口和产物接入主图。不要为保持单文件规则的形态而把每个 kernel
都切成独立接口，也不要为扩大施工范围而允许多个编译器无声明地拥有同一源码。

对于普通源码中的 OpenMP offload、stdpar 或既有大型工程，可评估由插件或外部
构建适配器拥有整个组件。它是否保留原源码、模块协作、宿主 ABI、设备符号与调试
体验，需要真实项目控制；当前缺少现成路径不能证明该方式必然不可行。

可执行外部构建命令只是接入的起点。要形成受支持路径，还需声明完整输入、
产物与使用需求、正确失效与运行闭包，且不在规划期通过扫描施工结果决定图。
组件中的普通 `.cpp` 也需要明确的所有权声明与消费边界；本节没有批准插件按
扩展名或导入顺序接管主图源码，也没有证明当前辅助工具已经提供完整的组件接口。

### 4.3 核心扩展的准入

提出核心新机制时提供以下材料：

1. 一个具有明确交付目标和约束的最小真实场景。
2. 现有 actions、产物、依赖、使用需求与执行接口的表达尝试。
3. 无法表达或只能破坏 I1–I8 才能表达的具体关系。
4. 不携带厂商或计算框架知识的最小通用契约。
5. 至少两个用途的覆盖判据，或只有一个用途时对其通用性的具体论证。

“没有现成插件”“不能原样编译旧工程”与“现有图无法表达”分开记录。
源码兼容性可以是独立需求，但不能省略第 2、3 项论证。

## 5. 多后端的组合方式

| 编号 | 场景 | 接口与构建要求 | 主要责任 |
|---|---|---|---|
| M1 | 仓库保留多套实现，本次选一个 | 同一逻辑入口的替代实现，仅所选实现进入链接 | 工程选择；核心条件选择；插件编译 |
| M2 | 一个产物同时包含多套实现 | 每套实现有可同时存在的内部入口，外层提供统一接口或注册表 | 计算库或工程组织接口和分派；插件交付产物 |
| M3 | 一套实现包含多个设备代码目标 | 编译与设备链接使用同一目标集合，核验镜像覆盖 | 对应规则插件 |
| M4 | 同一进程使用多个后端或设备协作 | 运行时对象、内存、上下文、同步和错误处理有明确协议 | 应用与运行时库 |
| M5 | 不同程序或节点采用不同组合 | 每个产物有自身构建闭包，执行配置选择相应程序和资源 | 工程、依赖与执行适配层 |

M1–M5 可以组合。例如一个库以 M2 同时提供 CUDA 和 SYCL 实现，其中 SYCL 又以 M3
包含多个设备目标；应用以 M4 选择设备。这不要求核心增加五种构建模式。

### 5.1 替代与叠加的符号边界

当前 `tools-island` 的多 roots 描述同一入口的替代定义，约定一次只链接一个。
将这些定义同时链接不是 M2 的正确实现。C 链接名称不因 C++ namespace 不同而隔离。

M2 使用独立内部入口和外层分派。当前 `multi-backend` 示例已按此方式组织
CUDA、Vulkan 和 CPU。它证明这一图形态在源码中可表达，不构成 CUDA、SYCL、HIP
任意组合的运行验证。本轮未重新执行该示例的 GPU 验收。

若项目反复手写入口组织、注册与接口校验，可在插件辅助库减少机械工作。
分派优先级、可用性判断和运行时回退仍由计算库或应用决定，不由核心推断。

### 5.2 进程级约束

同时链接的实现遵守统一的宿主 ABI 与运行库约束。一个 `extern "C"` 入口不自动
隔离异常、分配器、全局 ABI 符号或运行时。继续使用 SPEC-002 的统一、孤岛和宿主
决定模式及其条件，不通过追加链接参数绕过兼容性检查。

## 6. mcpp#887 的分类与责任

分类依据是当前发布版和准确源码控制；Issue 的成功补丁属于报告者证据，
不自动证明每一项根因推断或当前版本中的行为。

| 编号 | 现象 | 分类 | 归属与处置 |
|---|---|---|---|
| B1 | SYCL 解析按普通逗号切分，架构集合变空 | 已确认解析 bug | mcpp-plugins 修正；HIP 同类代码一并核对 |
| B2 | SYCL chunk 的目标集合未被规则消费 | 目标表达缺口；已接受目标静默退化属于正确性问题 | 插件明确支持值域与诊断，不能以缺省 SPIR-V 掩盖不支持的请求 |
| B3 | 建议启用 `cuda` 来表达 SYCL 的 NVIDIA 目标 | 插件对既有选择语义的误用 | 修正规则的目标归属和建议，不改变核心对显式 CUDA 成员的正常选择 |
| B4 | 所需 CUDA payload 只在 SYCL、CUDA 同时选中时声明 | 工具请求与目标需求不一致 | 插件按实际目标请求已声明的工具；复用按需 provision |
| B5 | 被选中的 `.cu` 没有任何动作编译，核心拒绝 | 正确的覆盖检查 | 保留检查；可优化诊断以展示选择来源和规则归属 |
| B6 | 同一后端的版本或架构约束不满足，核心拒绝 | 正确的约束检查 | 不改为静默过滤；未选中的其他实现仍按既有语义排除 |
| B7 | store 中工具已安装，但本次未声明，规则读不到 | 声明范围的预期行为 | 修复声明或请求；不增加任意搜索 store 的回退 |
| B8 | 修改安装目录内的插件版本包后继续复用 | 不可变源码假设与诊断问题 | mcpp 单独明确契约；不是 SYCL 专属缺陷 |
| B9 | `sycl` 与带架构的请求共用构建指纹 | 本次 11.3.1 通用路径未复现 | 保留调查项；取得准确入口、工具链、有效请求与缓存证据后再归因 |
| B10 | 没有 NVIDIA 时要求自动改用 CPU | 需要代码覆盖、运行环境与应用策略共同满足的需求 | 构建规则生成被请求的形式；应用或运行时决定回退 |
| B11 | 请求缺少右括号或附带未消费尾部，11.3.1 仍构建成功 | 第二轮已复现的通用输入验证问题 | mcpp 完整验证通用结构；插件继续验证模型值域 |
| B12 | 同名实现出现两次，交换次序改变源约束是否通过 | 第二轮已复现的顺序相关行为 | mcpp 明确重复成员政策，不再按第一个成员无诊断判断 |

B2 的具体拼写支持属于接口设计，不能仅因核心能够传递一个字符串就断言规则已经
支持其全部值。输入的非法形式、不支持的目标、环境缺失和待安装工具应分别诊断。

## 7. 推荐的插件侧设计

### 7.1 通用读取与模型专属解释

在插件通用库收拢线格式的读取与括号感知切分，形成一个内部结构供各规则读取。
实现名称使用精确匹配；目标列表、版本和可移植形式修饰保留归属。
不要继续在各规则中用独立的 `split` 与 `starts_with` 推导成员关系。

核心继续定义通用线格式与归一化契约。L2 承担统一读取；L3 解释自身目标值及
调用工具的方式。本节未批准新的公开模块名或 API；若需要核心新增结构化读取接口，
先说明现有通道的不足，并保持接口不含厂商枚举。

### 7.2 工具请求与阶段

规则声明自己的编译工具及允许工程覆盖的默认值。只有部分目标需要的工具采用
现行 `provision = "on-request"`，在目标解析后请求。项目明确自备工具时，遵守
现行选择优先级，不重复下载。工具的选择和来源通过已有 decision 通道记录。

pending 表示引擎需要安装后重跑：程序正常返回，不提交依赖该工具的配置，也不报成
工具缺失。环境尚不完整时遵守 SPEC-007 的规划义务，尽可能输出确定配置和警告；
施工及环境校验经对应 action 完成。错误的请求形式与环境缺失不是同一类问题。

本方案不引入“目标厂商包含某值”的新 cfg，也不把 CUDA 工具包知识放入核心。
已有条件和按需请求不能覆盖的实际反例，才进入核心通道扩展评估。

### 7.3 多阶段编译

同一已解析目标集合同时驱动设备编译与设备链接。规则显式声明中间产物与依赖边，
不能让编译阶段和链接阶段各自解析一次并得到不同目标。

跨翻译单元、跨静态库的设备链接单列验收。若现有 actions 能表达，责任在插件；
若跨包产物及其使用需求无法传递，先提供最小反例，再设计通用产物传递或依赖契约。
具体设备链接命令继续属于插件，不能把 `nvlink` 或特定 SYCL 驱动流程嵌入核心。

### 7.4 兼容性

既有显式多成员请求继续表示同时选择这些成员，不能根据源码是否存在或某个规则是否
被导入，把 `sycl, cuda...` 静默改判为只选 SYCL。需要迁移的旧建议应提供明确诊断与
替代路径。本文不决定弃用日期，也不删除现有拼写。

## 8. 身份、产物与缓存

### 8.1 三类记录

| 记录 | 内容 | 校验目标 |
|---|---|---|
| 请求 | 工程选择与约束 | 明确用户意图及选择来源 |
| 有效计划 | 已解析目标、工具与声明输入、动作和依赖 | 不发生错误命中，不遗漏编译或链接阶段 |
| 产物事实 | 实际代码镜像、ABI、资源与运行依赖 | 元数据与发布产物一致 |

构建身份由影响对应工作的有效输入决定，不只哈希未经解析的字符串，
也不把所有执行参数无区别纳入全图指纹。插件的配置、动作命令与输入应形成完整
失效链。集合顺序的等价性与命令参数的顺序敏感性分别处理。

产物事实可以先通过 check action 与报告核验。是否新增可供跨包消费的机器元数据，
由具体需求决定。本文不宣称现有打包已经自动核验并发布全部设备覆盖信息。

### 8.2 源码身份

11.3.1 当前将索引版本包和固定 Git 源按不可变身份处理，path 源码按可变树摘要处理。
索引安装目录原地修改与 path 开发的契约不能混同。

推荐维持显式来源的边界：开发使用 path 或明确的替换来源，发行补丁进入可追踪
源码身份。若正式支持安装目录原地修改，应按可变来源跟踪；若坚持不可变，应在相应
输入校验中给出污染诊断或明确恢复方式。二者需要单独 review，不以每次全量哈希
所有已安装包作为未经测量的默认方案。

声明安装时的内容摘要不能独立证明安装后未被修改；诊断污染还需要有效检测机制。
同样，只在 `entry.json` 中没有看到源码摘要，不能证明整条构建失效链没有源码跟踪。

## 9. HPC 场景的覆盖账本

覆盖的对象是具体场景和约束，不是框架名称的数量。

| 场景组 | 当前证据与边界 | 继续验证的内容 |
|---|---|---|
| 原生 C/C++ 与模块 | 核心已有构建和目标侧契约 | 与外来编译组件的接口、使用需求和 ABI 一致性 |
| CUDA、SYCL 等设备单元 | 已有规则与 fixture；#887 暴露组合缺陷 | 单目标、多目标、多实现组合及错误输入 |
| HIP 的 AMD 路径 | 当前规则明确拒绝缺失的 ROCm 载荷 | 包供给、插件计划、实际运行分开验收 |
| CPU OpenMP | 索引有运行库与消费示例 | 不以此代替 GPU offload 验证 |
| 整组件 offload 与 stdpar | 当前没有完整的现成路径 | 组件所有权、原源码接入、ABI、增量和调试成本 |
| 跨库设备代码 | 单文件编译路径不足以证明覆盖 | 设备符号闭包、链接时机、库复用和失效 |
| MPI 与多节点 | 依赖、capability 和执行通道可作为接入基础 | 实现及 ABI 一致性、站点工具身份、实际多节点测试 |
| BLAS 等数值库 | 已有 capability/provider 机制及部分包 | 整数宽度、线程运行库和链接组合的具体兼容性 |
| 外部 HPC 工程及其他语言 | 可评估外部构建适配 | 完整输入、产物、使用需求、闭包与复现能力 |

MPI 启动、站点环境、Slurm 等知识留在执行适配和相关包中。核心提供通用执行与
结果契约；应用的通信、设备调度、内存互操作和故障恢复不由构建系统自动保证。

## 10. 实施顺序与责任

| 阶段 | 工作 | 归属 | 前置与退出条件 |
|---|---|---|---|
| P0 | 固化 #887 最小复现、确认解析缺陷与选择来源 | 插件为主，核心提供诊断证据 | 当前错误可观测，避免测试依赖清缓存才成立 |

发布最低版本依据实际使用的核心协议确定，不因文档基线较新而无理由抬高插件门槛。

### 10.1 最短推进路径

先完成 P0 的确定性解析修复；P1 的 review 与核心独立项调查可以同时进行。
P1 定稿后验证工具请求和单实现目标，继而验证 P2 的共存，再推进 P3 的真实工程。
只有 P3 的反例证明通用契约不足时，才进入 P4，不能把未证明需要的核心改动设为
插件修复的前置。

默认平台升级 D7、兼容性审计 D9、进度可见性 D10 相互独立，也不是 #887 解析修复
的技术前置。D7 若纳入后续 mcpp 发布，仅等待 PL 矩阵中与默认组变化有关的检查；
不能只凭单机显式消费通过就发布。#885 原有引擎、服务器和性能验收按其既定依赖
推进，保留独立失败归因，不以新增设计项延长其发布链。

## 13. 首轮 Review 决策项

本节保留首轮取舍与依据，方向已获用户同意。第二轮实验和具体收敛见 §16；
尚待确认的细节由该节及研究记录更新，不将同意方向等同于实现完成。

### D1. 通用核心与 island 的施工范围

**推荐：** 保留 island 优先，以具有明确输入、产物和接口的组件作为可评估的最大
施工范围。先验证组件内多 TU、设备链接及整组件 offload，再判断是否缺少核心契约。
不为 CUDA、SYCL、OpenMP 分别引入核心构建模式。

**需要 review：** “可接入”是否还要求既有普通源码无需改写、C++ 模板或模块可直接
跨边界使用，以及调试与增量成本的预算。这些目标不能由动作图可表达性代替。
整组件方案若只能靠未声明源码接管或丢失使用需求完成，就仍有待解决的契约缺口。
验收为 A11、A13、A16 与一个真实 offload 工程；尚不作全部 HPC 覆盖声明。

### D2. 实现选择、设备目标与工具供给

**推荐：** 一个请求保留“所属实现—设备目标集合”的关系。SYCL 面向 NVIDIA 只使
SYCL 规则请求相应工具，不隐式选择 CUDA 源码实现。显式选择 CUDA、SYCL 两个成员
仍表示选择两套实现；核心的源码覆盖与约束拒绝保持有效。

**需要 review：** 目标的缺省形式、混合可移植代码与 AOT、别名、重复及集合顺序，
以及现有版本修饰的精确含义。`sycl+{sm_89}` 只是待定候选，不能先补解析再宣布
整套语义稳定。非法请求与不支持请求明确失败，不静默变为空集合。验收为 A1–A8。

### D3. 统一读取与按需工具请求

**推荐：** 核心定义已有通用线格式，L2 统一读取，L3 解释目标值与施工流程。
优先复用声明内的 on-request provision；首次缺工具走 pending、安装、重跑。

**需要 review：** 先确认现有协议是否足够；只有确有跨规则的结构读取缺口时，才增加
不含厂商枚举的核心接口。工具版本继续由依赖和工具链选定，不能在目标字符串中再建
一套版本解析体系。SYCL 的某些目标确需 CUDA 工具，A1 限制的是误启用 CUDA 源码
流程。验收同时覆盖首次安装、自备工具、无关工具不请求及离线诊断。

### D4. 替代、共存与运行时协作

**推荐：** M1 用选择关系，M2 用不同内部入口与外层分派，M3 用同一实现的设备目标
集合。M4 的设备、内存和同步协议交给应用及运行时。辅助库可以生成重复的入口与
注册代码，不能替应用决定分派优先级或回退策略。

**需要 review：** 共享逻辑接口的声明放在工程还是计算库，以及是否已经有足够重复
代码值得抽公共辅助库。C 入口隔离符号并不隔离 C++ 运行库。现有显式 exclusive
capability 已实现；不能对所有后端施加全局互斥。若两个独立程序各需不同互斥
provider，先复现当前选择范围是否过宽，再评估按链接闭包约束，不直接新增作用域。

### D5. 缓存与来源身份

**推荐：** 分别调查索引描述符及载荷更新、已安装源码污染、实际构建有效输入。
三个问题分别核对来源修订、安装内容身份及动作失效链；清缓存不能作为修复验收。

**需要 review：** 继续保持发行包不可变、开发使用 path 的契约，还是正式支持修改
安装目录。推荐前者，并另行设计有成本依据的污染检测与恢复诊断。安装时的一次摘要
不能检测安装后的修改。本轮 11.3.1 通用目标切换与 path 头文件控制通过，#887 的
具体缓存报告仍需独立复现；不得据此宣布不存在其他缺陷。验收为 A8–A10。

### D6. 当前交付与后续探索的边界

**推荐：** 已确认的解析 bug 先独立修复；目标接口定案后完成请求与工具闭环，
再验证共存及跨库场景。新的核心机制只由真实反例推动。#885 原有发布验收继续单独
跟踪，设计草案不代表引擎、服务器或性能验收已通过。

**需要 review：** 默认平台升级是否另立 mcpp 补丁，以及进度可见性和兼容性审计
是否进入后续任务。推荐它们与 #887 插件修复并行，避免形成无技术必要的串行依赖。
APE 单文件、clang/lld 映像化继续属于显式后续项，见 §14.2。

### D7. openkal 默认平台版本与显式平台选择

**推荐：** 如需零配置项目继承 0.23.5 的更新，后续 mcpp 补丁升级内置平台 pin，
按完整平台组验收。已发布的 11.3.1 保持其实际 0.23.3 默认；显式选择与已有锁记录
继续按既有规则约束，不通过索引更新静默替换已固定的平台。

**需要 review：** 本轮只要求消费者显式固定 0.23.5，还是同时要求 mcpp 的零配置
默认跟进。前者已存在实际消费证据，后者仍需核心版本发布，二者不能互相替代。
当前默认已含 Linux 0.24.1 的 Landlock 修复，不能把默认升级描述为该安全修复尚未
交付。接受的代价是明确发布一次默认变化；收益是未显式配置者获得更新且可复现。

### D8. 平台声明与核心专属分支

**推荐：** 核心解释平台通用契约，平台包声明工具链、运行层、编译链接约定、seal、
runner、carrier 和版本组，平台插件提供相应格式的施工。Linux/macOS/Windows 实现
与 libc/runtime 的缺陷在相应包修复，核心不增加对应系统调用知识。

**需要 review：** 对载体安装宿主识别、后缀回退、launcher 自举逐项提供契约依据。
优先使用已声明角色及运行宿主，不以搜索删除所有 `openkal` 字符串作为重构目标。
launcher 自己的 os/platform 组合独立于应用平台；默认 pin 升级须同时复核该组合。
非 openkal 平台的具体失败反例，才决定是否增加通用元数据，见 §14.4。

### D9. 设备兼容性比较的既有模型知识

**推荐：** 先承认并审计核心已有 `sm_`、`compute_`、`a/f`、PTX floor 和同主版本
兼容假设。不将这些数字规则继续套给新后端，也不把通用读取与语义兼容比较混为一项。

**需要 review：** 最小可版本化的兼容关系是否可由声明描述，例如精确匹配和明确的
覆盖关系；其数据来源、可信边界及旧描述符语义都需定案。未知模型宜保守匹配，
但改变现有行为需迁移控制。预构建包筛选不能为了比较而临时下载并执行构建插件，
也不为此引入任意表达式 DSL。尚未实测一个其他后端的错误接受或拒绝，故此项为
已有语义耦合审计，不是已复现的通用兼容性 bug。

### D10. 嵌套构建的进度可见性

**推荐：** 保留外层 action 完成计数，另行呈现活动 action、阶段、耗时，以及子构建
有依据的计数。由插件或执行适配报告子阶段，核心提供通用传递与呈现，不内置 LLVM
日志解析。普通日志仍可使用，但结构化进度需区分来源、顺序和完成状态。

**需要 review：** 先做独立的可见性优化还是制定结构化通道。后者还需覆盖 Ninja
缓冲、取消、并发输出、有界传输及现有机器输出契约。未知总量只显示阶段与时间；
心跳不表示编译仍有进展，子进度到 100% 也不替代 action 成功退出。AOT、打包、
代码生成和外部 CMake 工程均可复用此机制。该项未实现，不是已证实的调度死锁。

review 后以追加具名修订或后续记录保存决策。已发布实现的使用说明与规范修订，
随实际落地范围分别进入 `docs/` 与 `docs/specs/`，不把本设计草案直接作为使用承诺。

平台固定的是一起构建验证的依赖组。工程的覆盖若产生互相矛盾的精确版本，应展示

目标图、宿主构建程序、工具与载体各自遵守现有图和使用角色，不能假定所有宿主工具
都应链接目标图的 libc/runtime。平台造成的编译参数变化也应到达 std BMI 与其身份。

### 14.4 平台抽象的具体审计点

1. **核心默认表。** `modules/toolchain-model/src/triple.cppm::kKnownTargets` 的
   两个 pin 是默认选择。存在具名内置目标不违反通用构建设计；审计对象是行为依赖
   声明还是依赖目标名字。e2e 952 的非 openkal 平台是已有的通用性证据。
2. **Windows launcher。** `src/pack/pack.cppm::launcher_platform` 使用核心默认
   平台，`exe_launcher_manifest` 固定自己的 os 0.2.9。应用显式选择旧平台时，
   launcher 仍应使用与自身源码匹配的自举组合。e2e 995 正是这一控制，不能简单
   把 launcher 改为继承应用平台。后续默认升级应复核 os/platform/CRT/runner 组合。
3. **载体的安装宿主。** `src/pack/distribution.cppm::program_host` 对 openkal
   carrier 有专属判断。若其他非原生目标也使用 carrier，该关系可能应来自运行宿主
   元数据。当前未构造失败反例；先核对已有 `runs_on` 能否覆盖，再决定最小变化。
4. **文件角色。** `role_of` 保留 `.oke`、`.okso` 回退，但已声明角色优先，打包
   流程也显式记录 entry、program 和 launcher。不能断言更换后缀必然打包失败。
   新格式先声明角色；只有必要的旧包识别保留约定回退。
5. **seal 与格式插件。** 工具校验失败由核心如实拒绝，格式/ABI/工具缺陷回到平台
   包或实现包定位；若引擎错误传递参数、输入或阶段依赖，则由核心修正通用执行
   契约。归因先核对实际命令与产物，不能只根据最终失败阶段决定。取消校验或放宽
   发布门槛不能替代根因修复。

建议平台变更的验收分母如下；这是一份待执行矩阵，未整体标为通过。

| 编号 | 控制 | 断言 |
|---|---|---|
| PL1 | 不声明平台的新工程 | 使用新 mcpp 发布声明的默认组，来源可解释 |
| PL2 | 显式旧平台、显式新平台与既有锁 | 遵守选择和锁规则，不被默认或索引 latest 静默替换 |
| PL3 | 版本组冲突 | 指出请求者与矛盾版本；合法组合通过 |
| PL4 | 宿主图、目标图与跨架构 runner | 角色和工具链正确，不串用目标运行库或错误宿主程序 |
| PL5 | 平台编译参数及 std BMI | 同步生效，变化进入相应构建身份；无变化可复用 |
| PL6 | 旧应用平台与新版核心 launcher | launcher 自举组合正确，Windows 可执行及打包可用 |
| PL7 | 非 openkal 平台、显式角色与 carrier | 以声明驱动通用行为；无额外 carrier 时保留现有成功路径 |
| PL8 | self-contained/vendored 与 emit xpkg | 包装载体、所需 runner 和实际系统架构一致，不夸大覆盖 |
| PL9 | 索引普通安装及离线复用 | 完整发布组可获取；离线缺载荷明确诊断，不污染既有版本 |

### 14.5 设备兼容性残留与核心改动准入

`src/pack/abi_tag.cppm::accel_arch_level` 识别 `sm_`、`compute_`；
`accel_arch_covers` 解释 `a/f` 后缀；`accel_accepts` 使用 PTX floor，并对 backend
名称应用同主版本兼容判断。这些是当前存在的语义知识，不是仅有括号切分规则。
未知字符串中的前导数字也可能进入比较，不能据“核心未列举所有厂商名称”证明通用。

因此，“把解析收拢到插件 L2”不能解决全部核心边界问题。进一步设计应至少给出：
两个具有不同覆盖/版本规律的模型、旧元数据的兼容策略、未知关系的保守行为，以及
不执行任意插件的预构建筛选方案。精确相等与显式覆盖数据是候选起点，不在本轮
直接增加字段或改写既有接受集合。产物事实的真实性还需生产侧核验，不能由消费侧
兼容比较独立保证。当前没有自动生成全部 `accel` 事实的交付证据。

## 15. 多视角自审与修订结论

本节记录首轮对渲染成文的第二遍阅读；通过表示表述与当时证据相符，不表示提案已经
实现。第二轮实验补充及结论见 §16 和调研记录。

| 视角 | 检出的歧义或风险 | 修订与结论 |
|---|---|---|
| 使用者语义 | NVIDIA 设备目标可能被误读成 CUDA 源码选择 | §3、D2 保留归属；A1 允许确有所需的 CUDA 工具，通过 |
| 核心架构 | 把理想分工写成当前核心没有厂商知识 | §2、§14.5 明确现状与审计准入，通过 |
| 插件实现 | 每条规则独立 split、重复解析导致计划不一致 | §7、D3 统一读取及同一目标集合驱动各阶段，通过 |
| island 覆盖 | 图可表达被扩大为所有旧源码与性能都能保持 | §4、D1 分开三层判据并保留真实组件验证，通过 |
| ABI 与同产物共存 | C 入口被当成完整运行库隔离 | §5.2、D4 保留运行库和链接闭包约束，通过 |
| 来源与增量 | 一次内容摘要被当作污染检测，旧报告被当作当前 bug | §8、D5、§14.2 明确检测缺口与未复现范围，通过 |
| 平台版本与安全 | 新平台已发布被等同默认已升级；误称旧默认未含 Landlock 修复 | D7、§14.3 分别记录默认、显式消费和准确组内容，通过 |
| 自举与交叉构建 | launcher 或宿主工具无条件继承应用目标平台 | D8、§14.4 保留独立角色与自举约束，通过 |
| 打包与部署 | 文件后缀回退被当作唯一机制，#860 开着被当作仍未实现 | 显式角色优先；公开包实跑校验系统架构，通过 |
| 可观测性 | 完成项比例当成耗时比例，心跳当成施工进展 | D10、§14.2 区分外层计数、子阶段与实际完成，通过 |
| 兼容与演进 | 将现有数字兼容规则直接移除或扩散到所有后端 | D9 保留迁移要求并禁止盲目泛化，通过 |
| HPC 运行验证 | 驱动展开、源码示例或单机探针被写成 GPU/集群已验证 | §9、§11、§12 明确验证层级与缺失环境，通过 |
| 发布与责任 | 重新打开已实现的 L 项，或新增设计挟持 #885 发布范围 | §14.1 分清旧项状态，D6 要求独立验收，通过 |
| 文档与 review | 决策表缺少具体取舍，读者无法决定接受的边界 | D1–D10 给出推荐、待定项、代价及验收，通过 |

首轮 D1–D10 的方向现已同意；第二轮待 review 的细化见 §16。运行证据缺口按
A1–A16、PL1–PL9 及调研记录的 V1–V9 跟踪，不由文字自审替代。

## 16. 第二轮调研后的收敛（2026-11-05）

用户已同意首轮十项方向，并要求 D10 的进度能力可在 build.mcpp 中按需配置。
本节更新仍未明确的接口、缺陷归属和实施顺序；原 §15 为首轮自审记录，第二轮
自审和实验以[调研记录](2026-11-05-heterogeneous-build-research-and-experiments.md)为准。

### 16.1 可选子进度

推荐 `mcpp::action` 新增默认关闭的 `bool progress`，在 build.mcpp 中写
`a.progress = true`。这是拟议接口，11.3.1 尚无该字段。配置只声明参与报告，实际
计数由执行期工具或插件 adapter 提供，不在规划期运行子构建。

核心提供每运行、每 action 独立的快照通道；插件通用辅助负责可选写入，工具规则
解释自己的阶段。采用最新状态而非无界日志；建议 8 KiB 上限、单写者原子替换、
递增序号及每秒五次写入限频。普通 action 不受启用要求约束，计数和心跳不能声明
构建成功。随机通道与实时内容不进入构建身份；修改构建程序启停开关仍可能重建。

Linux 原型通过普通、verbose、并行、关闭、失败及进程组取消控制。普通模式约
0.469 s 读到子进度，外层 Ninja 约 1.347 s 才输出；子进度 3/3 后失败仍无 stamp。
原型不是当前核心 UI；跨系统、NDJSON 兼容与实际调度集成仍需实现和验收。

### 16.2 新确认的核心正确性问题

1. **通用结构未完整验证。** 发布版实际接受 `sycl+{sm_89` 与
   `sycl+{sm_89}garbage`。核心负责完整消费结构和报告位置，插件负责目标值域。
2. **重复成员顺序影响约束。** 源约束 sm_90 时，两个 sycl 成员先 89 后 90 被拒绝，
   先 90 后 89 则通过。推荐拒绝重复实现并提示合并目标集合，集合内去重及规范化
   另行明确；不再无诊断地只比较第一项。
3. **工作空间作用域过宽。** 两个独立程序各依赖一个 provider，单独构建运行通过，
   合并构建被 exclusive 检查拒绝。去掉 exclusive、增加各自的 requirement，仍被
   全局多候选检查拒绝。推荐 requirement 在最终消费上下文内绑定，保留应用为
   库声明的需求供给 provider 的能力，不能仅限于库自身的子依赖；exclusive
   在实际链接组合闭包检查，不新增用户可选的互斥模式。单程序双 provider 拒绝保留。

因此，“exclusive 已有实现”仍成立，但不能再据此把工作空间组合范围也标为正确。
这些是通用核心缺陷，不要求插件增加 GPU 专属绕过。

### 16.3 请求与规则阶段

SYCL 推荐规范表达收敛为所属实现内的有域目标集合，例如
`sycl+{spir64,nvptx64-sm_89,nvptx64-sm_90}`。既有核心形状可传递，现有发布插件
尚未实现相应消费。裸 `sycl` 保留缺省 SPIR-V；显式集合只生成列出的形式。
CUDA 工具由该 SYCL 请求按需取得，不以启用 CUDA 成员作为条件。

实际 DPC++ 控制完成了多 TU 的 sm_89/sm_90 与 SPIR-V/sm_89 两种组合，并从最终
程序提取镜像；单目标跨静态库也通过。但多目标与静态库组合出现设备符号重复定义，
设备执行则被系统驱动 mismatch 阻止。后续规则验收保留这些交叉组合及失败诊断，
不把独立 SDK 编译通过写成插件、跨包或 GPU 执行通过。

驱动调用优先使用已验证的明确 triple 与后端参数。别名本身编译通过，失败限定为
本版驱动的别名与 save-temps 组合，不能扩大为“别名不受支持”。

### 16.4 平台、兼容性和缓存的边界

默认平台升级按已同意的 D7 推进后续补丁设计，仍需 PL1–PL9。非 openkal 平台的
e2e 952 本轮实际通过。合成 carrier 元数据实验确认专属分类存在，但没有真实其他
carrier 的端到端交付证据；优先评估已有 `runs_on` 和角色，不新增重复宿主字段。

数字及同主版本兼容已存在公开契约。本轮优先修结构与作用域，新 SYCL 使用有域
opaque 目标走精确路径；不为 #887 引入 `accel_match` 或覆盖 DSL。旧契约的迁移
仍独立保留，不声称厂商语义已经全部移出核心。

集合换序实际造成不同指纹，属于冗余构建优化，不是错误命中证据。不可变发行包与
可变 path 的来源边界保持；不以一次摘要声称能检测安装后污染，不承诺启用遥测时
零重建，也不因本轮进度设计引入安装源码全量扫描。
