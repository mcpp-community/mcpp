## 2. 判定的依据

一项请求纳入方案须同时满足三条：它在一个以上的工程或平台上出现（通用）；现有机制不能表达它（必要）；它的解法符合 AGENTS.md
第 2、3 节的约束。不满足第三条而问题本身成立的，改用符合约束的解法（#955、#952 的第 1 项、#931 的两个候选接口）。

十个 issue 的原因归为五类，方案按类给出，而不是逐个修补：

| 类 | 表现 | 涉及 |
|---|---|---|
| 一个事实有两个定义 | 写出方与读取方各自定义描述符的形式；没有规范条款，也没有往返测试 | #960 |
| 一条规则带着例外 | 约束改写了请求却没有进入合并；谓词之前有按系统名写的分支；规则只覆盖了它所述对象的一部分写法 | #956、#957、#931、#954 |
| 引擎的事实没有通道 | 只有引擎知道的事实不能进入动作，于是规则在事后猜测 | #959 |
| 工具的逻辑进入引擎 | 把会随工具变化的词汇放进引擎 | #955 |
| 不可观察被当作可以等待 | 一种不会改变的回答被等待后拒绝；拒绝不写出对象与出路 | #952、#953、#958 |

## 3. 描述符的 `mcpp` 字段：两种形式与发布的写出（#960）

### 3.1 现状

- **写出方。** `emit_xpkg`（`src/pm/publisher.cppm`）写出 `mcpp = { schema, language, import_std, modules, deps, [runtime], manifest = "mcpp.toml" }`。
- **读取方。** 六处按字段的种类分支：`src/build/prepare/graph_load.cpp` 的布局核对（795）、安装前的子依赖（916）、读清单（1298）、
  补丁根（1456），`src/scaffold/create.cppm`（91），`src/cli/cmd_xpkg.cppm`（196）。表形式一律交给 `synthesize_from_xpkg_lua`，
  它要求 `sources`；`manifest` 不在 `kKnownXpkgKeys`（`modules/manifest/src/xpkg.cppm`）中。
- **结果。** `mcpp publish` 与 `mcpp emit xpkg` 写出的描述符不能被解析、不能作为依赖、不能作为模板包（1.1 节）。#960 报告的是其中第三个。
- **未被发现的原因。** mcpp-index 中带 `mcpp` 字段的描述符 74 个为字符串形式、194 个为带 `sources` 的表形式，没有一个带 `manifest` 键；
  `tests/unit/test_xpkg_emit.cpp` 断言写出方输出 `manifest = "mcpp.toml"`；e2e 772 以 `path` 依赖消费发布的归档，不经描述符。
- **规范。** `mcpp` 字段的形式只在 mcpp-index 的文档中以 Form A、Form B 描述，mcpp 的规范没有条款。

### 3.2 方案

1. **条款。** SPEC-001 增加一节“描述符的 `mcpp` 字段”：
   - **指针形式** `mcpp = "<glob>"`：载荷带有清单。glob 相对版本目录，恰好匹配一个 `mcpp.toml`，它所在的目录是包根。字段缺省时依次
     尝试 `mcpp.toml` 与 `*/mcpp.toml`。
   - **内联形式** `mcpp = { ... }`：载荷不带清单，该表即清单；键的集合是 `kKnownXpkgKeys`，`sources` 必须给出。
   - 表中指向载荷内清单的写法不是第三种形式，`manifest` 键不存在。Form A、Form B 作为两种形式的别名保留。
2. **写出方。** 发布的归档就是包的源码树，其顶层目录内有清单（工作区成员为规范化后的清单），因此 `emit_xpkg` 写出
   `mcpp = "*/mcpp.toml"`。`xpm.<platform>.deps`（安装期的边）不变。`modules`、`deps` 与 `runtime.requirements` 不再写入描述符
   （决定 D6，依据见 15.6）。
3. **一个读取函数。** `descriptor_manifest(lua, 版本目录, 名字, 版本, 平台)` 返回清单、包根与形式，取代上述六处分支。
   `mcpp new --template` 由包根查找 `templates/`，拒绝的条件是没有该目录，消息写出查找的目录，不再以形式为由拒绝。
4. **往返测试。** 单元测试：`emit_xpkg` 的输出经 `mcpp xpkg parse` 的同一函数读取成功。e2e：发布一个带模板的成员，以本地索引
   消费它，构建并运行；`mcpp new --template <包>:<模板>` 创建工程并构建。`test_xpkg_emit.cpp` 中对 `manifest` 键的断言改为对指针形式的断言。

### 3.3 兼容

指针形式是已发布的每个 mcpp 都读取的形式（索引中 74 个条目）。此前由 `mcpp publish` 生成的描述符没有进入过索引，
不需要迁移。文档：docs/11 与 docs/zh/11 写明 `mcpp publish` 写出的字段。

## 4. 版本解析：版本组的约束与 build-only 包的条件表（#956）

### 4.1 原因

报告把原因写为“范围请求与精确请求分别解析”。实测表明目标图的范围请求已解析为组中版本，失败只发生在 `mcpplibs.os`
经构建依赖进入图时（1.1 节）。原因是两条，彼此独立：

- **F1 版本组的精确约束不进入合并。** `step4b_pin_to_platform_group`（`src/build/prepare/platform.cpp:1026`）把请求的版本改写为
  `=<组中版本>`，并跳过 build-only 的请求（SPEC-013 §7.5：只为本机构建的包不受约束）。同一个包的第二个请求到达时，
  `step4b_identity_version_merge`（`src/build/prepare/graph.cpp:697`）合并的是双方**书写时**的约束（`item.originalConstraint`），
  改写后的精确约束不在其中。于是 build-only 的边先取得区间内最新的 0.23.5，平台的层随后到达，合并认为已有版本满足双方书写的约束而保留它
  （实测没有 `Merged` 一行），遍历之后的断言再把它拒绝。通用的合并规则已经存在，版本组绕过了它。
- **F2 build-only 包的条件表按目标求值。** 交叉到 `x86_64-macos-musl` 时，一个只经构建依赖到达的包读取的是
  `[target.macos.dependencies]`，而它为构建机器构建（SPEC-013 的“宿主图”）。主遍因此解析了任何构建都不使用的包，
  而构建程序实际链接的 openkal-linux 不在 `mcpp.lock` 中（1.1 节第四行）：交叉构建时锁没有记录宿主一侧的构建内容。

F1 是 #956 的直接原因；F2 使它在宿主与目标不是同一系统时也出现，并且是锁的完整性缺口。任何平台在组中列出、
又被某个构建期的库以范围请求的成员都会遇到；插件全部依赖 `mcpplibs.os`，所以带插件的工程在 hosted 行上都在其中。

### 4.2 方案

1. **R1 版本组的约束进入合并。** 版本组对一个成员的精确约束是该请求的约束，随请求进入解析表的记录与此后的每次合并。
   同一个包的全部请求由一个它们都容许的版本满足：`>=0.22.0, <0.24.0` 与组的 `=0.23.4` 给出 0.23.4（输出一行 `Merged`），
   与请求到达的先后无关。没有这样的版本时拒绝，消息列出每个请求者与其约束（`ResolvedRecord::constraintsBy` 已有记录，
   当前只写出第一个）。只为本机构建、始终没有进入目标图的包不受约束，SPEC-013 §7.5 的条文不变；遍历之后的检查保留为断言。
2. **R2 条件表的求值行。** 包为哪一行构建，它的 `[target.<selector>.*]` 就按哪一行选择，依赖表在内。只经构建依赖到达的包按宿主行求值，
   主遍与宿主图自身的准备给出同一组请求，`mcpp.lock` 记录构建程序实际链接的包。写入 SPEC-004 的解析轴一节与 SPEC-013 §2 的“宿主图”定义。

v1 的做法（对 build-only 的请求也提前改写为组中版本）撤回：它让目标平台的版本组约束了只为本机构建的包，与 §7.5 的条文相反，
而 R1 用已有的合并规则得到同样的结果。

### 4.3 验证与生态规则

- e2e（本地索引，一个带 `[platform.versions] m = "1.0.0"` 的平台夹具，索引列出 `m` 的 1.0.0 与 1.0.1）：build-only 的库以 `^1.0`
  请求 `m`，目标图也使用 `m`，结果为 1.0.0 并输出 `Merged`，两种到达顺序各一例；build-only 的库以 `=1.0.1` 请求时拒绝并列出两个请求者；
  build-only 且目标图不使用 `m` 时为 1.0.1；build-only 的包带两个系统的条件依赖表时，交叉构建读取宿主的那一个，锁记录它。
- 复现脚本的 956 一项不再复现。
- “成员的补丁不列入索引”这一临时规则随修正撤销（见 14.3）。
- R2 改变主遍为 build-only 包解析出的包：交叉构建时 `mcpp.lock` 记录的是宿主一侧的成员。升级后的处理见 17.1 的 U5。

## 5. 执行可达性的单一谓词（#957）

`unreachable_execution`（`src/build/execute.cppm:1525`）的注释写明“一个谓词适用于每一行”，而谓词之前有一个分支：
宿主不是 macOS 且三元组属于 Apple 时一律拒绝，不看行是否声明了运行器。其后的通用谓词（行的执行系统不是本机系统且没有声明运行器时拒绝）
已经给出同样的答案，并在有运行器时放行。该分支在引擎中点名了一个系统（AGENTS.md 第 2 节）。

**方案。** 删除该分支。Apple 的行与其余的行一样由通用谓词判定：运行器的 `hosts` 含本机时可达，否则拒绝，消息由通用分支给出
（执行系统取自行的数据，已含 `run_under` 与运行器两条出路）；`other_hosts_note` 照常附加。

**使这一类不再进入。** `check_system_names.py` 的词表含宿主谓词（`is_macos` 等），不含三元组的系统谓词，所以该分支的 `t->is_apple()`
不被计数。词表增加三元组的系统谓词（`is_apple`、`is_ios`、`is_ios_simulator` 与同类），基线取当前计数；本项删除的分支使
`is_macos` 与 `is_apple` 的基线各降一。

**验证。** 单元测试：一行 Apple 三元组、一个 `hosts` 含 Linux 的运行器，谓词放行；无运行器时拒绝且消息写出执行系统。
e2e：平台夹具定义一行 Apple 三元组并声明一个回显参数的运行器，`mcpp run` 在 Linux 上调用它。docs/04（`run_under` 一节，
“Apple artifact on a host that is not macOS, with no `run_under`, is refused”）按新行为改写（中英文）。PureDarwin 的运行器包是实验性包，
不属于本方案。

## 6. 链接标志点名的文件是链接的输入（#931）

### 6.1 现状

`src/build/flags.cppm`（`ldFileInputs`）已有规则：链接标志中以绝对路径点名的现有文件，是携带该标志的每个链接的隐式输入。
它识别两种写法：整个词是路径；`@<文件>` 及该文件列出的路径。选项的值不在其中（`--js-library=<文件>`、
`-Wl,--version-script=<文件>`、`-Wl,-force_load,<文件>`、`/DEF:<文件>`），实测见 1.1 节。构建程序重新运行后给出相同的标志，
链接命令不变，于是链接被视为最新。

这是同一类问题的第三次：2026.10.31.1 补了整词的绝对路径（mcpp#869），2026.11.2.2 补了响应文件（mcpp#883），本次是选项的值。
三次的共同点是链接的输入由引擎从标志中推断。编译边没有这类问题，因为编译器自己报告它读了什么（依赖文件）。

### 6.2 方案

链接边的输入与编译边一样由两部分组成：规划时已知的，与工具自己报告的。

**B 链接器的报告。** 链接器能以 make 格式写出它读取的文件时，链接边带上该依赖文件（ninja 的 `depfile` 与 `deps = gcc`）。
GNU ld（2.35 起）与 ld.lld 以 `--dependency-file=<文件>` 提供，实测见 1.1 节；它覆盖标志推断不可能覆盖的输入：
按 `-l` 搜索找到的库、链接脚本中 `INPUT` 引入的文件。哪个链接器提供、以哪个选项，是链接模型
（`modules/toolchain-model/src/linkmodel.cppm`）中链接器的一个事实，引擎的规则只读取它。
ld64 的 `-dependency_info` 是另一种格式，wasm-ld、lld-link 与 link.exe 在帮助中没有对应的选项（LLVM 23.1.3），这些链接器只有 A。

**A 规划时已知的。** 现有规则不变，补全“点名”的位置。它覆盖链接器不读取而由驱动读取的文件（emcc 的 `--js-library`、`--pre-js`），
以及不提供报告的链接器。对每个链接词取候选：整个词；`=` 之后的部分；以 `,` 分隔的每一段；MSVC 链接方言下以 `/` 开头的词中
第一个 `:` 之后的部分。候选是绝对路径，且指向一个现有的普通文件或本次规划中某个动作声明的输出时，它是隐式输入。
目录（`-L`、`-rpath`、`--sysroot`）不是普通文件，不受影响；`-fuse-ld=<绝对路径>` 这类指向程序的值成为输入，程序变化时重新链接，符合规则的本意。
多认一个文件的代价是该文件变化时多一次链接，少认一个的代价是陈旧的产物，所以候选取宽。

不增加接口。报告的两个候选都不采纳：`mcpp::link_input` 一名已由 SPEC-013 的平台陈述使用，含义是“链接进每个映像的文件”；
把构建程序的 `rerun_if_changed` 文件计为链接输入，会使构建程序的任何输入变化都重新链接它的全部消费者。

### 6.3 文档与验证

docs/30 中“写在 `[build].ldflags` 里的预构建对象不被跟踪，修改后报告 `ninja: no work to do`”一段与 2026.10.31.1 起的实现不符，
随本项改写为两条规则及其边界：只有 A 的链接器上，相对路径与规划时尚不存在、也不是任何动作输出的文件不是输入。
e2e：三种写法（整词、`@file`、选项的值）各改写一次文件，程序重新链接，`mcpp:link-script` 的脚本一并断言；
在提供报告的链接器上，改写一个只经 `-L`、`-l` 找到的静态库，程序重新链接；wasm32-emscripten 上改写 `--js-library` 的文件，程序重新链接。

## 7. 条件行的来源（#954）

`inherit_workspace_layer_rows`（`src/project.cppm`）把 `[workspace.target.<sel>]` 的行插入每个成员的条件行之前，行不带来源。
警告的条件（`src/build/prepare/features.cpp:514`）是“不是根包且声明了 abi”，继承的行因此被当作成员自己的声明。

**方案。** 条件行携带来源（陈述它的清单与层：成员、工作区层），与平台字段的 `origin` 同一种记录。警告只对来源为该包自身清单的
`abi` 行发出。工作区层的行是根的陈述，不产生警告。成员自己写的表在它作为依赖到达时照常警告。
来源同时进入 `mcpp self env` 与机器输出中该值的出处，与其余带来源的值一致。

**验证。** e2e（`tests/e2e/workspace/`）：虚拟根陈述 `abi`，两个成员，零条警告；成员自带 `abi` 表并被另一成员依赖，一条警告，点名该成员。
docs/07 写明虚拟根在 `[workspace.target.<selector>.abi]` 陈述 abi。

## 8. 动作：引擎提供事实，步骤的逻辑属于插件（#959、#955）

### 8.1 现状

动作的命令是一个 argv，没有 shell；`${mcpp.*}` 是封闭的词汇（八个记号），只在 argv、输入、输出、环境与工作目录中展开。
引擎自身提供一条文件命令 `${mcpp.self} stage`。mcpp.plugins 0.25.0 的 `tools-steps` 以一组可移植操作描述多步动作，
后端是 `cmake -P`；0.26.0 在一天之后为 `glob` 增加了 `exclude`，此前已有 #955 的表中没有的 `append` 与 `copy_tree` 的 `if_exists`。

宿主工具的通道实测如下（1.1 节末行）：`[build-dependencies]` 的边接受 `tools = [...]`（要同时导入其库须写 `host-module = true`），
程序为本机构建并进入全机的工具存储；路径只到达**写出该边的那个包**的构建程序。插件的库在另一个包的构建程序中运行时，
`mcpp::dep_bin` 回答空串。插件因此不能携带自己的程序，这是它们改用 `cmake -P`、shell 脚本与 JDK 的原因。

### 8.2 `${mcpp.objects:<name>}`（采纳，D2）

链接单元由哪些对象组成只有引擎知道；规则在事后遍历 `obj/` 并按路径排除，是在猜测引擎的事实。可对照的做法是 CMake 的
`$<TARGET_OBJECTS:tgt>`。

| 项 | 规定 |
|---|---|
| 名字的解析 | 与 `${mcpp.target_file:<name>}` 相同，未知与有歧义的名字同样拒绝 |
| 展开为 | 构建目录中一个清单文件的绝对路径（正斜杠）。引擎在写出规划时写它，字节不变时不写 |
| 内容 | 该单元的链接边作为显式输入的对象文件（静态并入的依赖的对象与标准库模块的对象在内，库与框架不在内），按链接顺序，每行一个绝对路径，UTF-8，`\n` 结尾 |
| 依赖 | 清单与其中每个对象是该动作的隐式输入 |
| 角色 | `artifact` 与 `check`。`source`、`prepare`、`object` 中使用时拒绝并写出角色：它们先于或进入清单所依据的编译与链接 |
| 第二种拼写 | `${mcpp.objects_rsp:<name>}`：同一清单按响应文件的引号规则写出，供以 `@file` 读取的工具（`ar`、`llvm-ar`、`lib.exe`）。按行读取的工具（Apple `libtool -filelist`）用前一种。两种格式不能合一：构建目录的路径含空格时（Windows 的用户目录常见），按行的清单不能被 `@file` 正确切分，带引号的清单不能被按行读取 |
| 协议 | 协议 20。`import mcpp;` 提供 `mcpp::objects_of(name)` 与 `mcpp::objects_rsp_of(name)` 返回记号文本，使旧引擎上的构建程序在编译时失败，而不是把未展开的记号交给工具 |

### 8.3 `${mcpp.self} write`（采纳，D2）与这一族命令的判据

`${mcpp.self} write --output <file> [--append <file>]... -- <line>...` 写出各行与每个 `--append` 文件的内容，写在别处后改名，
字节不变时不动输出。`--append` 的文件由动作声明为输入。

引擎自身的命令以一条判据为界，而不是逐个列举：**一个输出，内容完全由声明的输入与 argv 决定，重复执行结果相同**。
`stage`（放置一个文件）与 `write`（写出规划已知的文本）满足；删除、建目录、通配、按顺序运行多个程序不满足，它们属于步骤程序（8.4）。
判据写入 SPEC-007，此后对这一族的增补以它裁决。

### 8.4 多步动作的运行器归插件（#955 不按原样采纳，D1）

#955 请求引擎解释一组操作。结论是运行器为插件包自己的宿主程序，依据见 15.1。引擎欠的是 8.1 实测出的那条通道：
**插件携带它自己的程序**。方案是让 `tools` 这个键出现在特性上，含义不变：

```toml
# mcpp.plugins 的清单
[features.tools-steps]
sources = ["tools/steps.cppm"]
tools   = ["steps"]          # 本包的一个 kind = "bin" 目标；特性激活时为构建机器构建
```

| 项 | 规定 |
|---|---|
| 含义 | 一条边激活带 `tools` 的特性，效果等同于该边写了 `tools = ["steps"]`：程序为本机构建，进入全机的工具存储（键为源码、宿主工具链、特性与依赖闭包） |
| 可见范围 | 图中链接了该包的宿主模块且该特性激活的**每个**构建程序，都得到 `MCPP_DEP_<PKG>_BIN_<TOOL>`；经框架到达的应用不需要在自己的清单中写出工具名 |
| 未声明的工具 | `mcpp::dep_bin` 对没有任何边或特性声明的工具不再回答空串：构建程序以 `build-program/undeclared-tool` 报告，写出包、工具名与应当写的那一行 |
| 动作 | 工具是使用它的动作的输入，字节变化时动作重新运行（docs/30 已有的规则） |
| 位置 | 只在 `[features.<name>]`。没有特性的包以 `default` 所含的特性陈述。`tools` 一个键、一个含义、两个位置（边与特性），符合 AGENTS.md 第 3 节“一个概念一个拼写” |

写入 SPEC-007 与 docs/30、docs/31。**插件一侧（mcpp-plugins，不属于引擎的改动）：** `tools-steps` 的后端改为 `steps <步骤文件>`；
`dist-apple` 的 `#!/bin/sh` 动作改用步骤；成员表中 `"xim:cmake"` 只留在以 CMake 为工具的成员上。

### 8.5 验证

e2e：一个动作以 `${mcpp.objects:app}` 归档程序的对象，修改一个源文件后归档重新生成，未修改时不运行；构建目录的路径含空格时
`objects_rsp` 被 `llvm-ar @file` 正确读取；`${mcpp.self} write` 的输出含展开后的绝对路径，重复构建不改写文件；
复现脚本的 955 一项在特性声明 `tools` 后两处都得到路径，Windows 宿主在内；未声明的工具得到诊断。

## 9. 进程启动的大小界限（#958）

### 9.1 现状

- openkal-linux `src/process.cpp:33` 与 openkal-macos `src/process.cpp:35`：`kMaxEntries = 512`，参数向量与环境各自超过即返回
  `kal_err_no_memory`。两个向量都按实测总量分配，该常量不保护任何定长缓冲。openkal-windows 的 `process.cpp` 没有该常量。
- openkal 规范 §7.6 规定实现“原样传递向量”，没有授权条数的界限。内核报告的 `E2BIG` 在 openkal-linux 的转换表中落入默认分支
  `kal_err_io`。
- **影响面。** 界限同时约束参数向量：`[build] defines` 写 520 项的工程在终端中即不能编译（1.1 节）。依赖多的工程的包含目录与宏定义
  合计达到这个数量是正常情况，所以它不限于报告中的 Xcode 环境（546 个变量）。消息为内存不足，不指向原因。

### 9.2 方案

1. **openkal 规范。** §7.6 增加：实现不得对向量与环境的条数或总量设置低于其环境的界限；环境因大小拒绝的启动报告为
   `kal_err_no_space`。一致性套件（`tests/cts`）增加三例：2,000 个参数的启动成功；2,000 个环境变量、约 200 KiB 的启动成功；
   超过环境界限的启动报告 `kal_err_no_space`（Linux 以单个超过 128 KiB 的字符串构造，macOS 以总量超过 `ARG_MAX` 构造）。
2. **实现。** openkal-linux 与 openkal-macos 删除 `kMaxEntries`，`E2BIG` 转换为 `kal_err_no_space`；openkal-windows 把命令行与环境块的
   长度拒绝转换为同一值；其余实现以套件核对。
3. **mcpplibs.os。** 启动失败的错误带上两个向量的条数与字节数。
4. **mcpp。** 启动失败的消息写出它们：`cannot start '<程序>': the request is larger than the system admits (N arguments, A bytes; M variables, E bytes)`，
   原因标识 `spawn-too-large`（docs/50）。e2e：复现脚本的 958 一项构建成功。

mcpp 是否应当为编译器裁剪环境是另一个问题（“默认封闭”一条），本文不处理。

## 10. 编译运行状态：观察的回答与恢复（#952，#953 的两项）

### 10.1 现状

- **单元与引用。** Linux 上一个单元是一个进程组，引用为 `L2;<组>;<出生>;<boot_id>;<pid 命名空间>`
  （openkal-linux `src/process.cpp:2025` 起）。引用的来源与调用者不同时，`kal_process_job_open` 返回 `kal_err_not_supported`，
  `kal_process_job_observe` 回答 `UNKNOWN`；组号现在指向另一个出生时刻的进程时也回答 `UNKNOWN`。
- **引擎。** `observed()`（`src/build/schedule/compiler_transaction.cppm:305`）把打开失败与 `UNKNOWN` 合并为 `unknown`；
  `recover_generation`（623）对未决的尝试等待 5 s 后以 `previous compiler unit is occupied or unknown` 拒绝。
  调用它之前，`RunScope::begin`（`detach_codegen.cppm:655`）已经取得旧一代的 `owner.lock` 并确认各 actor 的锁空闲；
  这些锁在 Linux 上是打开文件描述的锁（`F_OFD_SETLK`），属于文件系统而不属于进程空间。
- **状态的位置。** `<工作目录>/.mcpp/compiler-runs/<输出目录的散列>/`，有意置于 `target/` 之外，使锁不随清理消失；
  `mcpp clean` 因此不触及它。
- **实测。** 在一个 pid 命名空间中被结束的构建，从另一个命名空间永远不能继续，`mcpp clean` 之后仍然如此；连续两个容器作业的情形
  四次均拒绝（1.1 节）。容器与沙箱每次启动都是新的命名空间，CI 的容器作业复用工作目录、开发容器重建、代理的沙箱会话都在其中。
- **命名空间的名字不是它的身份。** 引用中的进程空间取自 `/proc/self/ns/pid` 的链接文本（`pid:[<编号>]`），而内核把结束的命名空间的编号
  给后来的命名空间（实测：四个不同的命名空间同名）。名字相同时实现认为是同一来源，并按该编号下的进程组回答，
  回答的是另一个空间中无关的进程。
  #952 的现场（进程全部不存在而失败持续一天）与此相符；是否为同一条路径没有确立，首次中断的原因在报告中未知。
- **准入的拒绝。** 所有者对六种条件都回答 `REFUSED`（`serve()`，485–513），控制方把任何拒绝视为最终结果并输出
  `compiler-run owner refused unit admission`。
- **无声的返回。** `run_capped`（`detach_codegen.cppm:1158`）中 `owned_unit::create()` 失败、`admitted` 记录写入失败等路径返回 1 或 2 而不输出。
  Termux 应用沙箱中 `__compiler-cap` 无消息失败与此一致；怀疑的原因是读取 `boot_id` 被拒绝，使单元不能声明，未在沙箱中测量。
  同一函数已有不声明单元、只受内核许可约束的分支（所有者不受管理时）；#953 的探针测得在一次构建之外直接调用
  `__compiler-cap` 在该沙箱中成功。

### 10.2 原因

观察有三种事实：单元为空、单元被占用、从此处不可能观察。模型只有“空”与“未知”两种出路，而“不可能观察”不会随等待改变。
另有两种情形当前回答未知，而它们可以证明为空；进程空间的标识不精确，使“是否同一来源”本身可能答错。
能否声明单元是环境的性质，当前在每次编译失败时才被发现。

### 10.3 方案

**A. openkal 规范（可观察单元一节）与各实现。**

| 情形 | 回答 | 依据 |
|---|---|---|
| 引用产生于本机的上一次启动 | `EMPTY` | 上一次启动的进程都已结束 |
| 标识单元的进程号现在属于另一个出生时刻的进程 | `EMPTY` | POSIX：存在以某进程号为组号的进程组时，该进程号不被重新分配 |
| 引用产生于同一次启动的另一个进程空间 | `kal_process_job_open` 返回 `kal_err_not_supported`（现状），规范写明这是对该调用者不变的回答 | 调用者无从枚举另一空间的进程 |
| 进程空间的标识 | 规范：引用**必须**精确标识其进程空间，实现**不得**以另一空间的进程回答。openkal-linux 的引用在命名空间的编号之外记入该空间 1 号进程的出生时刻（格式 `L3`；`L2` 的引用按不可观察处理） | 编号会被复用（实测）；同一次启动内编号与 1 号进程的出生时刻不会同时相同 |
| 能否声明单元 | `KAL_PROCESS_PROP_JOB_OBSERVE` 只在实现能够产生引用的环境中声明（启动标识、进程空间与出生时刻均可读） | 条款 6.1：能力的缺失是使用者得知的事实 |
| 其余不能判定的情形 | `UNKNOWN`，含义限定为暂时 | — |

**B. mcpplibs.os。** `unit_observer::open` 的错误区分“不可观察”（`not_supported`）与其余失败；提供对 `KAL_PROCESS_PROP_JOB_OBSERVE` 的查询。

**C. 引擎的恢复（D3）。** 未退役的尝试有三种结果：

- 空：恢复，与现状相同。
- 被占用或暂时未知：在界限内等待，之后拒绝。
- 不可观察：不等待。此时旧一代的所有者锁与全部 actor 锁已经空闲，这是跨进程空间仍然成立的证据：
  该代的控制方、辅助进程与状态写入者在任何共享此目录的进程空间中都已结束。该尝试按被放弃的尝试处理，未完成的输出走同一条作废路径，
  并经 `diag::degraded("compiler-run/unobservable")` 报告一次，写出代的目录与影响：在那个进程空间中比其控制方活得更久的编译器后代不会被发现。
  其中任一把锁被持有时照常拒绝，消息写明另一个进程空间中的 mcpp 正在构建该配置。

残留的情形是：另一个仍在运行的进程空间中，控制方被强行结束而编译器后代仍在写同一个输出。当次构建中该文件可能有两个写入者；
此后的后果有界：迟到的写入使输出的身份与退役证书不符，下一次构建按已有的证书检查作废并重编该单元（依据 `cached_result` 的实现）。

**D. 清理。** `mcpp clean`（含 `--stale`、`--older-than`）在移除一个配置的输出目录时，在构建所用的同一把闸锁之下退役该配置的各代
（`run-*`），锁文件保留；所有者或 actor 的锁被持有时该配置不清理，消息写出正在进行的构建。输出已被移除，旧一代没有可保护的对象，
退役不需要观察。

**E. 拒绝的消息。** 写出代的目录、未决尝试的个数、每种状态的个数与出路：

```
error: 3 compiler units of an interrupted build of this configuration may still be running (2 occupied, 1 unknown)
       state: <工作目录>/.mcpp/compiler-runs/<散列>/run-<…>
       When no compiler of this configuration is running: mcpp clean, then build again.
```

原因标识 `compiler-run-occupied`。

**F. 准入。** 所有者的回答带上条件：`REFUSED <标识>`，标识取自 `outside-generation`、`record-unreadable`、`actor-outside`、
`actor-not-held`、`controller-ended`、`unit-unobservable`、`owner-stopping`；控制方把它写进消息。`record-unreadable`
在启动宽限内重试，与未得到回答的登记相同；其余为最终结果。所有者与控制方是同一次构建中的同一个程序，没有版本间的兼容问题。

**G. 返回路径。** 引擎内部的辅助命令（`__compiler-cap`、`__action`、`stage`、`write`）以非零状态结束时必有一行写出步骤与原因；
130（被取消）除外。由事务套件的故障矩阵断言：每个注入的故障对应的 stderr 非空且含该步骤的名字。

**H. 单元不能声明的环境（D4）。** 一次构建在开始时查询该性质一次。环境不声明它时，整次构建的编译走已有的不声明单元的分支，
经 `diag::degraded("compiler-run/no-unit")` 报告一次，影响同 C；声明了而 `owned_unit::create()` 失败是错误，拒绝并写出原因。
这样行为由环境的性质决定，不由某一次调用的失败决定。Termux 的原因在 G 落地后由 `ci-fresh-install` 的输出直接给出；
是否确为 `boot_id` 在此之前不下结论，方案不依赖它。

### 10.4 两个不采纳的做法

- **#952 的第 1 项**（控制方与单元的进程都不存在时视为已放弃）：组长不存在不能证明没有仍在写入的后代，这是 2026-11-06 的记录中明确拒绝的推断。
  A 给出了可以证明的两种情形，C 给出了不可观察时的规定行为，二者覆盖该请求的现场。
- **以继承的文件锁作为单元的见证**（辅助进程持有一把锁并让编译器的进程树继承其描述，锁空闲即单元为空，与进程空间、启动无关）：
  它在任何命名空间都可判定，但编译器启动的常驻进程会继承该描述并一直持有（`launcher` 为 sccache 时的服务进程、Windows 的 `mspdbsrv`），
  单元永远显示为被占用；进程组的做法在这一点上没有问题。

### 10.5 验证

- openkal 的套件：上一次启动的引用（以改写引用中的启动标识构造）回答 `EMPTY`；另一个进程空间的引用，`open` 返回 `not_supported`；
  与当前空间同名而 1 号进程出生时刻不同的引用，`open` 返回 `not_supported`；不能产生引用的环境不声明该性质。
- e2e（Linux，要求可创建 pid 命名空间，否则 `SKIP`）：复现脚本的 952 与 952s 两项改为断言：继续的构建成功并输出一次 `degraded`；
  旧一代的 actor 锁被持有时拒绝；`mcpp clean` 之后 `.mcpp/compiler-runs/<散列>/` 下没有 `run-*`。
- 事务套件：G 的故障矩阵；F 的每种条件各一例；H 以注入 `not_supported` 构造。

### 10.6 产物的事务化发布（N1）

10.3 的 A 至 H 修正的是观察的模型。需要观察的原因在更下面一层：**编译器直接写已发布的路径**。对象以 `-o $out` 写出；
GCC 的 BMI 由编译器自己写 `<名>.gcm~` 并改名到位，clang 的 BMI 直接写到最终路径（`detach_codegen.cppm` 开头的记录）。
GCC 的策略又有意让代码生成在 ninja 的边结束之后继续。因此一个比控制方活得更久的编译器能够改写已发布的产物，
“被占用则拒绝”与 10.3 C 的残留情形都由此而来。

**做法。** 编译器只写该次尝试私有的路径，发布由引擎的辅助进程以改名完成：BMI 在它完整时，对象、依赖文件与状态在编译器结束时。
残留的编译器只能写它自己的私有文件。恢复即丢弃未发布的尝试，不需要以观察保护输出；单元只用于取消时结束进程与并发上限的记账，
在那里答错的后果是多占一个并发名额。

**已有的基础。** 每个单元的 BMI 路径已由模块映射给出（`ModuleScope`，`src/build/plan.cppm:399`：GCC 读 `-fmodule-mapper=`，
clang 与 MSVC 读参数文件）；辅助进程持有编译器的 argv；对象截断已在执行器中把旧对象改名保留再比较。

**前提，在该检查点内对每个编译器测量。**

| 前提 | 内容 |
|---|---|
| P1 | GCC 16.1 以该次尝试的映射把自己的 BMI 写到私有路径，辅助进程发布后导入者读取；mcpp 自身的构建与测试通过，冷构建的总时间与当前之差在重复测量的波动之内 |
| P2 | clang 的 `-fmodule-output=` 与 `-o`、MSVC 的 `/ifcOutput` 与 `/Fo` 指向私有路径，结果相同 |
| P3 | 带着输出路径的附属产物逐个核对：覆盖率记录、分离的调试信息、PDB、时间跟踪。列出 mcpp 实际产生的那些，各自或随对象一同发布，或其内嵌的路径以编译器的映射选项写为最终路径 |

**前提不成立的编译器**保持就地写入并按 10.3 C 处理；“产物可重定向”是工具链模型中编译器的一个事实，引擎的规则只读取它。
**成立的编译器**上，10.3 C 的报告与残留情形、E 的拒绝不再出现；D、F、G、H 仍然需要。

## 11. #953 中的两项

### 11.1 同一输出路径的两种配置（D5）

一个配置的构建目录由它的谱系命名（编译器家族、目标、标准库、C++ 标准、旗标、基座），特性不在其中。docs/07 规定：
一次命令内，多个成员共用的包按该次选择请求的特性的并集编译一次；并且写明测试的规划会因开发依赖改变一个包的特性。
因此同一个目录中，同一个对象路径在不同的命令下对应不同的命令行：

| 触发 | 例 |
|---|---|
| 构建与测试交替 | 开发依赖为某个共用的包多激活一个特性：`mcpp test` 之后的 `mcpp build` 把它编回去 |
| 选择交替 | `-p X`、`-p Y` 与 `--workspace` 对同一个包给出不同的并集 |

31 个成员的工作区上测得两个成员之间 43 条这样的边（2026-11-17 记录 10.6 节）。产物是正确的（ninja 按命令行重建），重复的是工作，
并且经模块的 BMI 传到导入者。

**方案。** 一个包实例的对象目录由它的配置命名：`obj/<包>@<摘要>/`。摘要覆盖决定其命令的因素：该包激活的特性与宏、
作为根的成员对它的声明，以及它所依赖的各包的摘要（导入者的命令含被导入包的 BMI 路径，所以摘要必须传递）。
摘要与谱系一样只含配置，不含版本与编译器的构建号：升级不改变路径。同一模块名的两个实例的 BMI 由已有的模块映射区分
（每个单元的映射给出它所见的 BMI 路径，GCC 的映射不回落到按名字的默认位置），不需要新的机制。两种配置并存，交替的命令不再重新编译；
`mcpp clean --stale` 按构建记录回收不再被引用的实例目录，`mcpp clean --report` 按实例列出体积。

**验收的测量。** 实施前在同一工作区上记录 `mcpp build` 与 `mcpp test` 交替三轮、以及 `-p X` 与 `-p Y` 交替三轮时重新运行的边数，
实施后同样测量；预期第二轮起为零。磁盘的增量以 `clean --report` 给出。

### 11.2 Windows 的 LLVM 载荷不读压缩的调试段

Windows 的 LLVM 载荷中的 lld 构建时未带 zlib，不能读取带 `ELFCOMPRESS_ZLIB` 段的对象；FreeBSD 基座以解压其链接输入绕过（修订 2），
用户自己的对象仍不可读。mcpp 自身的 dev 构建在 Linux 上以 `-gz=zlib` 编译（实测的命令行），所以这类对象不是少数情形。
规则：一个工具链载荷在每个宿主上读取同样的输入。xim-pkgindex 的 LLVM 载荷在 Windows 上以 zlib 与 zstd 构建 lld，
载荷的 CI 在每个宿主上链接一个带 zlib 压缩段与一个带 zstd 压缩段的对象。之后 e2e 1116 在 Windows 宿主上不再跳过，
FreeBSD 基座包恢复上游的字节（修订 3，撤销修订 2 对链接输入的解压）。

## 14. 各仓库的改动、拉取请求与检查点

### 14.1 原则

- **每个仓库一个拉取请求。** 拉取请求内的提交是检查点：每个提交自身可构建并通过它引入的测试，提交信息陈述该检查点的内容；
  规范条款、中英文文档与测试随它所属的检查点提交（AGENTS.md 第 1 节）。
- **依赖而不复制。** 下游的拉取请求在上游发布之前以 `git` 依赖指向上游拉取请求的分支，最后一个检查点改为版本依赖。
- **前提在拉取请求内测量。** 只能在真实 runner 上得到的事实（macOS 与 Windows 的单元回答、Termux 的性质、Windows 的 lld）
  由相应拉取请求自身的 CI 测量，结果追加到本文的状态行；不另开探针拉取请求。
- **合并与发布按依赖顺序。** 下表的序号相同的仓库彼此独立。

## 15. 七项决定的结论与依据

每项列出相关的视角、两种做法在该视角下的情况与结论。视角取自：mcpp 的设计规范、openkal 的规范、通用架构、简洁、语义与一致性、
跨平台、稳定与兼容、开发体验、扩展与演进、行业做法。

### 15.1 D1 多步动作的运行器：插件自己的宿主程序

| 视角 | 插件的宿主程序（采纳） | 引擎解释步骤词汇 |
|---|---|---|
| mcpp 规范 | 引擎增加的是机制（特性携带工具），步骤的词汇留在数据与插件中 | 引擎持有一种会随工具变化的词汇，违反“机制在引擎” |
| 扩展与演进 | 词汇随插件的版本演进 | issue 提出后一天词汇已变（`exclude`）；每次变化对应引擎发布、协议号与每个使用者的引擎下界 |
| 简洁 | 一个已有的键多一个位置 | 十余个操作、列表变量、通配的语义各需规范条款 |
| 语义与一致性 | 构建逻辑只有一种语言：宿主上的 C++ 程序 | 引擎内出现第二种带变量与条件的语言 |
| 跨平台 | 标准库与 mcpplibs.os，每个宿主相同；没有 shell | 同样可移植 |
| 开发体验 | 每台机器、每个插件版本与宿主工具链构建一次，进入全机存储；不再安装 `xim:cmake` | 零构建成本 |
| 行业做法 | Bazel 与 Buck 的动作运行在执行配置下构建出的工具；Cargo 的 `build.rs` 是编译出的宿主程序 | CMake 的 `-P` 是这种做法：脚本语言由构建工具自身携带，其词汇随工具的版本冻结 |
| 通用性 | 通道对所有带辅助程序的规则包成立（代码生成、反射、打包） | 只解决步骤 |

结论：引擎解释词汇只在首次构建的几秒上占优，其余视角相反。并且 8.1 的实测表明通道的缺口是插件改用外部工具的原因，
补上它同时消除三种变通（shell 脚本、JDK 上的 Java 程序、`cmake -P`）。

### 15.2 D2 `${mcpp.objects:}` 两种拼写与引擎内的 `write`

| 视角 | 采纳的做法 | 另一种做法 |
|---|---|---|
| mcpp 规范 | 对象清单是引擎的事实，以封闭词汇中的一个记号给出 | 规则遍历 `obj/` 并排除：猜测引擎的事实，增量依赖也不成立 |
| 语义 | `write` 是纯边：一个输出、内容由输入与 argv 决定、可重复，与 `stage` 同类 | 交给步骤程序：规则包为写两行文本要带上运行器，且规划已知的内容被放进一个带副作用的步骤 |
| 稳定与兼容 | 命令族以判据为界，判据写入规范；此后不逐个争论 | 不设判据地增加命令，会逐步回到 15.1 被否掉的做法 |
| 跨平台 | 两种拼写分别对应按行读取与 `@file` 读取；构建目录含空格时二者不可合一 | 单一拼写在含空格的路径上对一类工具失效 |
| 行业做法 | CMake `$<TARGET_OBJECTS:>`、`file(GENERATE)`；Bazel `ctx.actions.write`、`use_param_file` | — |

结论：两个记号与 `write` 都采纳。

### 15.3 D3 不可观察的单元：锁空闲时恢复并报告

| 视角 | 恢复并报告（采纳） | 保持拒绝，只改消息 |
|---|---|---|
| 语义 | “不可观察”是不变的事实，等待它没有意义；按可得的最强证据（锁）决定 | 把不变的回答当作暂时的 |
| 稳定性 | 容器中被中断的构建在下一个容器中继续 | 每次都要手工清理；CI 的容器作业复用工作目录时每次失败（实测） |
| 安全 | 残留情形见 10.3 C：当次构建可能有两个写入者，此后由退役证书发现 | 没有残留情形 |
| mcpp 规范 | 少做经 `diag::degraded()` 报告，写出影响 | 符合，但把通常已经结束的构建当作仍在运行 |
| openkal 规范 | 条款 6.1：能力的缺失是使用者得知的事实，使用者据此行动 | — |
| 行业做法 | Cargo、Bazel、ninja 以文件锁判断上一次构建已结束；mcpp 在可观察时多一层，不可观察时与它们相同 | 没有工具在这种情形下拒绝 |

结论：恢复并报告。以继承的锁作为见证的做法另行评估后否掉（10.4）。它是就地写入之下的规定行为；就地写入本身由 10.6 处理。

### 15.4 D4 单元不能声明的环境：降级并报告

| 视角 | 降级并报告（采纳） | 拒绝 |
|---|---|---|
| 通用性 | mcpp 在应用沙箱一类的环境中可用 | Termux 应用沙箱自 2026.11.7.1 起不能构建 |
| 简洁 | 走 `run_capped` 中已有的分支，不新增路径；由环境的性质在构建开始时决定一次 | — |
| 语义与一致性 | 与 D3 同一条规定：观察能力缺失时按许可与锁运行，并写明 | 两处行为不一致 |
| 安全 | 失去的是对比控制方活得更久的编译器后代的发现，即引入单元之前的行为 | 没有损失，也没有构建 |

结论：降级并报告；依据是环境不声明 `KAL_PROCESS_PROP_JOB_OBSERVE`，声明了而失败照常拒绝。

### 15.5 D5 同一路径的两种配置：配置计入对象目录

| 视角 | 实例目录带配置摘要（采纳） | 全工作区取并集 |
|---|---|---|
| 语义 | 不带测试的构建不被测试的依赖配置；成员单独构建的结果不随无关成员变化 | 为消除“构建与测试交替”必须把开发依赖的特性并入普通构建，发布的库随之改变 |
| 一致性 | 目录已由配置的谱系命名，实例目录用同一条原则 | 版本在工作区内是统一的，特性也统一，这一点一致 |
| 稳定与兼容 | 路径方案变化，升级后一次全量重编译；摘要不含版本，此后升级不变 | 路径不变 |
| 开发体验 | 交替的命令不再重编；磁盘随并存的配置增长 | 不重编；`-p X` 的规划须遍历全部成员的图 |
| 简洁 | 对象路径的每个读取方都要改（规划、编译数据库、清理、报告） | 改动小 |
| 行业做法 | Cargo 的产物按单元的元数据散列并存（含特性与依赖的散列），解析器 v2 停止把开发依赖的特性并入普通构建；Bazel 的输出目录按配置散列 | Cargo 的旧解析器；`cargo-hakari` 以人工的方式逼近它 |

结论：配置计入对象目录。并集的做法在“构建与测试交替”上只能以改变产物为代价，不能采纳。该项的改动面是本方案中最大的；它在本轮实施（17.1 的 U1），验收为 11.1 的测量。

### 15.6 D6 发布的描述符：指针形式，不带摘要

| 视角 | 指针形式（采纳） | 保留 `modules`、`deps` 并让读取方接受第三种形式 |
|---|---|---|
| 语义与一致性 | 清单是依赖与模块的唯一陈述 | 一个事实两处陈述 |
| 正确性 | — | 描述符的 `deps` 在结构上不能携带目标轴的依赖（mcpp-index 的文档以 huxerui 为例：`emit xpkg` 写出空的 `deps`，36 项闭包手工抄入）；它不是清单的忠实摘要 |
| 稳定与兼容 | 已发布的每个 mcpp 都读取 | 需要新引擎才能读取 |
| 读取方 | 引擎之外没有读取者：xlings（`4f5df092`）与 mcpp-index 的工具中均未找到对 `mcpp` 表的读取 | — |
| 生态演进 | 将来若需要不下载即解析，摘要应由索引从已发布的清单生成并带目标轴，而不是由发布方手写三块平台表 | 现在的形状承担不了该用途 |

结论：指针形式。

### 15.7 D7 openkal 的两处条款：规范的次版本

| 视角 | 0.26.0 与家族级联（采纳） | 补丁版本 |
|---|---|---|
| openkal 规范 | 第 8 条：每个实现都必须满足的要求推进次版本；两处条款都是 | 违反第 8 条 |
| 稳定与兼容 | 新版本在 mcpplibs.os 0.4.4 的范围之外，已发布的引擎不受影响 | 落在范围之内；已发布的引擎在 hosted 行上因 4.1 的缺口失败，#830 的情形重演 |
| 代价 | 一次家族级联（版本组中十三个包、平台、mcpplibs.os、索引） | 只发两个实现 |
| 生态演进 | 版本号如实表达“实现须重新符合” | 版本号掩盖了要求的变化 |

结论：次版本。512 的界限若单独看可以作为补丁（§7.6 已要求原样传递），随同一次发布走，不单独发补丁。

### 16.2 第二轮（v2 至 v3）：是否从成因解决

逐节问一句：这一节消除的是成因，还是这一次的表现。

| 节 | v2 的状态 | 判定 | 调整 |
|---|---|---|---|
| 3 | 一个定义、一个读取函数、往返测试 | 成因 | — |
| 4 | 约束进入通用的合并；条件表按构建的行求值 | 成因 | — |
| 5 | 删除特例 | 特例是成因，但同类分支仍可无声进入：现有的系统名检查不计三元组的谓词 | 词表增加三元组的系统谓词 |
| 6 | 补全“点名”的位置 | 表现：这是同一类问题的第三次修补 | 增加规则 B，链接器自己的报告；规则 A 保留给驱动读取的文件与不提供报告的链接器，二者都是长期规则 |
| 7 | 条件行带来源 | 成因 | — |
| 8 | 引擎的事实一个记号；插件携带自己的程序 | 成因 | — |
| 9 | 规范条款与实现 | 成因 | — |
| 10 A | 两种可证明为空的情形 | 不完整：进程空间以名字识别，而名字被复用（实测） | 引用精确标识其进程空间，写入规范；实现记入 1 号进程的出生时刻 |
| 10 H | 调用失败后降级 | 表现：能力的缺失在每次编译失败时才被发现 | 由 `KAL_PROCESS_PROP_JOB_OBSERVE` 在构建开始时决定一次；实现只在能产生引用的环境声明它 |
| 10 C | 不可观察时按锁恢复并报告 | 表现：它规定了就地写入之下的行为，而需要观察的原因是编译器直接写已发布的路径 | 增加 10.6，产物的事务化发布，前提在检查点内测量；列为 N1 |
| 11.1 | 配置计入对象目录 | 成因 | — |
| 11.2 | 载荷带 zlib 与 zstd | 成因；但生态中已有的绕过未撤销 | FreeBSD 基座恢复上游的字节 |
| 12 | 消息与测试 | 成因在各节；超时的证据留存是新增的机制 | — |
| 全文 | — | 没有列出本轮之后应当消失的变通 | 14.3：十一项变通逐项对应章节，作为“是否从成因解决”的验收 |

结合 openkal 规范的复核：版本由第 8 条决定（15.7）；大小的条款是对 §7.6“原样传递”的补全；“不可观察”与“不能声明”都落在条款 6.1
（缺失是使用者得知的事实）之下，前者是 `open` 的不变回答，后者是性质；引用的格式是实现的私有内容，规范只规定它必须精确标识进程空间。
结合 mcpp 规范的复核：每一项的规则在引擎，事实在数据或规范（链接器是否提供报告、特性携带的工具、行的执行系统）；
没有新增按系统名的分支；新增的键（特性上的 `tools`）沿用已有键的名字与含义；每一处少做都经 `diag::degraded()` 或拒绝写出。

复核后仍存在的弱点：11.1 的收益没有在目标工作区上按新的两种交替测量（检查点 9 的验收即为此）；10.6 的三个前提都未测量，
`detach_codegen.cppm` 与 `compiler_transaction.cppm` 只读了与本文相关的部分；10.3 C 的残留情形只有论证没有构造的用例；
第 5、9 节各有一项只读了源码；规则 B 在 macOS 的系统链接器与 Windows 上不可用。

## 20. 编译器的文本与依赖记录（#970）

**来源。** mcpp#970（Windows 11，`msvc@system`，VS 2022 BuildTools，MSVC 14.44.35207，只装中文资源）报告两项：
头文件改动后不重编，`ninja -t deps` 对每个目标文件为 `#deps 0`；编译失败时 mcpp 以
`internal: unhandled exception: [json.exception.type_error.316] invalid UTF-8 byte` 结束。用户决定本轮从成因解决，
不留变通，随 2026.11.19.1 发布。

### 20.1 现状

- **依赖。** 方言的 `ninjaDepsMode = "msvc"` 使 cl.exe 的编译规则带 `/showIncludes` 与 `deps = msvc`，不写
  `msvc_deps_prefix`（`ninja_backend.cppm`）；ninja 以缺省的英文前缀 `Note: including file:` 识别依赖行。
  `build_env_for_cl` 在构建环境中写 `VSLANG=1033`，注释称它保证英文前缀（`msvc.cppm`）。
- **文本。** 自 2026.11.7.1 起每个编译边经执行器 `__compiler-cap` 运行，执行器以 `Streams::inherit` 启动编译器；链接边经
  `link-output`，归档边（lib.exe）由 ninja 直接运行。ninja 把各步骤的字节原样交给 mcpp。mcpp 的文本是 UTF-8：mcpp.exe
  声明 UTF-8 活动代码页，openkal-windows 写控制台时把 UTF-8 转为 UTF-16。失败步骤的输出经 `parse_compiler_diagnostics`
  写入 `result.json` 与事件流，`doc.dump(2)` 在不是 UTF-8 的字节上抛出 `type_error.316`。`execute.cppm` 中测试记录的两处
  写出已使用替换策略。
- **读诊断的另外两处。** `missing_header_in` 以英文句子 `Cannot open include file: '` 识别 C1083；
  `parse_compiler_diagnostics` 的 MSVC 分支要求严重性词后跟代码，不带代码的 `note:` 行落入 GNU 分支，路径记为
  `k.cpp(1)`，行号为 0。

### 20.2 实测

windows-2022，探针 mcpp#971（运行 44508574496），以 `CreateProcessW` 启动 cl.exe 与 link.exe，两个输出流写入一个管道。

| 项 | 结果 |
|---|---|
| 附着于控制台，输出代码页 437、1252、936、65001 | cl 与 link 按该代码页写文本：437 中 `é` 为 0x82、汉字为 `?`；1252 中 `é` 为 0xE9；936 为 GBK；65001 为 UTF-8 |
| `DETACHED_PROCESS`（无控制台） | 两者按系统的 ANSI 代码页写（runner 为 1252） |
| `CREATE_NO_WINDOW` | 得到一个新的控制台，代码页为系统的 OEM 代码页（437） |
| 代码页不能表示的字符 | cl 写出时已成为 `?`：437 下的标识符 `未定义_é` 写作 `???_é` |
| `/sourceDependencies <文件>` | JSON（`"Version": "1.2"`），UTF-8，非 ASCII 字符原样；列出全部头文件，含工具链与 SDK 的；路径整体小写（源目录写作 `Inc Dir\Héader.h`，记录为 `c:\p970\中文é\inc dir\héader.h`）；编译失败时也写出；模块接口单元同样（`ProvidedModule`）。只给该选项时 cl 的输出只有源文件名一行 |

| runner 的步骤 | 附着于一个没有窗口、代码页为 65001 的控制台 |

### 20.3 成因

1. **依赖取自写给人看的文本。** 前缀是界面字符串，随安装的语言资源与 `VSLANG` 变化；路径以控制台的代码页编码，代码页
   不能表示的字符成为 `?`，记录下的依赖指向不存在的文件。`VSLANG=1033` 是对前缀的变通：它假定英文资源存在，并覆盖
   用户自己的设置。
2. **文本跨进程时不带编码。** cl.exe 的文本按它所附着的控制台的代码页编码，mcpp 的文本是 UTF-8，两者之间的管道只有字节。
   编码只在运行该程序的进程中可知：ninja 的输出流中同时有 ninja 自己的 UTF-8 行（取自构建文件）与各步骤的字节，宿主工具链
   与目标工具链的步骤编码也可以不同，所以在 mcpp 读取 ninja 处统一解码是错误的。
3. **写出 JSON 的函数在外来字节上抛出。** JSON 只承载 UTF-8（RFC 8259 §8.1）；一个程序写出的字节不应使 mcpp 以内部错误
   结束。

识别 C1083 的英文句子是第 1 类在读诊断上的一个实例。

### 20.4 方案

**T1 依赖取自编译器为程序写出的记录。** 一次编译读取的文件取自编译器为程序写出的记录，不取自写给人看的文本。方言以数据
说明记录的形式（`inputsRecord`）：GNU 驱动写 Make 规则（`-MMD -MF $out.d`，`make`），cl.exe 写 `/sourceDependencies`
的 JSON 记录（`source-dependencies`）。执行器把 JSON 记录中的路径逐行写到自己的标准输出（前缀 `mcpp.inputs:`、一个
空格与路径），cl.exe 的编译边以 `deps = msvc` 与 `msvc_deps_prefix = mcpp.inputs:` 读取，GNU 驱动的编译边仍以
`deps = gcc` 读取它自己写的 Make 规则。不写成 Make 规则：ninja 1.12.1 读取 Make 规则时在 `'`、`&`、`;`、`^` 与反引号处
结束一个名字（`a'b.h` 读成 `a` 与 `b.h`，实测），Windows 的路径可以含有它们（`C:\Users\O'Neil`），而前缀行的其余部分
整体是路径；前缀是 mcpp 的，不随语言改变。
- 位于工具链环境的 `INCLUDE` 与 `EXTERNAL_INCLUDE` 目录之下的头文件不写入，与 `-MMD` 不列系统头文件相同；工具链与 SDK
  的改变由工具链的身份与构建环境反映。
- 位于构建目录（执行器的工作目录，即 ninja 的 `-C`）之下的路径，写作该目录的写法加上其下各级名字在磁盘上的写法：记录把
  路径改为小写，而生成的头文件是图中另一条边的输出，节点名须与之相同，否则生成器重新运行之后包含它的单元要到下一次构建
  才重编。与构建目录只在 ASCII 以外字母的大小写上不同的路径，按磁盘上各级名字的写法再比较一次（名字比较只折叠 ASCII）。
  其余路径按记录写出，Windows 的文件系统以不区分大小写的名字打开它们。
- 编译成功后写出路径，失败时不写（ninja 不读取失败的边的依赖）；记录在两种情况下都删除。
- 依赖因此与语言、控制台的代码页无关。cl.exe 的 `/showIncludes` 不再使用，`VSLANG` 不再设置：编译器的语言是
  用户环境的（`VSLANG` 或 Visual Studio 的界面语言），要英文诊断的用户自己设 `VSLANG=1033`。

**T2 文本在读入它的进程中按产生者的编码解码。** mcpp 内部的文本是 UTF-8。一个程序的文本在读入它的 mcpp 进程中解码，
编码由该程序所属工具链的方言以数据说明（`textEncoding`）：GNU 驱动为 `utf-8`；cl.exe、link.exe、lib.exe 与 rc.exe 为
`console`，即所附着控制台的输出代码页，没有控制台时为系统的 ANSI 代码页（20.2）。
- 执行器（`__compiler-cap`、`link-output`）接受 `--text console`：以一个管道读取程序合并的两个输出流，逐行解码，写到
  自己的标准输出。没有该词时照旧继承两个流，GNU 工具链的命令与行为不变。逐行解码不会切开字符：Windows 代码页的多字节
  序列与 UTF-8 的序列都不含换行字节。
- 方言的文本为 `console` 时，归档边经 `link-output --text console` 运行；不带发布选项时 `link-output` 只运行命令。
- mcpp 自己运行并读取的同一工具链的程序（std 模块的构建）以同一规则解码（`mcpp::run::Options`）。
- `console` 到代码页的解析与代码页到 UTF-8 的转换属于系统层：mcpplibs.os 0.4.6 的 `mcpplibs.os.text`，在每个系统上
  定义，Windows 以外 `console` 即 UTF-8。执行器、ninja 与编译器附着于同一个控制台（或都没有），执行器解析一次，所见即
  编译器所见；引擎不点名系统。
- 解码不改变内容：源文件名一行、诊断及其顺序保持编译器写出的样子。代码页不能表示的字符在 cl 写出时已成为 `?`，解码
  不能恢复；依赖不受影响（T1）。终端为 UTF-8 控制台（`chcp 65001`）时诊断保留全部字符。

**T3 承载程序文本的文档总是 UTF-8。** `result.json`、`target/.last-result.json`、事件流、协议的信封（含
`mcpp.build-database`）、测试运行的记录（`run.json`、`programs.ndjson`、`cases.ndjson`、`index.ndjson`）与构建程序
的图承载程序写出的文本（诊断、失败的输出）或路径，由一个函数写出（`mcpp::wire::text`），把不是 UTF-8 的序列写作 U+FFFD（Unicode 第 3.9 节，最大子部分
的替换）。T2 之下 MSVC 的文本不再经过它；它留给声明为 UTF-8 而实际不是的字节，例如 GCC 引用一个 Latin-1 源文件的行。
终端与日志中的输出保持原样。

**T4 诊断按各语言不变的结构读取。** MSVC 的诊断为 `<路径>(<行>[,<列>]): <严重性>[ <代码>]: <正文>`，严重性为
`fatal error`、`error`、`warning`、`note`，中文版亦然（20.2）。不带代码的 `note:` 行按这一形式读取。缺失的头文件以代码
`C1083` 与其操作数的位置识别：操作数是以最后一个冒号（其后是 C 运行库的原因，原因中没有冒号）之前结束的那段引号内的名字，
引号的字形（`'`、`“”`、`「」` 等）、冒号前后的空格与前面的词随语言变化（`file: 'x.h': No such`、`文件: “x.h”: No such`、
`include : 'x.h' : No such`、`。'x.h':No such`）。GNU 驱动的
诊断不在本节：其严重性词随区域设置翻译，mcpp 不设置区域，行为不变。

### 20.5 多视角复核

- **架构。** 事实（记录的形式、文本的编码）在方言的数据中；机制（转换、解码）在执行器与系统层；`check_system_names`
  的计数不增加。
- **稳定性。** 依赖与语言、代码页无关；程序写出的字节不能使 mcpp 以内部错误结束；依赖取自工具为程序写出的记录，与
  #931 的规则 B（链接器的报告）是同一原则。
- **简洁。** 每个编译边的依赖为同一形式（`deps = gcc`）；删除 `VSLANG` 的变通与 ninja 前缀的依赖。
- **用户体验。** 任何语言的 Visual Studio 在头文件改动后重编；终端中的诊断可读；`result.json` 的诊断为 UTF-8，`note`
  的路径与行号正确；缺失头文件的建议在各语言中给出。
- **兼容与无感升级。** cl.exe 的编译命令改变一次，各单元在升级后的第一次构建中重编一次；快速路径的环境键随 `VSLANG`
  的删除改变，自动重新生成。GNU 工具链的命令不变。用户自己的 `VSLANG` 从此生效。
- **跨平台。** `mcpplibs.os.text` 在每个系统上定义；Windows 以外执行器不加 `--text`。
- **测试覆盖。** 见 20.7；此前没有用例断言 MSVC 的构建记录了头文件依赖，#970 因此未被发现。

### 20.6 不采纳的做法

- **探测前缀并写 `msvc_deps_prefix`（报告的建议，CMake 的 `CMAKE_CL_SHOWINCLUDES_PREFIX`）。** 前缀的字节随控制台的
  代码页变化（同一前缀在 936 与 65001 下字节不同），按工具链缓存的前缀在另一个终端中失效；代码页不能表示的路径成为 `?`，
  依赖仍然错误。
- **设置控制台的代码页（`SetConsoleOutputCP(65001)`）。** 控制台由同一会话的所有进程共有，并行的执行器相互竞争，mcpp
  被强制结束时用户的终端停留在被改的代码页。
- **`VS_UNICODE_OUTPUT`。** MSBuild 内部的接口，没有公开的说明。
- **在 mcpp 读取 ninja 输出处解码。** 见 20.3 第 2 条。

### 20.7 验证

- **单元。** JSON 记录到依赖文件的转换：工具链目录的排除、构建目录之下的写法、空格与 `#`、`$` 的转义；MSVC 诊断的解析，
  英文与中文的样本（`error`、`fatal error`、不带代码的 `note`、`LNK`）；C1083 的识别，英文与中文的样本；`mcpp::wire::text`
  的替换。样本取自 20.2 的字节。
- **mcpplibs.os 0.4.6。** 936、1252、437 与 65001 的样本及无效序列的转换；附着于控制台时 `console` 解析为该控制台的
  代码页。
- **e2e（Windows，MSVC，970）。** 一个非 ASCII 目录中、头文件目录带空格的工程：编译规则带记录而不读 `/showIncludes`；
  头文件改为 `static_assert(false)` 后构建失败，改回后成功；在一个代码页为 936 的新控制台（`start /wait`）中构建失败时，
  mcpp 不以内部错误结束，终端与 `result.json` 中的诊断含正确的汉字。
- **规则的形状（单元）。** cl.exe 的编译规则带 `/sourceDependencies $out.json`、执行器的两个词、`deps = msvc` 与
  `msvc_deps_prefix = mcpp.inputs:`，链接与归档经 `link-output --text console`；GNU 工具链的命令不带这两个词。
- **语言包。** CI 不安装（6.4 分钟）；20.2 的测量由单元测试的样本覆盖。

## 21. 构建程序的解析范围、平台系列与两项引擎缺陷（#972）

**来源。** mcpp#972 与其补充评论（cmd.exe 解释器在 29 个目标上的验证）。按"排除不通用、不合规范的部分，从架构与成因解决"
分类后，用户决定：#965、#967、构建程序的解析范围（A）与平台系列的扩展随 2026.11.19.1 发布；映像启动映像（openkal-image#42）
并入 openkal-image 0.7.1。#956、#957 已在本轮修复（第 7 节）；无进程的系统（Web、UEFI、DOS）与 DJGPP 的 `fork` 不是缺陷；
`x86_64-windows-musl` 上的 "not recognized" 经分诊属于消费者：该行 `presents = "posix"`，消费者的 POSIX 分支以 `stat` 的属主
执行位判断能否执行，Windows 不记录这一属性（openkal fs.h），而 openkal-musl 的 `access(X_OK)` 与 `posix_spawnp`（`;` 与
`PATHEXT`）给出正确答案；盘符被正确识别。openkal-macos#53（PureDarwin 的卷不在声明执行属性的格式名单中）留在该仓库。

### 21.1 现状

- **一张解析表。** `ResolvedKey` 为命名空间、名字与变体；目标图、每个构建程序的 `[build-dependencies]` 闭包与宿主的读法都写入
  同一张表，一个包一个版本（`graph.cpp`）。构建依赖不改名（N29），所以两个版本被拒绝（"a build loads one version of it"）。
- **R10.2。** 宿主工具链与标准相同的构建程序是一个工作区的成员，由一个子构建规划；`resolution_pins` 按名字把外层的版本告诉
  子构建，一个名字一个版本。
- **测得。** 打包的 launcher（目标侧依赖 mcpplibs.os）与平台 0.31 的插件（宿主侧，经 mcpp.plugins 0.26.1 依赖 mcpplibs.os 0.4.5）
  共用一张表：launcher 写 0.4.4 与 0.4.6 都被拒绝，只能写平台构建程序的 0.4.5（e2e 988）。#972 的消费者的 `build.mcpp` 用
  mcpp.plugins 0.22.1，平台 0.31.0 的插件用 0.26.1，同样被拒绝，消费者只能抄写平台内部的版本。
- **平台系列。** 以范围选择的平台取范围内最新、引擎下界满足的版本（SPEC-013 §14）；版本组不容许目标图的某个请求时，整个
  构建以 `platform-version-group` 被拒绝。索引的平台列为 `@*`，消费者因此在自己没有改动时停止构建。
- **#965。** `resolve_clang_driver` 在载荷旁没有 cfg 时于取 base 的 C++ 头文件之前返回；`-nostdinc++` 只在 `bypassCfg`
  （要求载荷有 cfg）时写出。Windows 的 LLVM 载荷没有 `clang++.cfg`，所以 base 提供的 libstdc++ 在 Windows 主机上两者都失去
  （mcpp-platforms 的 Hurd、Haiku 两行）。libc++ 的 base 不受影响，因为 clang 的 FreeBSD、OpenBSD 驱动自己找到
  `usr/include/c++/v1`。
- **#967。** 索引的平台列（`platform_rows`）在本地索引中未命中时，行被拒绝为未知目标；依赖未命中时的刷新（`decide_for_miss`）
  不经过这里。

### 21.2 成因

1. **解析的范围是一次准备，而 C++ 模块的约束是一个程序。** 一个程序（一次链接）内一个包只能有一个版本；两个程序之间没有这个
   约束。执行上的共享（R10.2，多个程序使用的库只编译一次）被当成了解析上的约束。
2. **平台系列的选择只看引擎下界，不看本次构建能否使用该版本。**
3. **一个安装的事实决定了一个目标的事实。** 载荷旁有没有 cfg 文件决定了谁提供 C++ 头文件。
4. **索引的一种查询没有走索引未命中的统一策略。**

### 21.3 方案

**A1 解析的范围是程序。**
- 目标侧：命令选择的成员、它们经 `[dependencies]` 到达的包与平台加入的包是一个范围；版本组只约束它（SPEC-013 §7.5 不变）。
- 宿主侧：每个构建程序（一个包的 `build.mcpp` 或其规则合成的程序、平台的 `[platform] plugin`）以该包的 `[build-dependencies]`
  及其闭包为一个范围，以该包的身份命名（`build:<包>@<版本或来源>`）；一个构建依赖自己的 `[build-dependencies]` 是它自己的
  构建程序的范围。
- 请求在其范围内合并；不同范围的同一个包各有记录，互不约束。范围内的合并规则、变体与改名的边界不变；根的
  `override = true` 选择整个构建的版本，对所有范围生效。
- **共享。** 宿主范围的请求按约束取版本时，若另一个范围已取得满足该约束的版本，取其中最新者，否则取索引中最新者。没有冲突的
  构建因此与此前取得相同的版本，构建程序的身份不变，升级不引起重编。

**A2 执行：构建程序图按版本划分。** R10.2 的图仍按宿主工具链与标准分组；组内的程序按闭包中的版本划分：一个程序加入第一个
在共有的每个包上版本相同的划分，否则另起一个。第一个划分在原目录，其余在 `<group>-<摘要>`（摘要取该划分与第一个划分不同的
包与版本）。每个划分一个子构建，`resolution_pins` 取该划分的版本；划分内版本相同的包只编译一次，划分之间由全局依赖缓存按身份
共享。R10.3 的程序身份本来覆盖闭包中每个包的版本。

**A3 锁。** 一个身份一个条目；同一身份在另一个范围取得不同的版本时，该版本另成一个条目，名字带 `+b<范围摘要>`，`program`
写出该范围。合并与 `--locked` 按身份比较，不变。

**A4 诊断。** 冲突只在一个范围内发生：消息写出该构建程序（`the build program of <包>`）与每个请求者。

**A5 平台系列取可用的最新版本（SPEC-013 §14 第 2 条）。** 以系列选择、锁中没有记录的平台，解析因版本组被拒绝时，选择移到
系列中下一个更早、引擎下界满足的版本并重新准备；跳过的版本连同拒绝它的请求写入报告，与跳过引擎下界不满足的版本同一形式。
全部不容许时拒绝，消息列出每个版本与拒绝它的请求。精确版本与锁中记录的版本按写出的取。

**A6 launcher 回到 mcpp 自己的 mcpplibs.os。** A1 之后 launcher 的目标侧依赖与平台插件的宿主侧依赖互不约束；
`kLauncherOs` 与 mcpp 自己的版本相同，由 `check_version_pins.sh` 检查。

**B1 #965：C++ 层的词由提供者决定。** `resolve_clang_driver` 先取 base 的 C++ 头文件，再看载荷有没有 cfg；`-nostdinc++` 与该层的
目录在 C++ 层不由载荷提供时写出，与宿主无关；`--no-default-config` 仍由 cfg 的存在决定。

**B2 #967：平台列的未命中走索引未命中的策略。** 内置表与本地索引都没有答案的行，由 `decide_for_miss` 决定刷新（`--offline`、
`auto_refresh`、去抖、每次运行一次），刷新后重新扫描；仍未命中时拒绝，消息写出是否刷新及原因。扫描的缓存在刷新后作废。

**C1 映像启动映像（openkal-image 0.7.1）。** okrun 绑定 `kal_process_spawn`：映像文件或 okb 经 runner 指定的加载器启动，
`okrun [--require-signature] [--trust <key>]... --argv0=<argv[0]> -- <映像> <其余参数>`；启动前按加载器的检查拒绝不能发生的
启动（`kal_err_not_program`、`kal_err_permission`），句柄是加载器的、状态是映像的；其他文件按原样启动；不指定加载器的程序
（携带映像的程序）拒绝映像文件；映像的名字（`kal_env_image`）为解析后的绝对名。不采纳：binfmt_misc（只有 Linux，需要 root）、
映像自启动（ELF 的魔数须在开头，映像只导入 `kal_*`）、在 openkal 实现或 openkal-musl 中识别映像（它们不认识上层的加载器）。

### 21.4 多视角复核

- **架构。** 解析的范围与 C++ 的约束一致；执行上的共享由身份决定，不约束解析。平台系列与已有的跳过同一形式；#965 把安装的
  事实与目标的事实分开；#967 让索引的每种查询走一条策略。
- **稳定性。** 平台发布新版本或改变其内部构建工具的版本，不使消费者停止构建；冲突只在一个程序内报告。
- **简洁。** 不新增键；消费者与 launcher 都不再抄写平台内部的版本。
- **用户体验。** 跳过的平台版本与原因写在报告中；冲突的消息点名程序。
- **兼容与无感升级。** 没有冲突的构建版本不变、程序身份不变；只有此前被拒绝的构建得到新结果；锁只在两个版本并存时多出条目。
- **跨平台。** 与系统无关；#965 在每个宿主上相同。
- **测试覆盖。** 见 21.6。

### 21.5 不采纳的做法

- **构建依赖改名（N29）。** 构建程序以作者写的名字导入模块。
- **只分开目标侧与宿主侧，宿主侧仍一张表。** #972 的冲突在两个构建程序之间，不能解决。
- **宿主侧完全不共享。** 没有冲突的构建版本会改变，程序身份随之改变，升级后重编。
- **冲突时才给后来的程序另一条记录。** 一个共享包的依赖与该程序自己的请求可能取到两个版本，一个程序内出现两个版本。
- **以锁或新键固定平台系列。** 锁与 `[target.<选择器>] platform` 已经存在；问题是最新不等于可用。
- **B（范围代替精确版本）。** 0.x 没有兼容承诺，范围不能合并。

### 21.6 验证

- **单元。** 不同范围的同名包各有记录；共享的取版本规则；划分；锁条目的名字与 `program`；无 cfg 时 base 的 libstdc++ 的词；
  平台列未命中时的刷新决定。
- **e2e。** 工程的 `build.mcpp` 与平台插件用同一个库的两个版本（项目自己的索引），构建成功，两个程序各自编译；launcher 以
  mcpp 的 os 构建（988）；平台系列跳过版本组不容许的版本（项目索引中的两个平台版本）；平台列在刷新后命中（#967）。
- **openkal-image。** `examples/starts` 在四台机器上：启动自己（argv[0] 如启动者所给）、`exits.oke` 与一个系统程序；签名要求下
  未签名的映像被拒绝为 `kal_err_permission`；不指定加载器时被拒绝为 `kal_err_not_program`。

## 22. 源码的名字与路径依赖的缓存（#974）

**来源。** mcpp#974：经 `path` 到达的库从不进入全局构建缓存，依赖它的每个工程、每次干净构建都重新编译它；HuxerUI 的一致性 CI
中八个工程各自编译整个框架，每个约三分钟，调试与发布构建各一次，恢复 `~/.mcpp/build-cache` 也无济于事。用户决定：作为缺陷与
通用机制，从根与框架层面解决，修复并入 #966。

### 22.1 现状

- **依赖缓存。** 全局依赖缓存（`build-cache/v1/pkg`）只收索引包：`path`、`git` 依赖与工作区成员在任何深度都不缓存，依赖
  它们的包也不缓存（`localTaint`），理由是这些源码在版本不变时可以改变，以 `name@version` 为键察觉不到。
- **工具 store。** 宿主工具已按来源命名：`git` 包按解析的提交，`path` 包按树的印记（`tool_store::tree_stamp`：每个文件的
  相对路径、大小与修改时间），新条目写出时删除同一棵树的旧条目（mcpp#874）。
- **构建程序。** 程序的身份（R10.3）按树内容的摘要（`source_tree_digest`，以 stat 行缓存，mcpp#797）。
- 同一件事（一个包的源码是什么）因此有三种答法：依赖缓存没有答案，工具 store 用修改时间，构建程序用内容。

### 22.2 成因

1. **源码的名字没有一个定义。** 索引包的版本命名源码；`git` 与 `path` 包的版本不命名源码，依赖缓存于是整个放弃这些包，而没有
   换一个能命名源码的名字。工具 store 与构建程序各自补了一个名字，依赖缓存没有。
2. **"可缓存"按来源的种类判断，而应按"是不是正在编辑的树"判断。** 不缓存的真正理由只对工程自己的树成立：它每次编辑都是新键，
   进入缓存只增加写入与回收；工程之外的 `path` 依赖（框架、共享库）恰是被多个工程复用的部分。
3. **修改时间不是内容。** 检出、复制与 CI 的恢复改变修改时间而不改变内容，印记因而不命中；修改时间粒度之内的编辑又可能不被
   看见。

### 22.3 方案

**E1 一个源码的名字。** 索引包为 `name@version`；`git` 包为 `+git.<解析的提交>`；`path` 包为 `+path.<树内容摘要的前 16 位>`。
摘要覆盖依赖根下每个普通文件的相对路径与内容，不计 `target/`、`.git/`、`.mcpp/`、`compile_commands.json` 与带自己
`mcpp.toml` 的子目录（另一个包，以它自己的名字计入）。依赖缓存、工具 store 与构建程序的身份调用同一个函数
（`source_identity_suffix`、`tree_content_digest`），一次准备中每棵树只读一次；`tree_stamp` 删除。

**E2 工程自己的树在原处构建。** 正在编辑的树是：根包、被选择的工作区成员、本次构建的根（`workRoot`）之下的任何包；构建程序
与宿主工具的子构建继承上层构建的根（`own_roots`），上层工程的树在子构建中同样在原处构建。不以名字识别的包使依赖它的包也不进入
缓存（`localTaint` 的规则不变，判据换成 `sources_named`）。

**E3 摘要以内容为准，读取以 stat 为界。** 沿用 `source_tree_digest` 的 stat 行：大小与修改时间未变的文件沿用记录的内容摘要，
修改时间距记录时刻过近的文件（racily clean）重新读取。stat 行按树的路径保存在 `build-cache/digests/`；条目的键与树的位置无关，
同一份源码在两处检出共用一个条目。

**E4 写入前复核。** `path` 依赖的条目在编译完成之后、写入之前重新计算摘要；与键中的不同（编译期间被编辑）时不写入，作为降级
报告（`build/cache`，写出包与树），本次构建的产物照常使用。

**E5 一棵树一个条目。** 条目旁记录构建它的树（`source`）；写入新条目时，同一个包、同一棵树、另一个摘要的条目被删除，与工具
store 的规则（mcpp#874）相同。另一处检出是另一棵树，保留自己的条目，由 `mcpp cache gc` 按最后使用回收。

**E6 报告。** 命中的包一行 `Cached <包> v<版本> (<相对路径>, N units)`，与索引包同一形式；报告以包的限定名对应（此前缓存命中的
记录用依赖键，默认命名空间的 `greet` 与报告的 `mcpplibs.greet` 对不上，命中的包被显示为 `Compiling`）。`mcpp cache list`
显示 `<版本>+path.<摘要>`。

### 22.4 多视角复核

- **架构。** 一个名字、一个函数、三个使用者；是否缓存由"是不是工程自己的树"决定，不由来源的种类决定。
- **稳定性。** 内容摘要不受检出与恢复的影响；编辑中的构建不写入错误的条目；同一棵树的旧条目不累积。
- **简洁。** 删除 `tree_stamp`；不新增键与选项。
- **用户体验。** 多个工程共用一个框架时框架只编译一次；CI 恢复 `build-cache` 后命中；命中的包在报告中显示为 `Cached`。
- **兼容与无感升级。** 索引包的键不变；`git` 与 `path` 依赖在升级后的第一次构建写入缓存；工具 store 中以印记命名的旧条目不再
  命中，按新键重建一次，旧条目由回收删除；`--cache local` 与 `--cache off` 的含义不变。
- **跨平台。** 摘要以相对路径的 UTF-8 形式（`generic_u8string`）与内容计算，与宿主无关。
- **测试覆盖。** 见 22.6。

### 22.5 不采纳的做法

- **编译器启动器（ccache、sccache，#974 的备选）。** 只缓存单个编译，不缓存 BMI 与模块之间的次序；对模块单元的命中依赖编译器
  对路径的规范化；是引擎之外的第二个缓存，与依赖缓存的身份不一致。
- **继续用修改时间的印记。** 见成因 3。
- **工程自己的树也进入缓存。** 每次编辑一个新条目，就地的增量构建本来更快。
- **以绝对路径命名条目。** 同一份源码的两处检出（两次 CI 运行、两个工程）不能共用。

### 22.6 验证

- **单元。** 编辑与撤销编辑回到原摘要；`compile_commands.json`、构建输出与嵌套的包不计入；工具 store 的 scratch 目录。
- **e2e。** `bmi/19`：兄弟目录中的 `path` 依赖进入缓存，干净构建显示 `Cached mylibA v0.1.0 (../mylibA, 1 unit)`；工程目录之下的
  `path` 依赖在原处编译、不进入缓存；编辑后的新条目替换同一棵树的旧条目；传递的 `path` 依赖进入缓存；`cache list` 以 `+path.`
  显示；对传递依赖的编辑到达程序。`programs/857`：工作区之下的宿主模块库不进入缓存。两例在本地通过。
- **手工（#974 的复现）。** app1、app2 经 `path` 使用 greet：第二个工程显示 `Cached greet v0.1.0 (../greet, 1 unit)`；编辑 greet
  后重建一次并替换条目；把 greet 放入工程目录之下，在原处编译。
