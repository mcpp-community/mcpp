# 大型工作区的构建空间与复用（mcpp#874）

日期：2026-10-31。版本：mcpp 2026.10.31.3（PR #873）。前文：[part 2](2026-10-30-ecosystem-part2-ide-and-language-service-design.md) §25。
相关：mcpp#874（mui：112 个成员，`target/` 25 GB，`mcpp test --workspace` 407 分钟构建、3.4 分钟测试）、mcpp#702、SPEC-013 §4.6。

## 0. 结论

1. 一个开发构建的字节主要是**调试信息的副本**，不是代码。mcppls 的测试程序 `test_env` 为 96.0 MiB，其中调试段 91.2 MiB、
   `.text` 0.6 MiB；mui 的 `site_test` 中调试段占 80%。每个程序静态链接其闭包，并复制闭包全部对象的 DWARF。
2. 重复构建的原因是**键与图不稳定**，不是缺少缓存：host tool 的键取自本次命令走到的图，在 `test` 与 `build`、不同成员之间变化；
   action 规则没有 `restat`，生成器原样保留输出也使下游全部失效。
3. 本轮的做法分三类：去掉副本（调试信息、归档、放置、构建程序）、使键与命令无关（工具键、`restat`）、回收无人使用的内容
   （`uses.list`、全局缓存按最后使用回收）。每一项都不改变构建出的程序的行为。
4. 在 mcppls（6 个成员、61 个测试程序、clang）上实测：`bin/` 由 4 914 MiB 降至 1 217 MiB（−75%），测试链接时间合计由 75 s
   降至 32 s（−58%），编译 CPU 增加约 5%（clang；gcc 在测量波动内）。
5. 开发周期中的增长来自配置目录的数量：mcpp 升级、工具链变化使同一配置开出完整的新目录（mcppls 每次 2.9 GB）。
   复用的最细粒度是 ninja 的边，已经存在；本轮让同一谱系的演进在同一目录中发生（§8.3），并在构建后回收 3 天未用的目录
   （§8.4）。增长的上界由"历史的长度"变为"使用中的谱系数"。

## 1. 实测

### 1.1 mui（mcpp#874，mcpp 2026.10.27.1，gcc 16.1.0，dev，一个配置）

| 区域 | 大小 | 成因 |
|---|---:|---|
| `obj/` | 1.5 GB | 2 666 个对象 |
| `bin/` 测试程序（135 个） | 13.7 GB | 每个约 100 MB，DWARF 复制 135 次 |
| `bin/` 成员归档（15 个） | 5.3 GB | 11 433 个归档成员对应 2 666 个对象 |
| `bin/` 共享库放置（299 个） | 0.92 GB | 650 MB 为同一 `.so` 的副本 |
| `.build-mcpp/host/` | 743 MB | host 工作区内又嵌套了一份自身 |
| `.build-mcpp/out/` | 10 个哈希目录 | 7 个已无配置使用，`clean --stale` 不覆盖 |
| `~/.mcpp/build-cache/v1/tool/` | 611 MB | 17 个 `+path.<stamp>` 键，从不回收 |
| `~/.mcpp/build-cache/v1/std/` | 1.8 GB | 57 份 std 模块 |

一次 `mcpp test --workspace` 的 `.ninja_log`：6 512 条边对应 1 896 个输出，1 473 个输出被构建不止一次，
99.6 编译分钟中 69 分钟为重复构建；`runtime.o` 以同一命令哈希编译 7 次。

### 1.2 mcppls（本轮测量，clang 23.1.3，dev，`mcpp test --workspace --no-run`，61 个测试程序）

| 变体 | `obj/` | `bin/` | `test_env` | 其中调试段 | 测试链接合计 |
|---|---:|---:|---:|---:|---:|
| V0 2026.10.31.2（`-g`） | 824 MiB | 4 914 MiB | 96.0 MiB | 91.2 MiB | 75.1 s |
| V1 `-gz=zlib`（编译与链接） | 514 MiB | 1 937 MiB | 35.7 MiB | 30.9 MiB | 54.4 s |
| V2 V1 + `-fdebug-types-section` | 581 MiB | 1 799 MiB | 32.8 MiB | 27.9 MiB | — |
| V4 V1 + 本地单元 `-gsplit-dwarf` | 486 MiB（`.dwo` 55） | 1 217 MiB | 20.2 MiB | 15.4 MiB | 31.8 s |
| V5 本地单元 `-gsplit-dwarf`，不压缩 | 934 MiB（`.dwo` 324） | 1 217 MiB | 20.3 MiB | 15.4 MiB | — |
| V6 仅链接时压缩 | 823 MiB | 1 937 MiB | 35.7 MiB | 30.9 MiB | 52.2 s |

V4 中剩余的 15.4 MiB 调试段来自缓存提供的依赖对象（zstd、openkal-musl、mbedtls、mcpplibs.os、openkal-llvm-runtime、
libarchive 等，以压缩的形式留在段内，见 §4.1 (c)）。链接时间取自 `.ninja_log`，机器同时承载其他负载，作为方向而非精确值；
编译 CPU 以单个翻译单元重复编译、取用户态加内核态时间测得（§4.1）。

缓存提供的依赖对象在 `obj/` 中约 55 MiB，本地编译单元约 770 MiB：缓存到构建目录的拷贝不是主要成本（§4.8）。

## 2. 约束

- **不产生错误产物。** 缓存键逐字段比较；宁可多构建一次，也不复用输入不同的产物。
- **默认值不改变程序的行为。** 改变链接或运行方式的手段（共享闭包库、合并测试程序）不作为默认。
- **平台差异在实现内决定。** 一项手段按目标的对象格式、链接方式与调试器约定启用，不要求 mcpp.toml 区分平台。
- **可关闭。** 每项默认都有对应的关闭方式。
- **可验证。** 每项改变对应一个 e2e 判据，在旧版失败、新版通过。

## 3. 构成分析

| 来源 | 机制 | 占比（mui） |
|---|---|---|
| 调试信息副本 | 每个程序链接闭包的全部对象，链接器把每个对象的 DWARF 拷入输出；C++ 模块与 `import std` 使每个翻译单元重复携带标准库的类型描述 | `bin/` 的主要部分 |
| 成员归档 | 静态库链接单元收入了计划中全部编译单元的对象 | 5.3 GB |
| 共享库放置 | 已放置的等价副本在后续构建中被判为"已就绪"，不再换成链接 | 0.65 GB |
| 构建程序 | host 工作区的子构建在自身 `target/` 下计算 host 根，嵌套一份；构建程序旁的副本是拷贝 | 0.2–0.5 GB |
| 未回收目录 | `.build-mcpp/out/<hash>`、`host/<group>` 不在构建记录中 | 0.2–0.3 GB |
| 全局缓存 | `cache gc` 只覆盖 `pkg/`；std 与 tool 的命中不记录使用时间 | 2.4 GB |

| 重复构建来源 | 机制 |
|---|---|
| host tool 键 | 键的依赖闭包取自本次图：工具包只经构建依赖的 `tools` 到达时其依赖不被遍历（`test --workspace` 下闭包为空），作为成员构建时完整（`build`），被测成员的 dev-dependency 也会进入；键变则工具路径变，运行它的 action 全部重跑 |
| 无 `restat` | 生成器保留原输出时，ninja 仍视输出为新，扫描、BMI 与全部导入者重编 |
| 成员分组 | `test --workspace` 已按配置分组、每组规划与构建一次（成员选择设计 S4、D1）；组内的重复来自上两项 |

## 4. 方案

### 4.1 调试信息只存一份

**(a) 压缩调试段。** 有调试信息、目标为 ELF 时，编译与链接都加 `-gz=zlib`；平台以 `ld.lld` 直接链接的目标
（ok 映像）在链接行加 `--compress-debug-sections=zlib`。实测：

| 编译器 | `-g` | `-g -gz` | 对象大小 |
|---|---:|---:|---:|
| clang 23.1.3（mcppls 三个最大翻译单元，3 次） | 6.68 s | 6.66 s | 21.6 → 12.8 MiB |
| gcc 16.1.0（`import std` 与容器的 dev 翻译单元，8 次） | 3.19 s | 2.82 s | 程序 11.94 → 5.72 MiB |

压缩不增加可测的编译 CPU（两种编译器的差异都在 ±10% 的测量波动内），链接时间下降约 28%。gcc 的对象中调试重定位（`.rela.debug_info`）不压缩，对象缩小有限；链接后重定位消失，程序缩小 52%。gdb 与 lldb 读取压缩段。ok 映像：x86_64 映像
8.07 MiB → 3.93 MiB，okld 封装与 okrun 运行不受影响。

**(b) 本地单元的调试信息留在对象旁（`split_debuginfo`，新增 profile 键）。** profile 键 `split_debuginfo = "unpacked" | "off"`，
名称与取值取自 Cargo。`"unpacked"`：在构建目录中编译的单元以 `-gsplit-dwarf` 编译，`.dwo` 留在对象旁，程序中只有骨架，
链接器不再拷贝 DWARF。默认：`dev` 与 `mcpp test` 为 `"unpacked"`，其余 profile 为 `"off"`。

- 只在 `trim_paths` 关闭时生效：调试器按 `DW_AT_comp_dir` 加 `DW_AT_dwo_name` 查找 `.dwo`，`trim_paths` 把构建目录映射为
  `/mcpp/build`，查找会失败。`trim_paths` 默认只在 `release` 与 `dist` 开启，而这两个 profile 默认 `"off"`。
- `mcpp pack` 构建的 profile 默认 `"off"`，发布的产物带完整调试信息或被 strip，与现状相同。
- 实测：clang 编译 CPU +4.5%（与压缩同时使用），mcppls 的 `bin/` 再降 37%（1 937 → 1 217 MiB），测试链接合计再降 42%；gcc 编译 CPU 差异在波动内。收益随本地单元的数量增长：单个翻译单元的程序（调试信息主要来自 std 模块与库）只再降 4%（5.72 → 5.48 MiB）。

**(c) 缓存提供的单元保持压缩的段内调试信息。** 骨架记录的 `DW_AT_dwo_name` 是编译时的输出路径；缓存条目在临时目录中编译后
改名到最终位置，gcc 与 clang 都不对 `DW_AT_dwo_name` 应用 `-fdebug-prefix-map`（本轮实测）。要使骨架指向条目的最终位置，
需要逐边设置工作目录，或使用 clang 独有的 cc1 选项，代价与收益不成比例。缓存单元因此以压缩的段内 DWARF 为终点。

**(d) 不采用：类型单元（`-fdebug-types-section`）。** 单独使用时 `bin/` 降 7%，与 (b) 同时使用时无收益（V4 与 V2+V4 相同）。

**平台与工具链矩阵：**

| 目标 | 对象格式与调试信息 | (a) 压缩 | (b) split |
|---|---|---|---|
| Linux（gcc、clang）、交叉 Linux | ELF，DWARF 拷入程序 | 编译与链接 `-gz=zlib` | 默认 `unpacked`（dev/test） |
| ok 映像（`<arch>-openkal`） | ELF，`ld.lld` 直接链接 | 编译 `-gz`，链接 `--compress-debug-sections=zlib` | 默认 `unpacked`（实测骨架可封装、可运行） |
| 裸机（freestanding） | ELF，厂商调试器可能不读压缩段与 `.dwo` | 不启用 | `off` |
| macOS（Mach-O） | 调试信息留在对象中（debug map），程序不含 DWARF | 不适用 | 不适用（已是 unpacked） |
| Windows MSVC、clang-cl | PDB，每个程序一份，类型在 PDB 内合并 | 不适用 | 不适用 |
| MinGW（PE + DWARF） | DWARF 拷入 PE；汇编器不支持 PE 的压缩段 | 不启用 | `off`（PE 上的 split 不受支持） |
| WebAssembly（emscripten） | DWARF 在 wasm 自定义段 | 不启用 | `off` |

### 4.2 静态库只含本包对象（已实现）

静态库链接单元在计划完成后删去其他包的编译单元对象，与 docs/12"静态归档不携带其依赖的代码"一致。构建内的程序直接链接对象，
从不读归档，链接不受影响；`object` action 的输出不是编译单元，保留。mui：5.3 GB → 不超过各成员自身对象之和。

`mcpp pack` 发布的归档此前也携带依赖对象（对 path 依赖相当于隐式 vendor，对索引依赖则与消费者解析的同一依赖形成重复定义）；
现在只含本包对象，依赖由打包清单记录、由消费者解析，与文档一致。在 CHANGELOG 的 Changed 中写明。

### 4.3 共享库放置为链接（已实现）

`stage` 在目标已存在且内容相同时，若源为共享库且两者不是同一文件，以硬链接替换；无法链接时保留原副本。

### 4.4 构建程序（已实现）

- host 根由发起链路的构建传入子构建（`BuildOverrides::host_programs_root`），内层组为同级的 `<group>.<depth>`，不再嵌套。
- 构建程序旁的 `build.mcpp.bin` 是 host 组二进制的硬链接，失败时拷贝。
- 不同配置（dev、release、wasm）的 host 组本来就由（host 工具链、标准、版本）决定，已共享。

### 4.5 项目内回收（已实现）

- 每个配置目录写 `uses.list`：所用的 `.build-mcpp/out/<hash>` 与 `.build-mcpp/host/<group>`。
- `mcpp clean --stale` 以保留下来的配置目录的 `uses.list` 之并为在用集合，回收其余（`--older-than` 窗口内的保留）；
  没有任何 `uses.list`（旧版写的目录）时不回收这两类。
- `mcpp clean --report`：按配置给出 `obj`、BMI、`bin` 与 `.build-mcpp` 各区的大小。
- 构建前，构建目录所在文件系统可用空间小于 2 GiB 时警告，并给出回收命令。

### 4.6 全局缓存（已实现）

- `cache list/prune/gc/clean/verify` 覆盖 `tool/`；`clean --tools`。
- tool 条目命中时更新记录时间；path 工具写入新条目时删除同一源树的旧 `+path.<stamp>` 条目。
- std 条目命中时更新目录时间。
- 构建成功后至多每天一次，回收 `[cache] unused_days`（config.toml，默认 30，0 关闭）内未使用的 pkg、tool 与 std 条目。

### 4.7 重复构建（已实现）

- host tool 键的依赖闭包由工具包自身的 manifest 传递计算（与其子构建的解析一致）：path 依赖为版本与源树 stamp，git 依赖为
  声明的 rev，索引依赖为声明的版本要求；dev-dependency 不在其中。键与命令、成员无关。
- action 规则加 `restat = 1`：生成器保留原输出时，重建止于生成器。

### 4.8 评估后不采用

| 手段 | 不采用的依据 |
|---|---|
| 测试链接共享闭包库 | 代码只占测试程序的 0.6 MiB（`test_env`），(b) 之后剩余主要是缓存单元的调试段；收益集中在链接时间（V4 已为平均 0.52 s/个）。代价：`-fvisibility=hidden` 的包无法导出测试所需符号；MSVC 的数据符号需要 `dllimport`；ok 映像与裸机只有静态链接；静态初始化与单例的行为改变。 |
| 构建目录链接到缓存对象 | 缓存提供的对象只占 `obj/` 的约 7%；构建目录中的对象若是缓存的硬链接，此后本地编译写同一路径时会就地改写缓存条目。 |
| 项目级内容寻址对象库 | 同一配置内 ninja 已按命令哈希避免重复；跨配置的可复用部分以 dev/test 为主，而二者本来共用一个配置目录。收益不足以抵消 staging、`restat` 与 Windows 文件锁的改动面。 |
| 合并测试程序 | 改变测试的进程隔离，属于测试框架的选择，不属于构建系统。 |

## 6. 兼容与升级

- 编译行加入 `-gz=zlib` 与 `-gsplit-dwarf`，指纹变化，升级后每个配置完整重建一次；全局包缓存与 std 缓存各生成一份新条目，
  旧条目由 §4.6 的回收在 30 天后移除。
- 静态库内容变化（§4.2）：以 `bin/lib<target>.a` 在 mcpp 之外链接、且依赖其中携带依赖代码的用法需要同时链接依赖的归档。
- `uses.list` 由本版写入；旧目录在下一次构建后获得。
- `[cache] unused_days`、`split_debuginfo` 有关闭方式；`-gz=none` 写在包的 flags 中可关闭压缩。

## 8. 开发周期中的累积与划分的粒度

§1–§7 处理一次构建的大小。开发周期中 `target/` 的增长另有来源：配置目录的数量随时间增加。Cargo 的 `target/` 有同样的问题
（依赖的每个版本与 feature 组合各占一份，旧的不回收，需要 cargo-sweep 一类的外部工具）。

### 8.1 来源（代码与实测）

配置目录名 `target/<triple>/<fp>/` 的指纹有 11 个部分（`mcpp build --print-fingerprint`）：编译器名、版本、驱动身份、目标、
标准库与其版本、语言标准、配置级编译选项、mcpp 版本、`mcpp.lock` 哈希、std BMI、运行时契约。其中：

- `mcpp.lock` 哈希恒为空（`dependencyLockHash = ""`），依赖版本变化不开新目录。
- 编译选项一项是 `canonical_configuration_flags`：只含配置级的值（profile 键、方言选项、部署目标、c-abi 实现、调度、加速器）。
  包自身的 flags、feature 与依赖是节点的命令，在同一目录中由 ninja 增量重建。

因此随时间开出新目录的输入是：**mcpp 版本**（每次升级）、编译器版本与驱动身份、标准库版本、运行时契约、std BMI，以及配置级
选项的编辑。每次都是完整的新目录与一次全量重建，旧目录保留到手动 `clean --stale`。实测：mcppls 的同一配置因 mcpp 版本不同
有两个目录，共 4.0 GB；mui 的 `target/` 为 20 GB、3 个目录。

被删除或改名的源文件留下的对象与 BMI 与删除的代码量成比例，不是主要来源。不采用 ninja `cleandead` 式的"图外输出即删除"：
`mcpp build` 与 `mcpp test` 交替写同一目录的 build.ninja，按当前图删除会删去另一种图的输出。

### 8.2 划分的粒度

| 粒度 | 机制 | 复用的范围 | 结论 |
|---|---|---|---|
| 目录（现状） | 指纹的任一部分变化即新目录 | 同一指纹 | 演进输入使整份构建重复 |
| 边 | ninja 按每条边的命令哈希（`.ninja_log`）与输入时间决定重建 | 同一目录内命令未变的边 | 已是最细；前提是演进在同一目录内发生 |
| 包（索引包） | 全局缓存，键逐字段比较 | 所有项目、所有配置 | 已有 |
| 包（本地包）跨目录共享 | 项目级按包键存储，多个配置目录引用 | 不同配置中命令相同的包 | 不采用：各配置目录的 `.ninja_log` 互不知道对方对共享输出的改写，一个配置会把另一个配置写的输出当作自己的结果（命令哈希相同才安全，而键必须覆盖依赖的全部输出才能保证）；共享一个日志则把同一三元组的构建串行化。收益只在 feature 或成员选择不同、而 profile 与工具链相同的配置之间 |
| 单元变体 | 对象路径带命令哈希，多个变体并存 | 来回切换的单元 | 不采用：每次演进都留下变体，增长只能靠回收约束；对象路径不再稳定，所有按路径读取对象的工具（调试、编译数据库的消费者、测试）随之改变 |

结论：复用的最细粒度是边，ninja 已经实现；缺的是让演进发生在同一目录中。

### 8.3 谱系：一个配置的目录延续（已实现）

指纹分为两部分：

- **谱系**：编译器族、目标、标准库族、语言标准、配置级选项。开发者在其间切换、需要并存的值。工作空间中配置不同的组
  （`root_position_key` 不同）谱系不同，各有目录，不会互相覆盖。
- **演进**：编译器版本与驱动身份、标准库版本、mcpp 版本、std BMI、运行时契约。随时间单向变化的值。

目录名仍是完整指纹，构建记录、快速路径、`clean --stale` 的语义不变。每个配置目录记录 `lineage` 与 `toolchain`。规划到一个
尚无 build.ninja 的目录时，在同一三元组下找谱系相同、最近使用（build.ninja 最新）的目录：

- 工具链相同（只有 mcpp 版本、std BMI 或运行时契约变化）：其条目逐个移入新目录（包括 `.ninja_log` 与 `.ninja_deps`），
  原目录删除。ninja 以命令哈希判断重建：编译、扫描与链接命令不含 mcpp 的路径，命令不变的边全部复用；引用 `$mcpp` 的
  `stage`、`dyndep` 边重新执行，`stage` 有 `restat`，内容相同时不写、不向下传播。mcppls 的构建图：222 条编译与扫描边与 19 条
  链接边复用，111 条 dyndep 边与 2 096 条 stage 边重新执行。
- 工具链不同：其中的对象与 BMI 不可复用（驱动身份变化时命令可能相同而产物格式不同），删除它，在一个目录中全量重建。
- 另一个构建持有它的锁：不动它，本次构建另开目录（由 §8.4 回收）。
- 逐个移入而不是重命名目录：快速路径在发现记录的目录没有 build.ninja 之前已经取得该目录的锁（因此目录已存在），
  且 Windows 不能重命名有句柄打开的目录。

一致性：`build`、`run`、`test`、`pack` 经同一规划入口，规则相同。

### 8.4 构建后的回收（已实现）

`mcpp build` 与 `mcpp test` 成功后，每个项目每天至多一次，执行 `clean --stale` 的同一逻辑：构建记录之外、且 `keep_days`
（config.toml `[build]`，默认 3，0 关闭）内未写过的配置目录，以及无配置在用的 `.build-mcpp/out`、`host/` 目录，被移除，并以
一行报告。§8.3 之后，这类目录只来自不再使用的谱系（不再构建的目标、profile、工具链族）。

### 8.5 多视角

| 视角 | 说明 |
|---|---|
| 架构 | 指纹与目录名的语义不变；新增的只是目录之间的延续关系（`lineage`、`toolchain` 两个文件）与回收时机 |
| 稳定性 | 复用的正确性由 ninja 的命令哈希保证；工具链变化时不复用；移入失败时退回到新目录，§8.4 回收 |
| 用户体验 | 无需操作；移除旧工具链目录时报告 `Replaced`，回收时报告 `Swept` |
| 兼容 | 本版之前写的目录没有 `lineage`，不被延续；升级到本版后第一次构建全量一次，旧目录在 3 天后回收（若仍在构建记录中则保留，可 `clean --stale`） |
| 跨平台 | 逐个条目移动，避开 Windows 对打开目录的重命名限制；锁用非阻塞尝试，持有者不受影响 |
| 代价 | 同一谱系不能并存两个演进版本（例如对比两个 mcpp 版本的构建）；需要时用不同的 profile 名 |

### 8.6 收益

- 一个配置在整个开发周期中只占一个目录：增长上界由"历史的长度"变为"使用中的谱系数"。
- mcpp 升级由全量重建变为只重跑 `dyndep` 与 `stage` 边（编译选项不变时）；mcppls 的单个配置目录为 2.9 GB，每次升级不再新增。
- 不再使用的谱系在 3 天后自动回收。

### 8.7 验证

e2e 1000：同一谱系的前驱被延续、不重新编译；工具链不同的前驱被移除并报告；其他谱系的目录保留；构建后回收 `keep_days`
之外的目录，`keep_days = 0` 时保留。
