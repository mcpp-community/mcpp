**结论。**

1. 测试与 CI 的时间主要花在构建上，而测试系统只在用例的粒度上看得见它。mcpp 的 C++ e2e 分片把 2,579 至 7,255 s 的边
   用时花在平台运行时的编译上；boost-m 的 `mcpp test` 一步有 95% 是构建。
2. 构建被重复的原因是产物的地址含有不决定其内容的量。已核实三处：包实例的摘要含单元集合（#986）；缓存键含构建程序的
   输出目录，该目录在工程之内；缓存键含 home 的绝对路径。另有一处是缺少寻址：根工程的单元只按修改时间判定。
3. 嵌套的并行没有共同的预算：四个测试进程各自启动并行构建，4 个处理器上平均 6.8 至 9.4 个进程排队。同一工作的
   墙钟因此为单独运行的 2.3 倍，时限按墙钟陈述，于是失败。
4. GitHub 的同一种 runner 是三种处理器，同一组命令的处理器时间相差 1.62 倍。按墙钟陈述的时限与估计在机器之间不可比。
5. mtest 相对 doctest：断言多的文件编译更快（Clang 上 2 至 4.5 倍），每个文件的首次使用成本在 GCC 上高一个数量级
   （1.1 s 对 0.07 s），链接更慢、程序更大，在协议下每个用例多约 2 ms。四项各有可定位的成因（5.12）。
6. 一个提交被验证至少两次，而被发布的产物没有被完整验证：CI 测试宿主构建，发布另行构建静态包（5.22）。
7. 有三类行为今天的测试看不见：没有被任何测试用到的选项与键、通过的用例中未声明的降级提示、没有被固定的次序
   （5.16、5.18、5.19）。
8. 此前已实施的机制（一次构建、分片、按测量调度、main 的测试构建复用、脚本 e2e 的覆盖图）保留；本文不重复提出，
   并记录其中被测量否定的两项（第 2 节）。

**不在范围：** 测试的书写形式（对象名与标识的重复）；另行讨论。

### 1.1 三个部分

本文是生态级的方案：mtest 是各仓库共用的框架，mcpp 的测试系统是它最大的使用者，CI 的形态由二者的能力决定。

| 部分 | 内容 | 决定 |
|---|---|---|
| mtest：功能、框架、运行时的控制与配置、数据的粒度 | 协议的步骤、用到的面、构建记录、预算与抖动；机器与用量；时限与预算的门禁；运行夹具；账本；用例结束时的检查；golden；适配器；库自身的成本 | 5.5 至 5.10 的协议与引擎一侧，5.12 至 5.14，5.16 至 5.19，5.21 |
| mcpp 自身的测试系统 | 产物的身份与复用；运行器实现上述协议；测试 kit；按变更选择；测试的规则；以自身的构建与测试为基准 | 5.1 至 5.4，5.5 至 5.11 的运行器一侧，5.15，5.20，第 6 节 |
| CI 的形态 | 档位与树的标记、发布的提升、缓存的写入与传输、分片与预算、夹具的恢复、记录与摘要、下游仓库共用的动作 | 5.22，第 7 节 |

实施的任务与依赖在第 12 节，自评在第 13 节。

**此前被测量否定、本文不再提出的两项。**

- **按文件粒度的覆盖图为 C++ e2e 收窄选择。** 2026-11-14 的记录第 4 节：覆盖图中 `src/` 的文件被执行它的用例覆盖的比例

### 3.4 mtest 0.10.0 与 doctest 2.4.12

方法取自 doctest 的 `doc/markdown/benchmarks.md`：三个场景，单线程构建，以工程自己的目标文件的边用时之和为编译成本。
本机 x86_64，GCC 16.1.0 与 Clang 23.1.3（libc++），`dev`（`-O0 -g`），mcpp 2026.11.20.1；生成脚本与结果在探针的
工作目录，不入库。doctest 的文件以 `#include` 取得头文件，mtest 的文件以 `import mcpplibs.mtest;`。

**场景一：200 个各含一个函数的文件。**

| 每个文件增加的编译时间 | GCC doctest | GCC mtest | Clang doctest | Clang mtest |
|---|---|---|---|---|
| 只包含或导入 | 39 ms | 26 ms | 256 ms | 4 ms |
| 另声明一个用例、写一条断言 | 71 ms | 1,111 ms | 251 ms | 270 ms |
| 运行器的实现（一次） | 2.3 s | 无（库的编译 9 至 16 s，见下） | 1.2 s | 无（库的编译 4 至 11 s） |

**场景二：10 个文件，各 50 个用例，各 100 条断言（共 5 万条）。**

| 编译时间（s，减去基线前） | GCC | Clang |
|---|---|---|
| doctest `CHECK(a == b)` | 40.7 | 33.7 |
| doctest `CHECK(a == b)`，`SUPER_FAST_ASSERTS` | 15.2 | 16.3 |
| doctest `CHECK_EQ(a, b)` | 72.1 | 14.7 |
| doctest `CHECK_EQ(a, b)`，`SUPER_FAST_ASSERTS` | 11.0 | 4.6 |
| mtest `expect(eq(a, b))` | 22.6 | 7.6 |
| mtest `expect(a == b)` | 13.4 | 4.6 |

**场景三：一个用例中 1000 万条通过的断言（处理器时间，s）。**

| | GCC | Clang |
|---|---|---|
| doctest `CHECK(i == i)` | 0.67 | 0.79 |
| doctest `INFO(i); CHECK(i == i)` | 0.89 | 2.31 |
| mtest `expect(eq(i, i))` | 2.14 | 2.35 |
| mtest `expect(eq(i, i)) << i` | 2.15 | 2.43 |

**其余四项。**

| 项 | doctest | mtest |
|---|---|---|
| 一个测试程序的链接（GCC / Clang） | 0.34 s / 0.06 s | 0.92 s / 0.21 s |
| 一个测试程序的大小（GCC / Clang，`dev`） | 4.1 MB / 1.4 MB | 11.6 MB / 7.2 MB |
| 协议下 510 个用例、5 万条断言的程序 | 不适用（一个程序一个结论） | 独立运行 0.03 s；协议下 1.05 至 1.27 s，其中处理器时间 0.1 s：每个用例建两个文件并 `fsync`（共 4,044 次） |
| 库在每个工程中 | 仅头文件 | 重新编译：`mcpplibs.mtest` 的目标文件单线程 4 至 16 s，其依赖均命中缓存 |

**`release`（`-O2`，GCC 16.1.0；Clang 未测）。**

| 项 | doctest | mtest |
|---|---|---|
| 每个文件：只包含或导入 / 另声明一个用例、写一条断言 | 16 ms / 37 ms | 37 ms / 1,600 ms |
| 5 万条断言：缺省形式 | `CHECK` 175.8 s；`CHECK_EQ` 114.6 s | `expect(eq)` 82.5 s；`expect(a == b)` 19.3 s |
| 5 万条断言：doctest 的快速形式 | 48.9 s 与 12.2 s | — |
| 1000 万条通过的断言（处理器时间） | 0.30 s | 0.14 s |
| 库的编译（每个工程，单线程） | 无 | 16 至 33 s |

**读法。**

- doctest 的成本集中在实现的那一份：只在一个文件中实现时，其余文件在 GCC 上每个 39 至 71 ms。boost-m 的 416 个文件
  各实现一次。Clang 上每个文件的 0.25 s 不随断言增加；推断来自 doctest 的头文件包含的标准库头文件与标准库模块并存，
  未单独测量。
- mtest 的导入几乎不花时间，成本在首次使用：GCC 上声明第一个用例约 0.3 s，第一条 `eq` 再约 0.3 s（单独编译实测），
  在场景一中每个文件 1.1 s。断言本身比 doctest 的缺省宏便宜（GCC 上 22.6 s 对 40.7 s），在 GCC 上仍高于 doctest 的
  两种快速形式（15.2 s 与 11.0 s）。
- mtest 的程序更大、链接更慢，来自调试信息：11.5 MB 中调试段 8.5 MB，代码 1.1 MB，其中 `nlohmann.json` 0.13 MB、
  `mcpplibs.os` 与 openkal 0.09 MB（5.15）。
- mtest 库不由缓存提供：新的构建目录中，2026.11.17.2、2026.11.18.1 与 2026.11.20.1 都重新编译它（mtest 0.9.0 与

  `Cached`。缓存中有 `mcpplibs.mtest@0.9.0` 的一个条目，由别的依赖图写入。mcpp 不说明原因。

## 5. 决定

每项陈述决定、机制、它取代或关闭的事项，以及验收。验收的数字来自第 3 节；标为「推算」者在实施中以测量替换。

### 5.1 包实例的摘要是包的配置的函数（mcpp；关闭 #986）

**决定。** 一个包的实例由它的配置决定：声明的标志、宏、包含目录、按 glob 的规则、生效的特性、语言标准，以及其依赖的
实例摘要。实例目录的摘要与缓存键的配置部分由同一个函数产生。单元集合与单元的输出路径不进入。

**机制。** `plan.cppm` 中逐单元累加 `cu.object + flags_text(cu)` 的一段改为读取包的配置；`cache_key.cppm` 的
`fill_package_config` 是这个函数的现有形态，二者合一。按 glob 的规则以规则本身进入，而不是以它匹配到的单元。

**后果。** `mcpp build` 与 `mcpp test` 在特性相同时共用一个实例；测试计划以 `[test] features` 打开特性时配置不同，
实例不同，这是应有的区分。模块映射文件的名字含实例目录，随之稳定。`clean --stale` 与 `clean --report` 读取的
「每个配置一个目录」不变。

**包含目录是配置的一部分，只有一份推导（拉取请求 984）。** 一个包展开后的包含目录现有三份推导：依赖包的编译
（`package_root.cpp`：展开 glob，丢掉不存在的字面目录）、根清单的编译（`plan.cppm` 的
`expand_manifest_include_entry`：展开 glob，保留不存在的字面目录，因为它可能由稍后的构建步骤建立，#390）、资源脚本
（`windows_resources.cpp`）。#984 之前第三份不展开 glob，`*/include` 原样到达 `llvm-windres`，在 Windows 上失败；
#984 改为调用 `expand_dir_glob`，方向正确，CI 全部通过。核对代码后有一处：它没有第二份的回退，规划时尚不存在的
字面目录此前被原样拼接，现在被丢掉，资源脚本包含其中生成的头文件时首次构建找不到、第二次构建找到。这一点来自
读代码，没有运行复现。本轮把资源脚本改为调用 `expand_manifest_include_entry`，并在用例 837 中增加「稍后建立的字面
目录仍在 `rc_object` 的边上」；三份推导随配置函数合为一份。

**验收。** #986 的最小复现：`mcpp build` 之后 `mcpp test` 只编译 `src/b.cppm` 与 `tests/t.cpp`。SPEC-004 §9 第 17 项
写明摘要的输入。

### 5.2 路径按角色进入键；可缓存的包的构建程序输出在 home 中按身份寻址（mcpp）

**决定。** 键中的路径以其角色出现：`<store>`（每一个存储根）、`<pkg>`、`<out>`（构建程序的输出）。绝对路径不进入键。
来源被命名的包（索引的版本、git 的提交、路径依赖的内容摘要，#974），其构建程序的输出目录位于
`<home>/build-cache/v1/out/<包>@<版本>/<键>`，键为该包不含输出目录一项的配置键。

**成因的细节。** `state.programOutDir` 把输出目录放在 `<工程>/target/.build-mcpp/out/<id>/<包>`；构建程序以
`mcpp:include-dir=<OUT_DIR>` 声明的目录进入包的键，`relativize` 只认识 `<store>` 与 `<pkg>`。`openkal-musl`（openkal
目标）与 `openkal-windows`（windows 目标）因此每个工程一个键，其上的 `llvm-runtime` 经 `upstream` 一项随之改变。
另一处：`nlohmann.json` 的包含目录以 `/home/<用户>/.mcpp/registry/data/xpkgs/...` 进入 `mcpplibs.mtest` 的键
（`mcpp cache info`），`relativize` 只替换第一个存储根。

**不采用「在键中抹去路径」。** 构建程序收到 `MCPP_OUT_DIR`，可以把它写进生成的文件；输出的位置因此是内容的一部分。
把位置固定为身份的函数，内容与地址才一致。输出按 2026-11-19 记录的事务方式发布：两个工程同时运行同一个构建程序时，
先完成者发布，后完成者核对后采用。

**验收。** 探针的第二遍：同一 home 的新工程中，三个配置的步骤 A 不编译平台运行时的任何单元。预期用例 955 的步骤 A
由 478 s 降到与步骤 D（7 s）同一量级加打包的时间（推算）。新增 e2e：两个工程依次构建同一 openkal 目标，第二个工程的
编译边数为它自己的单元数。

### 5.3 根工程与未命名来源的单元按内容寻址（mcpp；取代 W1 的修改时间恢复；关闭 #927 第 5 项）

**决定。** 执行器在运行编译器之前计算这次编译的键，命中时从缓存发布输出，不运行编译器。键的输入是决定输出的全部：
工具链的身份、归一后的命令、源文件的内容、它读取的每个文件的内容、它导入的每个 BMI 的内容。引擎的版本不进入。

**机制。**

- 位置是 `__compiler-cap`：它包住有上限的图中的每一条编译命令（2026.11.7.1 起），持有输出的发布（2026-11-19 记录
  10.6）。本项使每个图都经由它。
- 读取的文件在编译之前未知，采用清单的方式：第一级键（命令、源文件内容）指向若干份清单，每份清单是一次编译实际读取
  的文件及其摘要（来自依赖文件；MSVC 来自 `/sourceDependencies`）；清单中的文件都未变时，其结果即命中。
- 输出为目标文件、BMI、依赖文件与拆分的调试信息。GCC 的 BMI 以模块映射的拼写记录其导入的路径（BMI 目录与包的
  实例），随 5.1 稳定；Clang 与 MSVC 的 BMI 在验收中各自核对。
- 源码根的绝对路径进入键，除非工具链的行陈述其输出可重定位。CI 的检出路径不变，命中不受影响；本机的两个工作树之间
  不共享，这是正确的结果。
- 条目位于 `<home>/build-cache/v1/unit/`，由 `mcpp cache gc` 按最近使用回收。CI 中只有 main 的推送运行写入（R3，5.22：它登记一次已通过的
  全量运行的条目，或自己运行全量），拉取请求的运行只读；经 artifact 传输：仓库的 Actions 缓存已用 9.98 GB（2026-11-14 记录 6.1）。
- ninja 仍决定哪些边要运行；新的检出使全部边变脏，执行器逐条命中并以 `restat` 结束。链接不缓存。
- 文件的摘要在一次构建中按（路径、大小、修改时间）记忆，一个头文件只计算一次。
- 修剪按使用：全量运行在上传之前去掉本次没有读取的条目，传输的大小随当前的树，不随历史。

**取代。** W1 的 `source_mtimes.py` 与 `.source-blobs`；`bootstrap-mcpp` 恢复 `target/` 后仍运行 830 条边中的 830 条；
第 3.5 节中各作业从零构建 mcpp；工具升级后的全部重编（指纹目录改变，条目命中）。

**验收。** 在一个已填充缓存的 home 上，新检出的无改动构建不运行编译器，其用时记入本文（现为 11 分 37 秒）；改动一个接口模块时，运行的编译器数为其
导入闭包的单元数。逐字节核对：同一键的两次冷编译产出相同的目标文件与 BMI（GCC、Clang、MSVC 各自测量；不相同的
工具链在其行中标为不可缓存，并以 `diag::degraded` 说明）。

### 5.4 缓存的每一次拒绝都有原因（mcpp；mtest 库不由缓存提供）

**决定。** 一个包或一个单元未由缓存提供时，构建记录写出原因标记，`--verbose` 打印它。`serve_or_fill` 现有的五条返回
路径（无身份、来源未命名、受未命名来源影响、不在存储之内、有不可寻址的单元）各一个标记。

**mtest 库。** `mcpplibs.mtest` 作为根工程的 dev 依赖不由缓存提供，也不被写入（3.4）。成因未定：它落在上述五条路径
之一，而这五条路径今天不可区分，这正是本项要改变的。成因在实施中以原因标记确定，并按成因修复。每个使用 mtest 的
工程、每个 e2e 用例建立的工程都付出这次编译。

**验收。** 新工程第二次构建时 `mcpplibs.mtest` 显示为 `Cached`；新增 e2e 断言 dev 依赖由缓存提供。

### 5.5 一台机器一份预算：处理器槽位与内存（mcpp；SPEC-017 新增 O11；关闭 #802）

**决定。** 运行测试的 mcpp 持有机器的预算。它的工作进程与这些进程启动的每一次构建从同一份预算取槽位。预算另带内存的
阈值：可用内存低于阈值时不发放新的槽位，已运行的编译器不被结束。

**机制。**

- 预算是一个目录，其中有与槽位数相同的文件；持有一个文件的锁即持有一个槽位。运行器建立它并在环境中陈述其路径
  （SPEC-017 O11 `budget`）。任何程序都能遵守：`mcpplibs.os` 的文件锁，或脚本中的 `flock`。不认识它的程序不受影响。
- 一个测试进程持有一个槽位；它启动的构建以这个槽位为第一个编译器，其余向预算申请。不构建的测试以自己的槽位运行。
- mcpp 的执行器在环境陈述了预算时，启动编译器之前先取预算的槽位，再取本次构建的 generation 的槽位；没有陈述时
  只取后者（现状）。
- 内存的准入在同一处：执行器在取得槽位后、启动编译器前读取可用内存（`mcpplibs.os.machine`）。阈值是数据
  （`[build] memory_threshold`，四层取值）。`bmi_schedule = "on"` 的分离代码生成经同一执行器，因此被覆盖。
- mtest 引擎运行脚本 e2e 时同样建立并陈述预算。

**验收。** 探针的分片条件重跑：运行队列的平均值不超过处理器数加一；用例 955 的步骤 A 在分片内的墙钟不超过单独运行的
1.3 倍（现为 2.3 倍）。分片的总墙钟不增加。

### 5.6 构建是运行图的节点（mcpp、SPEC-017 B4；关闭 #927 第 2 项）

**决定。** 运行存储新增 `runs/<id>/builds.ndjson`：每条运行过的边一行（输出、所属的包与测试程序、开始、用时、
处理器时间、最大驻留集）；由缓存提供的边按包汇总为一行。`mcpp test` 与 `mcpp build` 的汇总行列出各阶段，并列出最慢的若干条边。
一条边运行超过一分钟而无输出时，进度行写出正在运行的边及其已用时间。

**机制。** ninja 的日志已有每条边的开始与结束，`progress::Attribution` 已把边归属到包；处理器时间与最大驻留集由
执行器在回收编译器时取得。本项把它们写出。
P12.3 规定的关键路径由此可以下到边。按测量的调度（O10）在排序测试程序时计入其构建的用时。

**验收。** boost-m 的一条腿重跑后，存储回答第 3.3 节的问题：长尾是哪些边、各用多久。`mcpp test -p` 的汇总各段之和
与总时间之差小于 1 s。

### 5.7 步骤是用例的一部分（SPEC-017 P5、mtest、测试 kit）

**决定。** 协议新增 `step` 事件：属于一个用例，带名字、开始、用时、处理器时间、退出状态。测试 kit 为它运行的每条
mcpp 命令写一个步骤；该命令是一次构建时，步骤带上那次构建的记录标识。

**后果。** 用例 955 的四个步骤各自可见；`mtest analyze path` 从运行下到用例、步骤、边。探针三轮得到的分解成为一次查询。

### 5.8 时限只陈述一次，按处理器时间比较（mcpp、mtest；关闭 #976 的一项）

**决定。**

- 用例或套件声明的 `timeout` 是唯一的时限。选择一个套件之下的用例时，运行器取它所属的各级作用域声明的时限
  （`--case 'sets/*'` 与 `--failed` 现取运行的缺省 300 s 或 `--timeout`）。
- kit 的每条命令缺省 10 分钟的时限改为取用例剩余的时间。
- 时限防止挂起。性能以指标判定：每个用例的处理器时间进入记录（5.9），界限与趋势按它陈述（P6.5），不按墙钟。
- 报告列出余量：最近若干次运行中用时超过时限五分之四的用例，连同机器的类别。

**验收。** #976 的重现：`--case 'sets/*'` 在套件的 30 分钟内运行。

### 5.9 机器与用量进入记录（mcpp）

**决定。** `run.json` 的 `machine` 写出处理器型号、核数、内存（型号取自 `mcpplibs.os.machine` 新增的接口，任务 O1；没有回答的系统上机器的类别取架构与核数）；`mcpp test` 缺省以 `basic` 陈述监测程度，并按 P10.4
从自己的进程测量不写 `usage` 的程序。按测量的调度与分片在估计用时时按机器的类别取历史；没有该类别的历史时取全部。

**验收。** 同一测试在两类机器上的估计分开；3.1 的 1.62 倍在报告中表现为类别的差异，而不是回归。

### 5.10 共享的 home 是运行夹具（mcpp 实现 O6；测试 kit；关闭 #293，处理 #976 的 875）

**决定。** `mcpp test` 实现运行夹具（P11）：以 `MTEST_SERVE` 服务，把端点交给使用它的程序。测试 kit 把现在隐式共享的
home 声明为运行夹具：其内容（工具链、平台包、索引）是声明，摘要是它的身份。

- 夹具的准备用时记在夹具上（`fixtures.ndjson`），不记在碰巧第一个运行的用例上。
- 用例陈述它对 home 的使用：只读，或修改。只读的用例共用一个；修改的用例得到自己的 home，其载荷以只读的存储根
  提供，而不是指向共享载荷的符号链接。`home::shared` 之下以 `machine` 独占来避免干扰的用例改为后者。
- CI 以夹具的身份为键恢复它；5.2 使其中的构建缓存对每个工程有效。

**验收。** 875 与并行的用例同时运行而不受干扰；`sets`、`trees` 的第一个用例不含填充的时间；#293 的复现不改写
开发者的载荷。

### 5.11 按变更选择的两处补充（mcpp）

- **头文件。** `--since` 现把任何头文件的变更视为影响全部测试。改为：构建目录或存储中有基线提交的依赖记录时，
  头文件影响依赖记录列出它的单元及其导入者；没有记录时保持现状。记录是 5.3 的清单（每个单元实际读取的文件），
  随 main 登记的单元缓存到达拉取请求。对头文件构成的库（boost-m）这是按变更选择能否生效的条件。
- **C++ e2e。** 文件粒度已被否定（第 2 节）。本轮测量函数粒度：覆盖图记录每个用例执行的函数，统计一个函数被多少
  用例执行。中位数低于 50% 时实施（变更的函数与用例执行的函数相交），否则把测量记入本文并不实施。

### 5.12 mtest 库的四项成本（mtest；其中一项归 mcpp）

| 项 | 成因 | 决定 | 验收（第 3.4 节的方法） |
|---|---|---|---|
| 每个文件的首次使用（GCC 1.1 s） | 接口中的模板与标准库类型在每个导入者中实例化 | 用例的声明与 `expect` 的常见形式（整数、字符串、布尔）在库中有非模板的入口；接口不要求导入者实例化 `std::function`、流与格式化 | GCC 上每个文件不超过 150 ms |
| 链接与程序大小 | 依赖与运行时库的调试信息（8.5 MB 中的大部分）；JSON 库的代码只有 0.13 MB | 不在库中处理：库继续依赖 JSON 库（mtest 的规则：已有的库被依赖，不重写）；由 5.15 处理 | 见 5.15 |
| 协议下每个用例约 2 ms | 每个用例为输出归属建两个文件并 `fsync` | 输出经由一个按用例标记的通道；不 `fsync`（进程崩溃不丢失已写入的数据） | 510 个用例的程序在协议下不超过 0.1 s |
| 每个工程重新编译库 | mcpp 不由缓存提供它（5.4） | — | — |

断言的运行成本（每条 0.2 µs）不处理。

### 5.13 需求、用例与理由的账本（mtest）

**决定。** `mtest.toml` 的 `[ledger.<名>]` 陈述一组需求的来源（一个文件，或一条产生列表的命令）。用例以 `clause{}`
陈述它覆盖的需求。每条需求必须有通过的用例，或一条带理由的豁免；豁免的数目只减不增。`mtest gate` 判定，
`mtest report` 生成表。

需求由产品给出、证据取自记录的形式见 5.16。

**取代三份手工维护的账本。** mcpp 的 `tests/e2e/coverage-debt.tsv` 与 `coverage-exceptions.tsv`；`docs/specs/` 中
每条条款的实现状态；boost-m 的 `coverage.toml` 与 508 行的 `test_coverage.py`。

### 5.14 其余

- **doctest 适配器（mtest）。** 与 GoogleTest 适配器同级（1 级）：一个 doctest 的报告器与入口，使现有的 doctest 程序
  列出、选择并报告用例。测试文件去掉 `DOCTEST_CONFIG_IMPLEMENT_WITH_MAIN` 一行，其余不变：实现与入口由适配器提供
  一次，每个文件各实现一次的成本（GCC 上约 1.6 s）随之消失。
- **归档运行的选择（mcpp）。** 3.1 的三个缺陷：归档运行接受部分的模式；已列出用例之下的通配选中匹配的用例；
  `--cases --archive` 列出而不报错。
- **骨架的 mtest 版本（mcpp）。** `kMtestRelease` 进入 `check_version_pins.sh`。

### 5.15 依赖的调试信息是 profile 的数据（mcpp；mcpp#927 第 4 项）

**测量。** 一个 mtest 的测试程序（GCC、`dev`）11.5 MB，其中调试段 8.5 MB（`.debug_info` 6.0），代码 1.1 MB。按符号归属的代码：
标准库与运行时 0.74 MB，mtest 0.14 MB，`nlohmann.json` 0.13 MB，`mcpplibs.os` 与 openkal 0.09 MB。链接已带
`--gc-sections`。程序的大小与链接用时因此来自依赖与运行时库的调试信息，不来自 JSON 库的代码。#927 的工作区中，
349 个测试程序占 22 GB 中的 15.4 GB，去掉调试信息并剥离后一个程序由 24.5 MB 降为 4.3 MB。

**决定。** profile 按包的类别陈述调试信息的程度：工作区的成员一类，来自存储与 git 的依赖一类。`dev` 之下成员保持完整的
调试信息，依赖缺省为 `debug = "lines"`（已有的取值：只带行表，回溯仍有文件与行号）；两者都可在 profile 中覆盖。
陈述依赖一类的键的拼写与缺省的程度在 SPEC-004 中陈述（N8）。

**机制。** 标志是工具链行的数据（GCC `-g1`，Clang `-gline-tables-only`，MSVC 的对应项）；它进入包的配置（5.1），
依赖因此在缓存中另有条目。工具链自带的静态运行时库中的调试信息不由编译标志控制，其份额在实施的第一步测量。

**验收。** 3.4 的方法重测：程序的大小、链接用时与依赖的编译用时记入本文；#927 的工作区重测测试程序的总大小。

### 5.16 产品面的覆盖（mtest 的账本，mcpp 给出面与记录；扩充 5.13）

**决定。** 账本的需求可以由产品自己给出，证据可以取自运行的记录，而不只取自用例手写的 `clause{}`。

- **面。** `mcpp emit surface` 写出 mcpp 的面：每个子命令、每个选项、清单的每个键、每个原因标记，一行一项
  （`command build`、`flag build --target`、`key build.sources`、`reason build/cache`）。命令与选项取自命令行的
  定义，键取自 `mcpp.manifest`，原因标记取自 `check_reason_tokens.sh` 所核对的那些；本项只是写出。
- **证据。** 协议新增 `exercise` 事件：属于一个用例，列出它用到的项。测试 kit 为它运行的每条 mcpp 命令写出命令与选项；
  一次调用读取的键与发出的原因标记由 mcpp 写入该次调用的记录（环境变量指明文件），kit 转为 `exercise`。
- **判定。** 面中没有任何用例用到的项使门禁失败，除非账本中有带理由的豁免；指向已被用到的项的豁免同样失败。
  不设百分比的门槛。

**取代。** `check_e2e_coverage.py` 之外没有检查回答「哪个选项、哪个键从未被测试用到」；AGENTS.md 的「未知的键被报告」
与本项互为两面。

### 5.17 预算是门禁（mtest；mcpp 的分片）

**决定。**

- `mtest.toml` 的 `[budget]` 陈述一个用例的处理器时间上限与一个作业的墙钟上限。超过用例上限的用例使 `mtest gate`
  失败，除非有带理由的豁免（5.13 的形式）。处理器时间取 5.9 的记录，按机器的类别比较。
- 作业的上限决定分片数：`mtest ci plan` 已按宿主的历史为脚本 e2e 计算分片；`mcpp test --shard` 的 C++ 测试改为同一
  来源（现为固定的四片）。

**验收。** 用例 955 与其余超过上限的用例各有一条理由；一个新加入而未豁免的超限用例使门禁失败。

### 5.18 用例结束时的检查（mtest 的 e2e 模块；测试 kit）

**决定。** e2e 的用例结束时检查两件事，任一不满足即失败。

- **进程。** 用例启动的进程都已结束。`mcpplibs.os` 的进程单元已能回答一个单元是否为空。
- **诊断行。** 被运行的程序的输出中，匹配工程声明的诊断模式的行，必须由用例声明；用例声明而没有出现的行同样失败。
  mcpp 的 kit 声明的模式是 `warning:`、`error:` 与降级的提示。

**依据。** AGENTS.md：做得少不能静默。今天一个用例通过时，mcpp 在其中打印的降级提示不被任何检查看见。

**迁移。** 现有用例中合法出现的诊断行在本轮逐个声明；其数目在实施中以报告模式测得。

### 5.19 抖动（SPEC-017 新增 O12；mtest、mcpp 的钩子）

**决定。** 运行器可以陈述抖动的上限（毫秒）与种子。框架在声明的竞争点、kit 在每条命令的前后、mcpp 在取锁与发布处，
各等待一段不超过上限的随机时间。它在三种场合运行，不每夜运行：

- **结论翻转时。** 存储中一个用例的结论在同一棵树上发生改变（重试后通过，或两次运行不同）时，CI 以若干个种子带抖动
  重跑这一个用例，把结果与种子写入摘要。
- **每周一次**，在 main 上运行全部测试。
- **手动。**

**依据。** 偶发失败的来源是没有被固定的次序。这类缺陷只在并发相关的代码改动时新增，每夜扫描在绝大多数夜里没有发现；
已有的证据是 2026-11-15 并行暴露的两个锁的缺陷（#976 的四个偶发失败中，两个与次序无关，一个由 5.10 解决）。
能力本身很小，定位一个翻转的用例时才用得上它。

**边界。** 抖动不进入拉取请求的运行与全量的验证。mcpp 的钩子是一个环境变量与一处等待，位于取锁与发布所经过的
一个函数中。

### 5.20 等待事件，不等待时间（mcpp 的测试）

**决定。** 测试只等待被测程序给出的事件（一行输出、一个文件、退出）。`sleep_for` 与轮询不出现在新的测试中；现有的
77 处记入基线文件（`.github/tools/` 中已有两份同类的基线），基线只减不增。时间本身是断言的用例在基线中注明。
测试需要而产品没有的事件，加到产品中。

### 5.21 契约性的输出整段比较（mtest 的 golden；mcpp 只用于契约）

**决定。** `e2e::golden` 增加脱敏的规则（路径、用时、大小、摘要）与更新时的摘要（哪些块改变、新增、移除）。mcpp 的
测试把它用于其格式本身是契约的输出：机器可读的记录（docs/50）与带原因标记的拒绝。现有的 2,302 处 `contains(` 不迁移。

### 5.22 一棵树验证一次，被使用的就是被验证的（CI；发布规程）

**现状。** 一次合入至少有两次全量运行：拉取请求上一次，合入后 main 上一次（发布提交的那一次现在被手动取消）。CI 测试的是
`mcpp build --strict` 的宿主构建；发布的是 `release.yml` 另行构建的 `mcpp pack --target x86_64-linux-musl` 静态包，
它在发布前只经过冒烟，完整的验证在发布之后（`ci-fresh-install`）。main 的规则集没有必需的状态检查：CI 的结论由
负责人查看后合入（3.6）。

**决定。** 验证的对象是源码树，不是提交，也不是推送。

- **标记。** 一次全量运行通过后，留下以树的标识命名的标记，连同它的归档、缓存条目与记录。任何之后的使用都按树查找。
- **全量运行属于检查点。** 拉取请求的推送运行 `pr` 档；工作到达一个检查点时加 `ci:full`，运行全量。实施中的提交是
  本地的检查点，推送发生在包含多个提交的检查点上。
- **main 的推送。** 合入的提交的树已有标记时（验证之后 main 没有移动），不运行测试：把那次运行的产物登记为 main 的，
  保存缓存。没有标记时运行全量。供其他运行使用的缓存与历史只由这一步写入（R3 不变）。
- **发布。** 标签所指的树已有标记时，提升那次运行的归档；没有时按现在的方式构建，并写明这次是构建。
- **被测的即被发布的。** CI 中被测的二进制改为发布的形态：`build.yml` 产出打包后的归档，测试使用其中的程序。

| 时机 | 运行 | 产物 |
|---|---|---|
| 拉取请求的推送 | `pr` 档：每个宿主的构建与门；Linux 的全部单元分片与脚本 e2e 的 `pr` 集合；macOS 与 Windows 各一个单元作业；容器中的 e2e 与各宿主的 e2e | 不被使用 |
| 拉取请求加 `ci:full`（检查点） | `full` 档：全部作业 | 通过时留下树的标记 |
| 推送到 main | 树已有标记：只登记与保存；没有：`full` 档 | main 的缓存、历史、覆盖记录 |
| 发布 | 树已有标记：提升；没有：构建 | release 的归档 |

**合并队列不是前提。** GitHub 的合并队列在合入之前对「main 加上排队的拉取请求」运行必需的检查，是给出同一个标记的
又一个来源。工作流接受它的事件，启用与否是仓库的设置：在规则集中加入「要求合并队列」与「要求状态检查」（指向汇总
作业 `verdict`）两条。每天合入 1 至 4 个拉取请求时不启用；并发的合入使 main 在合入后才发现失败成为常态时，由负责人
启用，工作流与本文不需改动。

**代价。** 拉取请求验证之后 main 又移动时，验证发生在合入之后，与今天相同。次要作业的问题到检查点才暴露。

**前提，在实施中核对。** 测试是否依赖宿主构建而在静态二进制上不成立；macOS 与 Windows 的 CI 构建与发布构建的差别；
mcpp 的二进制不含提交的标识（同一棵树的两次构建给出同一个程序）。

### 5.23 构建程序的输入由观测给出；提示的统一机制；契约中名字的歧义（mcpp；mcpp#991、#852）

**决定。** 全文在[子方案](2026-11-21-build-program-observed-inputs-design.md)，本节只陈述它在本轮中的位置。

- 构建程序的输入分为预测、编译读取、运行读取三类；编译读取取自子构建对程序单元的依赖记录（GNU 的扫描 depfile，
  MSVC 的 `sourceDependencies`），写入 `programs.json`，进入程序的身份。工程的快速路径、编译闸门与运行缓存读取这同一份
  记录。它与 5.3 是同一条原则：能观测的输入以观测为准。
- 包含标准库头文件与包含本包头文件两种用法在文档中标为不推荐并给出推荐的写法；一个工程第一次构建时各提示一次，
  `mcpp clean` 之后重新提示。
- 读取包外文件在本地构建中警告一次，在 `mcpp publish` 中拒绝（原因标记 `build-program-unpublished-input`）。
- 提示有一个汇点（`mcpp.diag`）与一张登记表（新包 `modules/notice`）；策略为 `always`（缺省）与 `once`（一个工程每个键
  一次，记在 `target/.mcpp-notices`）；直接的 `ui::warning` 与三处各自的「只说一次」并入汇点。
- 构建程序契约中的名字按发布的变量判定歧义（#852 的根因：按拼写判定，而变量由拼写有损地变换得到）；依赖的目录、
  链接形式、工具与载荷四个通道共用一个分组函数，有歧义的变量不发布，读取者拒绝并说出可用的拼写，构建时不再警告。

**验收。** 子方案第 6 节的 T1 至 T10 与 U1 至 U3；#991 的复现在 Linux、macOS 与 Windows 上给出新值；#852 的两种情形
（共有的末段，变换后相同的名字）构建时都不警告，询问时都被拒绝。

### 5.24 离线、宿主输入与工具链的缺省（xlings、xim-pkgindex、mcpp；mcpp#988、#989、#990）

**决定。** 全文在[第二个子方案](2026-11-21-offline-host-inputs-and-toolchain-defaults-design.md)，本节只陈述它在本轮中的位置。

- xlings 以 sha256 从有序的来源列表取归档（本地目录在网络之前），并能把一组包连同索引快照导出为目录、从目录安装；mcpp 以 `mcpp fetch`
  （`--to`、`--from`）把一个项目所需之物导出与导入，离线是工程与机器两层都可写的 `[build] offline`。
- 宿主输入逐类显式开启（新增 `[build] allow_host_tools`），身份进入缓存键与锁，每一类在一个工程中提示一次；引导工具按需检查。
- 工具链的请求只有一个解析函数，写明的请求进入锁；配套载荷的版本取自工具链的声明而非目录的顺序，并可以覆盖；编译器的版本由驱动的
  机器可读查询给出，三元组的 vendor 段为任意词。
- 缺省是数据，取上游最新的正式发布并经 CI 验证；本轮刷新 gcc、llvm、binutils、linux-headers、patchelf 与 ninja 的缺省。
- 命令行的 `@<版本>` 是按书写精度的前缀，`@=<版本>` 是精确的键；清单的版本字符串仍是要求文法。
- 以 `dlopen` 加载的库的可达性按发起加载的对象判定（带 `DT_RUNPATH` 的对象看不到可执行文件的 `DT_RPATH`），不可达时报告并指出须声明的运行依赖。

**验收。** 第二个子方案第 6 节的 X1 至 P1；mcpp 自身在无网络的命名空间中由 bundle 构建。

## 6. mcpp 的构建与测试即规模基准

基准不另设工作量。每次 CI 已经构建 mcpp（830 条边）并构建、运行它的全部测试；5.6 与 5.9 使这两件事留下记录。

| 类别 | 内容 | 判定 |
|---|---|---|
| 不变量（每个拉取请求，小工程的 e2e，带指标与界限） | 无改动的重建运行 0 条编译边；`build` 之后的 `test` 只编译新增的单元（#986）；同一 home 的第二个工程编译 0 个平台单元（5.2）；新检出在已填充的缓存上运行 0 个编译器（5.3）；dev 依赖由缓存提供（5.4） | 超出界限即失败 |
| 规模记录（每次全量运行） | 自建：边数、运行的边数、编译器的处理器时间、最大驻留集、最慢的边；测试构建：同上；测试运行：处理器时间、每个用例的开销；一次无事可做的 mcpp 调用的用时（e2e 调用它成千上万次） | 趋势；拉取请求与同类机器的中位数比较，写入摘要，不判定 |
| 引擎对照（`bench/`，手动） | 不变 | 不变 |

第一类中的每一项对应本文的一个缺陷：它们在引入时都没有测试能察觉。

## 7. CI 的形态与实现

### 7.1 形态

| 阶段 | 现在 | 本文之后 |
|---|---|---|
| 触发与档位 | 拉取请求与 main 的推送各运行全部作业；`pr` 与 `full` 只改变 e2e 的集合与一个 macOS 镜像的子集 | 拉取请求的推送运行 `pr` 档，检查点（`ci:full`）运行 `full` 档；main 的推送在树已有标记时不运行测试（5.22） |
| 被测程序的构建 | 每个宿主一次，从零；宿主构建 | 每个宿主一次，单元由缓存提供（5.3）；发布的形态（5.22） |
| 其他工具链与目标的自举构建 | 各自从零（3.5），每次运行 | 只在 `full` 档；各自的配置在缓存中命中 |
| 测试的构建 | 一次；main 的构建目录按修改时间复用（W1） | 一次；按内容命中（5.3） |
| 分片 | 固定四片，按宿主的历史分配 | 片数来自作业的预算（5.17），按机器类别的历史分配（5.9）；一份预算（5.5） |

## 10. 风险与未采纳

- **5.3 的正确性取决于键的完备。** 遗漏一个输入会提供错误的目标文件。清单取自编译器自己的依赖记录；逐字节的核对是
  验收的一部分；不可复现的工具链不缓存。
- **5.5 改变每一次嵌套构建的并行度。** 单独运行的构建不受影响（没有父 generation）。
- **5.10 把 home 的内容变成声明。** 现有用例中隐含依赖共享 home 里某个包的，会在迁移时暴露；逐个改为声明。
- **5.12 的接口改动**不改变已发布名字的含义（SPEC-017 的「只增不改」针对协议；库的源码兼容性另由 mtest 的版本规则约束）。
- **5.22 之下次要作业的问题到检查点才暴露。** 需要提前看到时加 `ci:full`；验证之后 main 又移动的情形与今天相同。
- **5.18 使现有用例中未声明的诊断行成为失败。** 其数目未知，在实施中先以报告模式测得。
- **5.15 改变依赖的缺省调试程度。** 调试进依赖的代码时需要在 profile 中覆盖；缓存中依赖的条目重建一次。
- **未采纳：以 GNU make 的 jobserver 作为预算的形式。** 它需要命名管道，`mcpplibs.os` 没有；槽位文件以已有的文件锁实现。
- **未采纳：在 Linux 上交叉构建各平台的测试、到各平台只运行。** macOS 的原生目标与 MSVC 不能从 Linux 交叉；macOS 的
  瓶颈是 runner 的排队（2026-11-14 记录）。
- **未采纳：更大的 runner。** 2026-11-15 已定。
- **未采纳：以 boost-m 作为规模基准。** 规模基准是 mcpp 自己的构建与测试（第 6 节）。

### 14.3 与第 5 至 12 节的差别

1. **M6、M7、M9 的位置。** 预算的客户在 `src/build/schedule/detach_codegen.cppm` 与 `src/home/files.*`，运行器的记录与
   夹具在 `src/build/execute.cppm` 与新的 `src/build/test_fixture.cppm`，没有成为 `modules/budget`、`modules/test-run`：
   它们接入运行器的工作循环及其类型（`TestRunnable`、分片、`TestResult`），这些类型位于 `execute.cppm`；运行器移出
   `src/` 是一次单独的移动。新包为 `modules/build-record`、`modules/unit-cache`、`modules/surface`。
2. **K1 的用到的项来自 mcpp 自身。** kit 不解析命令行：解析器知道一个选项属于哪个命令，kit 重新实现它会与之分歧。
   `MCPP_SURFACE_RECORD` 命名一个文件，调用的每个进程追加它用到的命令、选项、键与原因（每项每进程一次）；kit 读取后
   写出 `exercise`。
3. **M13 的记录来自构建目录。** 头文件的读者取自 ninja 的依赖日志（格式 4）与扫描的 `.ddi.dep`，而不是单元缓存的清单：
   清单只存在于缓存保留的编译（cl.exe 的编译与没有缓存的 mcpp 没有），构建目录记录它构建的每个单元。工程的某个单元
   没有记录时，头文件影响全部测试，并说明原因。
4. **K5 以报告的策略声明。** 诊断行按 `warning:`、`error:` 两个模式以 `report` 策略声明，运行给出各用例的数目，不逐个用例
   声明。
5. **K2 与上游的链接条目。** 继承的 home 以 `[xlings] upstream` 指向共享 home 与用户的 `~/.xlings`，不再链接载荷、不复制
   subos。实施中发现：上游的版本目录在下游是指向所有者载荷的链接，配方的 `config()` 钩子经由它写入了所有者的文件——
   用户 home 中 GCC 的 specs 与 binutils 的 `ld` 包装被写入了临时 home 的路径（#293 的机制）。已就地修复，并在配方中
   修正：链接条目走借用的分支，`ld` 包装跳过链接条目（xim-pkgindex #1211）。此后 914 检查共享 home 在一次构建后没有
   文件被写入。修正只在索引含有它时生效：用例的 home 链接用户 home 的索引，本地的索引停在 #1211 之前时再次写穿；
   CI 恢复的沙箱同样带着保存时的索引，因此使用本提交 mcpp 的每个作业先运行 `mcpp index update`（`use-built-mcpp`）。
6. **CI6。** home 夹具的恢复即 `bootstrap-mcpp` 的沙箱缓存，其键（`mcpp.toml`、`.xlings.json`）就是夹具的身份；不另设
   缓存。
7. **CI2 的档位。** 发布形态只在 `full` 档构建（`release-build.yml`，与 `release.yml` 同一组作业），Linux 的单元与 C++ e2e
   分片测试 Linux 归档中的程序；`pr` 档测试宿主构建。发布形态是又一次自举构建，`pr` 档的目的是时间。macOS、Windows
   与 aarch64 的归档由各自的冒烟步骤核对，与发布相同。
8. **P10.4。** 不实现：工作线程在同一进程中运行测试程序，系统对子进程的计量按进程汇总，一个程序的用量无法分离
   （SPEC-017 写明）。
9. **CI10。** 按 7.3，在固定版本移动到含 5.3 的版本之后。
10. **K7 的两份表。** `coverage-exceptions.tsv`、`coverage-debt.tsv` 与 `host-requirements.tsv` 仍由
    `check_e2e_coverage.py` 判定，没有迁入 `[ci.coverage]`：它的 `job`（工作流按名字运行一个测试并自行断言其结果）与
    `unaffected`（`pr` 集合按变更略去的测试）两种判定在 `mtest ci coverage` 中没有对应，迁入会使这两类测试成为未覆盖。
    新的账本是面的账本（`[ledger.surface]`）。
11. **构建记录的 `staged`。** 1122 在实施中失败：缓存提供的包的单元由 `stage_file` 边复制，构建记录把这些边与编译
    一同列出，第二个工程看起来编译了 mtest 的 13 个输出。记录为这类边增加 `staged`（SPEC-017 B4），它与单元缓存的
    `served` 一样不是编译。余下的一个编译是 mtest 的入口单元：包的入口单元随链接它的映像编译，不取自缓存中包的条目，
    1122 的界限为 1。
12. **第一次 CI 检查点的发现（运行 44823760291，`pr` 档）。** Linux 的单元分片有 49 个失败，各有成因，均在本拉取请求中修正：
    - **嵌套运行的死锁。** 另一个运行器的预算之内（用例中的 `mcpp test`），第一个工作者以持有的槽位运行全部测试，其余
      工作者等待永远不空出的槽位，嵌套的运行到 600 s 被结束；十余个用例与 macOS 的作业（90 min 被取消）因此失败，
      其余用例在只剩一个编译器的分片中变慢（`sets` 用尽 30 min）。等待槽位的工作者在测试已被取完时退出。
    - **单元缓存与 Clang。** Clang 经搜索路径找到导入的 BMI，其依赖文件不列出它：导入者的条目只记录源文件，修改的
      模块之后，导入者由缓存提供旧的目标文件（118 输出 41；Windows 的 1111、1112、1114；1113 的编译器崩溃）。
      Clang 的编译得到 `-fmodule-file-deps`（`BmiTraits::moduleFileDepsFlag`），依赖文件列出它读取的 BMI；单元的读取
      在编译器写出依赖文件之后读取，不列出任何文件的单元不保留。
    - **打包的一遍。** 打包提供者的输出取决于打包请求与成员的暂存树，不在其键中；在 home 中运行时两个工程读到彼此的
      归档（868）。打包的一遍中构建程序在工程中运行（SPEC-004 §9 第 18 项）。
    - **继承的 home。** 不再复制 subos、不再链接载荷之后，离线或换用替身 xlings 的用例得到未初始化的环境。kit 在建立
      继承的 home 时以真实的 xlings 运行一次 `mcpp self init`（不到 1 s），由上游按链接安装 patchelf 与 ninja。
    - **其余。** `memory_threshold` 进入成员的分组键；1069 的两处等待恢复（时间前移 2 s 使下一次构建仍晚于它）；
      数个用例改读 home 中的输出目录、BMI 旁的生产者键与 gc 的单元条目。
13. **面的账本的第一次数据。** 429 项中 331 项有通过的用例。未覆盖的 98 项中：命令行在解析之前读取的全局选项
    （`--no-color`、`--frozen`、`--system`、`--protocol-version`）用到而未被记录，调用改为从原始的参数记录它们；
    没有任何用例运行的维护命令与测试选项由新用例 1125、1126 运行；1125 发现 `mcpp index list` 不列出 `mcpp index add`
    加入的注册表（按旧的载荷形式读取提供者的列表），已修正。只由脚本 e2e 用到的项（脚本不写出用到的项）在账本中
    以豁免陈述，理由指名脚本。
14. **在同一个 home 中重复运行。** 本地以一个 home 反复运行全量用例，暴露了 CI 的新 home 看不到的四类事实：
    - **条目按它编译时所读的接口提供（SPEC-001 §10.4 第 7 条）。** `mcpp cache gc` 移除上游的条目后，同一棵树在另一路径
      编译出另一份接口（GCC 的 CRC 不同），依赖它的条目仍被提供，构建以 `module 'globbing' CRC mismatch` 失败
      （build-program 311）。条目改为记录所导入接口的摘要，上游在本次构建中编译时依赖者随之编译并重写条目（cache 1133）。
    - **store 按路径判定。** 由上游 home 链接安装的 nasm 被解析到上游的目录，判为宿主的汇编器（build 105）；改为按路径。
    - **断言偶然的事实。** 断言「本次编译了某个路径依赖或工具」的用例（features 82、build 50、build-program 698）在条目
      已存在时不成立：82 改为断言包在构建中，50 与 698 使用用例自己的 home。
    - **运行一次的键按规划陈述。** `[build] offline` 与 `allow_host_tools` 没有进入成员的分组键（SPEC-004 §9 第 10 条），
      工作空间依次规划各组时沿用前一组的陈述；两键进入分组键，每个规划陈述或撤回工程层（单元测试 KeyRegistry、RunKeys）。
15. **第二次检查点的发现（运行 44897058445，`full` 档）。**
    - **等待机器之门的工作者持有预算的槽位。** 每个工作者在整个运行中持有一个槽位，等待持有 `machine` 的测试时也不交回，
      该测试的构建只得到其工作者的一个槽位：234 的编译器峰值为 1（上限 2），860 在 `-j 4` 下三次编译没有重叠。等待门的
      工作者交回槽位，取得门之后再取（SPEC-017 O11 第 5 条）；860 陈述 `machine`，它断言的并行只在预算属于它时成立。
    - **在自己的目录中规划的命令写入了工程的提示记录。** `mcpp emit build-database` 写出 `target/.mcpp-notices`，工程的
      目录树改变（emit 688、817）。这样的命令读取记录而不写入。
    - **作用域的事件不指名用例**（mtest 0.11.2）：运行器把它们归入程序的记录（Windows 的 mingw 97）。
    - **用例探测的工具链依赖缓存。** 本次改变了 xlings 的版本，沙箱缓存的血统随之改变，Linux 分片中需要 llvm 的 14 个
      用例在任何 runner 上都没有运行，其中 988 是 `toolchain/default-changed` 提示唯一的用例。分片改为显式安装用例探测的
      工具链（`ci-unit.yml` 的 `toolchains`），与脚本 e2e 的分片相同。
    - **面的账本。** 用例 1127 运行构建命令共有的选项与其他用例没有陈述的 `[build]` 键；bundle 990 在不提供网络命名空间
      的机器（Ubuntu 24.04）上以引擎的离线为界运行，`ci-offline.yml` 仍在命名空间中构建本仓库。
16. **第三次检查点的发现（运行 44910330728，`full` 档）。**
    - **新的默认工具链暴露了依赖旧载荷的事实。** gcc 16.2.0 第 1 修订版内置的 sysroot 是构建它的 home 的 `subos/current`，
      重映射只认 `subos/default`，未描述环境的链接找不到 home 的 C 库（subos 221、binding 220、flags 141）；提供者把两者都
      视为构建它的 home 的环境。以路径指名的 GCC 使用自己找到的汇编器（mcpp#755），而 store 中 gcc 的 binutils 是单独的
      载荷，gcc 16.2.0 输出的指令宿主的 binutils 2.42 不能汇编，用例陈述汇编器（bases 925）。替身 xlings 的配置写死旧的
      默认工具链（local 60），改为沿用 home 已有的默认。
    - **升级通道。** 升级后的第一次运行安装本次提交钉住的引导工具（ninja、patchelf），通道从内建表的默认行读取它们；依赖的
      BMI 暂存目录的拼写在 2026.11.21.1 改变（mcpp#986），通道接受两种拼写。
    - **冷缓存下用例的时间。** 分片安装 llvm 之后，955 第一次在 Linux 上运行（此前在任何 runner 上跳过）：第一次打包为两种
      架构构建 openkal 集合，超过命令的十分钟。无 Visual Studio 的 Windows 上，182 在用例自己的 home 中安装 GNU 行的工具链：
      缓存热时 54 s，xlings 版本改变使缓存冷时超过五分钟。两个用例按测量陈述各自的时间（30 分钟、15 分钟）。
    - **860 在 macOS 上。** 三个处理器的 runner 上三次编译没有全部重叠（macos-15 与 xcode-27 均出现过，不是每次）。临时
      探测排除了内存阈值：三个、六个编译器运行时两种镜像上的可用内存为 2.9–3.5 GB，远高于 1 GiB。图的全部步骤（失败时
      报告）表明原因在扫描：每次编译等待其单元自己的扫描，同一文件的三次扫描在图开始后 1.9、3.5、7.7 s 结束，第一次编译
      在第三次开始前已经结束，而其间有两次同时进行。调度保证的是多于一次编译同时进行，而不是三次同时；用例在 `-j 4`
      下断言同时进行的编译至少两次，在 `-j 1` 下恰为一次。
    - **两处推导的 `-B`。** 以路径指名的 GCC 陈述 `tools.as` 后，`std` 模块的编译指向该汇编器，普通编译与链接仍由归档
      工具所在的目录推导；这样的 GCC 驱动旁没有归档工具，于是没有 `-B`，驱动从 PATH 运行宿主的 `as`（bases 925 在 CI
      上失败）。编译与链接改为取
      `gcc::binutils_prefix_dir` 的同一个答案。
    - **选中用例的时限。** 182 陈述的时限没有生效：程序的列表只列出顶层的用例，选中其下的用例时，运行器的时限是被列出
      者陈述的（SPEC-017 O5）。时限改由套件陈述。
    - **面的账本：用到而未记录。** 门禁列出 29 项没有通过的用例。其中数项已被用例运行而没有记录：kit 只为 `mcpp()`
      运行的命令设置记录文件，以会话、在另一程序之下（`unshare -rn`）或由用例自行运行的命令不写出。kit 改为为它组成的
      每条命令设置记录，`mcpp()` 在命令结束时陈述，其余在用例结束时（mtest 的 `at_case_end`）陈述；`options::wrap`
      使在另一程序之下运行的命令经由 kit（bundle 990、homes 919）。
    - **面的账本：没有用例。** 新用例 1134 至 1140 与已有用例中的步骤覆盖 17 项：加速器的测试与数据库、平台的链接
      驱动与封装工具及其 `tools`、平台阶段的指令、平台依赖、C 库声明的测量、伴随的 binutils、另一系统的工具链、链接的
      伴随文件、`fetch --package`、模块图的全量核对、上限与信号量。豁免六项，各陈述理由：只由脚本运行的 `--system`；
      没有输入能到达的 `ambiguous-request` 与 `layer-ordering`；只在 Windows 上到达的两个原因；需要自备载体包的
      `carrier`。
    - **一个答案的两处写法。** `why` 的两种 JSON 对没有记号的拒绝分别报告 `other` 与 `none`；改由拒绝记录的一个函数
      给出（`take_refused`），`other` 同时记入面的记录。拒绝 `system`、工具链命令的参数错误、`self config` 与
      `doctor` 的提示写死 gcc 16.1.0；改为读取内建表中本机的首次运行，`doctor` 的提示改为
      `mcpp toolchain install --target <triple>`。
17. **发布之后：命令的时限与 `pr` 档的门禁（运行 44937152470，`pr` 档的两个分片）。** `sets/985` 为每个系统打包的一步在第 10 分钟被
    结束，所在套件陈述 45 分钟而远未用尽；同一分片的 `sets`、`images`、`stack` 同时运行，`sets` 用时 2140 s，三个分片
    的运行中为 1162 s。原因是 5.8 的一项没有实现：mtest 0.11.1 使命令不超过用例余下的时间，kit 却仍以十分钟为每条命令
    的缺省，两者取小。此前 1033 与 955 各自把一条命令提高到 30 分钟，是同一缺口的两次绕行。kit 改为：命令不陈述时限时取
    用例余下的时间（`time_left()`），没有任何作用域陈述时限时取十分钟；两处提高删除，`images` 按测量陈述套件的时间
    （30 分钟；两个分片中 1102 s，三个分片中 707 s，运行的缺省为 1200 s）。
    同一运行的门禁另有一项与改动无关的失败：面的账本列出 14 项没有通过的用例，均只由 `full` 档的作业或用例用到（Windows
    的 `coff-def`、构建图内部调用的 `dyndep --split-module` 与 `link-output --aside`、只在某些行上到达的原因标记）。需求
    由运行组中通过的用例满足，`pr` 档只运行改动影响的作业与用例，于是每次 `pr` 运行的门禁都失败。账本是全部用例的性质，
    改由运行全部用例的集合判定：mtest 0.11.3 的门禁只在这样的集合中判定账本，其他集合判定失败与预算并注明未判定账本；
    `ci.yml` 以运行的集合调用门禁（`gate --set`）。新增面的项的拉取请求以 `ci:full` 确认它有通过的用例（贡献规程）。
18. **发布之后：单元分片的数目（main 的运行 44945453323，`full` 档的两个分片）。** 单元分片的数目此前取 main 上一次
    运行中各程序用时之和，除以一个分片的四个工作进程在 30 分钟内的工作量。三个分片的运行 44930053323（三个分片分别用时
    1236、834、1438 s）由此得出两个分片；两个分片分别用时 2544 与 2432 s，`trees` 用尽它陈述的 40 分钟（三个分片中为
    1369 s），`sets`、`images`、`stack` 在同一分片中同时运行；本拉取请求的 `pr` 运行同为两个分片，用时 2099 与
    1429 s，`trees` 为 1981 s，两次之差在 runner 的处理器之间（5.9）。用时之和除以工作进程数，假定四个工作进程始终各有程序
    可运行，且程序的用时不随同时运行的程序变化；openkal 的程序在机器的一份预算中并行构建，分片越少，同时运行的越多，
    各自越慢，一个分片的时间由其中最长的程序与同时运行的程序决定。分片数改为取 main 上一次运行的分片数 N 与其中最长
    分片的用时 W，N × W 按每片 30 分钟折算（`ci-unit.yml`；两次运行都得出三个分片）。套件陈述的时间不变：它们界定
    挂起，在三个分片中留有余量。
