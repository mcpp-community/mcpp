## 1. 目的

2026-11-10 方案回答了"能力够不够"。它落地后的一轮实施（mcpp#924 与外围九个 PR）暴露的是另一类问题：能力在增加，
但**同一类缺陷重复出现**——数据驱动的陈述与引擎里新增的系统名并存，本地通过而 CI 与新装用户路径不通过，资产修订两次
违反同一条布局约定。本文不再逐项补能力，而是回答三个问题：

1. 哪些结构使这些缺陷可以重复发生，改哪里能让它们**机械地不可能**（第 3–5 节）。
2. 已合入与在途的改动里，哪些不合理，各自怎样纠正（第 6 节）。负责人对三个生态都有决定权，所以已合入项可以用追加 PR
   纠正；纠正仍然先在本文定稿。
3. 以验证工程为尺，通用基础设施要到什么程度才算"支持一个程序去到所有平台"，包括 32 位与 16 位 DOS 的可能性；这些设施
   对验证工程之外的领域有什么收益（第 7–9 节）。

## 3. 诊断：六个结构性原因

审计发现的三十余个问题归为六个原因。每个原因对应第 4 节的一条原则与第 5 节的一处结构。

| # | 原因 | 表现 |
|---|---|---|
| R1 | **行是数据，读行的代码不是。** 行与提供者进了表，但"某个系统的载体以哪个身份构建""某个系统在 `uname` 里叫什么""宿主的系统是哪个"这类**系统级事实**没有表，于是每个消费点各写一个分支 | `pack.cppm` 的 `system == "freebsd"`；`polyglot` 的系统白名单；`execute.cppm` 的三元式；`windows_resources.cpp` 拼 `{arch}-windows-gnu`；`registry.cppm` 拼 `linux-{arch}` |
| R2 | **一条提供者条目承载两种载荷安排。** 原生与交叉写在同一条目上，行为随宿主分叉，"写出宿主自己的目标不改变任何东西"这一不变量随之失效 | e2e 295；默认身份漂移 |
| R3 | **链接模型没有单一求值点。** "C 库由谁供给"在五处用 `base.layers.cAbi.empty()` 重新推断，基座的两种布局走两条通道，其中一条不读折叠后的加载器 | 交叉产物烙入构建机路径；GCC 分支被顺手改坏 |
| R4 | **陈述先于门禁。** "已测""默认行为不变"写进了 PR 正文与设计记录，对应的门禁不存在、被跳过或是红的 | 1076 跳过即通过；三平面文档第 3 节；交接清单 |
| R5 | **资产准入只校验字节，不校验可用。** 修订通道核对摘要与平台齐全，不核对归档布局、清单内容与"装上之后能不能用" | llvm 修订 2；sysroot 修订 2 的三处缺陷 |
| R6 | **运行器仍是文档而不是数据。** 行表里没有"这个身份在这台主机上怎样启动"的条目，每个系统各有一份胶水 | FreeBSD 的手写路径；诊断里对 FreeBSD 产物建议 `qemu-aarch64-static`；三份虚拟机驱动 |

## 4. 原则

2026-11-10 方案的 P1–P9 全部保留。新增六条，各自针对一个原因。

- **P10 系统级事实也是数据（R1）。** 凡是按系统名分支的地方，分支的条件上移为系统表的一个键。验收是机械的：引擎源码里
  系统名的出现次数由一个 CI 检查持有，只许减少（第 5.2 节）。
- **P11 一条提供者条目只陈述一种载荷安排（R2）。** 原生与交叉是两条条目，各有自己的 `hosts`、`sysroot`、`linkage`
  与优先级。推论：一个身份在其原生主机上，写与不写 `--target` 得到同一条链接行。
- **P12 只写 `<arch>-<os>` 的请求，其回答是契约（R2）。** 新增提供者不得改变任何主机上既有请求的回答。新的提供者以
  低于现有回答的优先级进入；要改变缺省，是一次单独的、写进 CHANGELOG 的决定。这与 2026-11-10 的 Q3（默认 B 路线）一致。
- **P13 链接模型求值一次，渲染不再推断（R3）。** "谁供给 C 库、sysroot 在哪、加载器写成什么、哪些目录进 RUNPATH"
  在 prepare 里求成一个值；`flags.cppm` 只渲染这个值，不再读行、提供者或基座。
- **P14 陈述引用门禁（R4）。** 设计记录与 PR 正文里的"已测"必须指向一个在 CI 里运行的检查；本地测量写作"本地测得"，
  并写明主机与载荷布局。跳过不是通过：跳过的脚本以跳过报告，覆盖检查把"无处运行"当作失败。
- **P16 归属判据。** 一个事实放在哪里，依次问四句，第一个回答"否"的地方就是它的归属：

  | 问 | 回答"否"时归属 |
  |---|---|
  | 换一个程序，它还成立吗 | 程序自己的仓库（数据结构的大小、平台层的选择、进程与终端的语义） |
  | 换一块板、一个固件、一个客体镜像，它还成立吗 | 板级包（平台包）或镜像资产附带的描述（链接脚本、设备地址、模拟器参数、退出约定、客体的包装） |
  | 换一个系统，它还成立吗 | 行、系统表、提供者——主流系统在内置数据，长尾系统在平台包 |
  | 都成立 | 引擎的机制，或 openkal 的规范 |

  这是 docs/40 已有的一句话（"位置是目标事实，选择是板级事实"）向两端的延伸。

- **P15 新系统的准入以"引擎零改动"为验收（R1、R6）。** 一个新系统由数据（行、系统表条目、提供者）、包（实现、基座、
  平台、运行器、镜像）与门禁（一致性、金丝雀）组成。准入需要改引擎，说明缺的是一个通用机制，先补机制，再以该系统验收。

- **P17 一个事实只有一个实现。** 引擎里同一个问题有两处回答时，收敛为一处，另一处改为读它。这次实施中遇到的重复
  按 5.13 的清单逐项收敛；收敛不改变行为，由收敛前后的同一组测试证明。

## 5. 目标架构

### 5.1 四个平面与一张系统表

三平面记录把验证写成"归一化层"。本文把它升为第四个平面，因为 R4 与 R5 都出在这里。

```
 ┌──────────────────────────── 程序（语义面：进程模型、终端、路径写法，属于程序自己） ────────────────────────────┐
 │                                                                                                              │
 │  ① 身份面        ② 载荷面              ③ 运行面                 ④ 验证面                                     │
 │  行 + 提供者      工具链 + 基座包        运行器描述 + 运行器包      金丝雀 × 矩阵 × 准入门禁                     │
 │  + 系统表         + 平台包 + 实现        + 镜像资产                                                            │
 │  （mcpp 内置数据   （xim-pkgindex、       （内置数据 / 平台包 /      （mcpp CI、xim CI、                         │
 │   与平台包）       mcpp-index）           xim 资产 / dirun）         openkal-conformance）                      │
 └──────────────────────────────────────────────────────────────────────────────────────────────────────────────┘
      机制在 mcpp 引擎：选择规则 · 层的合并 · 链接模型 · 运行器协议 · 打包 · 修订通道的客户端
```

| 平面 | 持有的数据 | 所在 | 不变量 | 门禁 |
|---|---|---|---|---|
| ① 身份 | 行、提供者、**系统表** | `builtin.toml`、平台包 | 目标差异全在数据（P10）；一条条目一种安排（P11）；请求的回答稳定（P12） | 行表快照；e2e 295、299；系统名检查 |
| ② 载荷 | 工具链、基座包、平台包、openkal 实现 | xim-pkgindex、mcpp-index | 构建主机只需要 mcpp；基座供给 C 库时宿主链接模型整体让位（P13） | 基座准入契约；修订通道的安装检查 |
| ③ 运行 | 运行器描述、运行器包、磁盘镜像 | 内置数据、平台包、xim | 构建不依赖运行器；每个身份在每台主机上要么能启动，要么指名缺哪个运行器 | 运行矩阵 |
| ④ 验证 | 金丝雀工程、目标矩阵、期望输出 | mcpp 仓库、各仓 CI | 陈述引用门禁（P14） | 覆盖检查；夜间矩阵报告 |

### 5.2 系统级事实：先用已有的行键，系统表只补缺的一项

**问题。** 行回答身份级的问题。系统级的问题今天由代码回答。

**已有而未被消费的键〔读〕。** SPEC-016 §2.1 的行字段已经包括 `loader`、`execution`、`family`、`exe-suffix`、
`object-format`。内置数据只在 FreeBSD 四行上写了 `family`，其余键没有值，于是代码里各有一张自己的表。所以这里的
工作首先是**给已有的键填数据并让代码读它**，而不是新增 schema。

**新增的只有两处。**

```toml
[[platform.system]]             # 系统表：一个系统一条，内置数据与平台包同一 schema
name  = "freebsd"
uname = "FreeBSD"               # 多系统单文件的 POSIX 头里识别该系统的词；没有该键的系统不进这种文件

[[platform.provider]]
name           = "openkal"
serves         = ["x86_64-windows-musl"]
system-headers = "xim:mingw-w64-sysroot@20261104-2"   # 系统自身接口的头文件由谁给；只有资源编译等需要它的步骤读
```

"某个系统上自带运行器以哪个身份构建"不进系统表：它只对带运行器与载体的平台有意义，按 P16 属于那个平台。平台的
`runner` 陈述里 `hosts` 的每一项可以带它的身份（`{ host = "freebsd-x86_64", built-as = "x86_64-freebsd-musl" }`），
由 openkal-platform 写出。

**每个硬编码点的去向。**

| 现在的代码 | 改为读 |
|---|---|
| `pack.cppm` 对 linux、macos、windows、freebsd 各一个分支 | 平台 `runner.hosts` 各项的 `built-as` |
| `polyglot.cppm` 的系统白名单与 `uname` 词 | 系统表的 `uname`；没有该键的系统被拒绝并指名 |
| `execute.cppm` 把宿主映射成三个系统名之一（`unreachable_execution` 里原有一处，mcpp#924 又加一处） | 宿主身份所在行的 `execution`（缺省为 os 段）与目标行的比较 |
| `windows_resources.cpp` 拼 `{arch}-windows-gnu` 再找服务它的提供者 | 选中提供者的 `system-headers` |
| `registry.cppm::host_can_serve` 拼 `linux-{arch}`，musl 另有 `x86_64` 特例 | 只调用 `available_on(提供者, 宿主)`；该函数里不再有架构或系统判断 |
| `linkmodel.cppm::distro_loader_path` 按三元组前缀返回 `/lib64` 或 `/lib` | 行的 `loader`（已有键，补数据） |
| 运行器建议文字里的字面量 `qemu-aarch64-static`（三处） | 5.5 的运行器陈述；没有陈述时只写声明的形状，不写示例程序 |

**机械门禁。** 新增检查脚本，统计 `src/` 与 `modules/`（除 `modules/platform/` 与数据文件）里系统名词表的出现次数，
与仓库里的基线文件比较：多于基线则失败，少于基线则要求更新基线。P10 由此从评审意见变成检查。

**第二个使用者。** 任何平台包定义的系统（长尾系统、DOS、UEFI）自动得到多系统单文件与"已构建，未运行"的回答，不需要
引擎改动。

### 5.3 提供者：拆分、优先级与等级

**拆分（P11）。** `aarch64-linux-gnu` 的两种安排写成两条：

```toml
[[platform.provider]]          # 原生：宿主的载荷
name      = "glibc"
serves    = ["aarch64-linux-gnu"]
priority  = 100
hosts     = ["linux-{arch}"]
toolchain = "llvm@23.1.3"

[[platform.provider]]          # 交叉：基座包
name      = "glibc-sysroot"
serves    = ["aarch64-linux-gnu"]
priority  = 40                 # 低于 musl-gcc 的 100 与 openkal 的 50（P12）
hosts     = ["linux-x86_64"]   # 归档与宿主无关，范围随验证扩大
toolchain = "llvm@23.1.3"
sysroot   = "xim:aarch64-linux-gnu-sysroot@2.44.3"
linkage   = "dynamic"
```

这是 `mingw`（10）与 `mingw-llvm`（5）已有的写法。结果：aarch64 主机上两种拼写仍取原生条目（e2e 295 恢复）；x86_64 主机
上 `aarch64-linux` 仍回答 musl，`aarch64-linux-gnu` 写全才取交叉条目。

**等级随条目（建议）。** `tier` 现在在行上。同一身份的原生安排是 preview、交叉安排尚无门禁时，行的等级说不清是哪一个。
提供者条目可以带自己的 `tier`，缺省继承行；`mcpp toolchain list` 显示选中条目的等级。

### 5.4 链接模型：一次求值

**设计。** prepare 的末尾得到一个值，此后只有它被读取：

```
LinkModel
  c_library   : host-payload | base-package | graph | sdk      谁供给 C 库
  sysroot     : path?                                          base-package：包根
  search      : { crt: [path], lib: [path] }                   -B 与 -L
  loader      : { file: path, name: path }                     链接时用到的文件；写进产物的名字
  runpath     : [path]                                         只含产物运行时确实存在的目录
  runtime     : { rtlib, unwind, cxx, resource_dir }
```

**规则。**

1. `c_library` 的四个值两两互斥，由选中的提供者条目与依赖图决定；`flags.cppm` 里的五处推断删除。
2. **加载器的名字与文件分开。** 产物在本机运行的安排（原生的宿主载荷）：`name = file`，即今天的密封行为，不变。产物不在
   本机运行的安排（交叉、另一系统）：`name` 取行的 `loader`（SPEC-016 已有的键），`runpath` 为空。构建机的安装路径不进入
   这类产物。
3. 运行器拿到 sysroot：运行器模板增加 `{sysroot}` 占位，交叉 glibc 产物的缺省运行器是 `qemu-<arch> -L {sysroot} {}`。
4. 基座包只有一种读法。"包根即 sysroot"与"生态自己的 glibc 包布局"今天走两条通道；基座包的清单是它的陈述，带清单的
   一律按包根 sysroot 处理，布局探测只用于没有清单的目录。

**门禁：链接行的金样。** 渲染是纯函数，所以不需要工具链就能测：对 `编译器族 × c_library × 链接形态 × 原生/交叉` 的每个
组合保存一份期望的链接词表，作为单元测试。这次 GCC 分支的回归（gcc 15.1.0 的 `-B`、`-L`、加载器整组消失）在这种测试下
是一行差异。CI 另加一条 gcc `PayloadFirst` 的真实构建腿。

### 5.5 运行面：运行器是提供者的陈述

**已有的机制〔读〕。** 运行器今天可以写在四处：平台的 `runner = { cmd, host, hosts }`、`[platform.runners]` 的具名
运行器、项目与本机配置的 `[target.<sel>] runner`、作为目标工具的运行器包（`[target.<sel>.tools]`，docs/41 的运行协议）。
SPEC-016 §6 已经规定：行的 `execution` 不是本机系统、又没有运行器时，报告"已构建，未运行"。缺的只有一处：**内置提供者
不能陈述运行器**，于是 wine、qemu-user、虚拟机这些缺省安排没有数据可写。

**设计。** 不新增表。提供者条目可以带 `runner`，形状与平台的相同，外加它依赖的包：

```toml
[[platform.provider]]
name     = "openkal"
serves   = ["*-freebsd-musl"]
runner   = { cmd = ["dirun", "--profile", "{pkg:freebsd-disk-image}/dirun.toml", "--", "{}"], hosts = ["linux-*", "macos-*"],
             requires = ["xim:dirun", "xim:freebsd-disk-image@14.5", "xim:qemu-system"] }
```

**规则。**

1. 优先级沿用 P8：项目 `[target.<sel>] runner` 先于本机配置，先于平台，先于提供者。
2. `requires` 里的包在第一次 `mcpp run` 或 `mcpp test` 需要时按工具链同样的同意方式安装；构建从不安装它们。
3. 模板的占位：`{}` 是产物，`{sysroot}` 是该安排的基座，`{pkg:<name>}` 是 `requires` 中该名字的包的根（一个模板可以
   用到两个包——镜像与固件——所以占位按名字，而不是一个 `{image}`）。模板的程序先在 `requires` 的包里找，再找 PATH。
4. **不运行另一系统的程序来观察它。** 内置行与平台定义的行由同一个谓词判断：行的执行系统不是本机、又没有运行器，就在启动
   之前回答"已构建，未运行"，指名身份与可写的声明。另一系统的系统调用号在本机内核上指向别的操作，启动它的后果不确定
   （第 14 节第 2 条）。诊断的文字由数据生成，只有一处。

**运行器的五种来历**（是分类，不是 schema 里的键）：

| 来历 | 含义 | 实例 | 取状态的方式 |
|---|---|---|---|
| 用户态模拟 | 同内核、异架构 | `qemu-<arch> -L {sysroot}` | 进程的退出码 |
| 接口的宿主实现 | 另一系统的接口在本机的实现 | wine；DOSBox（探针 P2：0.33 秒，退出码如实） | 进程的退出码，或客体包装写出的状态 |
| 映像的加载器 | — | okrun、node | 进程的退出码 |
| 板 | 产物本身就是模拟的机器启动的东西 | qemu 加固件（探针 P5：OVMF 下 2 秒） | 板级包约定的出口（5.12） |
| 客体 | 启动目标系统，在里面运行产物 | dirun 加磁盘镜像 | 标记协议 |

"客体"只有一个实现：dirun。openkal-freebsd 的 `vm-run.py` 在 dirun 等价后退役。

**xim 侧。** 缺的包：wine、DOSBox、OVMF（本机的 `/usr/share/OVMF` 是宿主依赖，按 P9 应是 xpkg）。命名统一为约定文档的
`<system>-disk-image`；`freebsd-vm` 与 `freebsd-disk` 保留为指向它的别名一个周期后移除。

### 5.6 载荷面：基座包的准入契约

基座包的 schema 不变（2026-11-10 方案 E5）。增加的是**准入**：一个基座包进入索引之前，由索引仓库的 CI 用已发布的 mcpp
对它跑一组固定探针。

| 编号 | 探针 | 这次会拦下的缺陷 |
|---|---|---|
| BP1 | 归档顶层目录等于资产文件名主干（含 `-r<N>`） | llvm 修订 2、sysroot 修订 2 |
| BP2 | 清单能被引擎解析、无未知键；`provides` 的每一层在包内有对应的文件 | `compiler-runtime=libgcc` 而实际给的是 compiler-rt |
| BP3 | C 程序：静态与动态各链接一次 | — |
| BP4 | C++ 程序（头文件）：静态与动态各链接一次 | `libc++.so` 指向缺席的 `libc++.so.1` |
| BP5 | 声明 c++-abi 的包：`import std` 的程序构建 | 没有 `std-module` |
| BP6 | 有运行器的身份：BP3–BP5 的产物运行，退出码与输出相符 | — |
| BP7 | 产物里没有构建机的路径（`PT_INTERP`、`RUNPATH`、调试信息之外的字符串） | 烙入的加载器 |

BP1、BP2 与 BP7 中仅凭安装后的目录树即可回答的部分，是索引仓库里每个基座包测试模块调用的布局契约
（`tests/lib/base_package.py`）；BP3–BP7 中需要引擎的部分是基座包专有的作业，随引擎发布之后进入。**配方自己的验证在 CI
中运行：** 改动直接编辑的配方，在安装作业的每个宿主上运行其模块的 L3 与 L4 测试（15.2）。

镜像一致性：CN 镜像滞后时客户端装到旧字节。修订通道的客户端在摘要不符时回落到另一个镜像并报告，而不是由每个 CI 作业
手工钉 GLOBAL。

### 5.7 验证面：金丝雀与矩阵

**金丝雀。** mcpp 仓库持有两个中性的小工程，它们把验证工程对生态的要求（第 7 节）写成断言：

| 工程 | 形状 | 断言 |
|---|---|---|
| `canary-c` | C89、只用 POSIX、两个程序共享源码、带资源脚本、用 `sigsetjmp`、启动子进程、读写文件 | V1–V6、V8–V10 |
| `canary-cxx` | C++23 模块、`import std`、异常、线程 | 每个声明 c++-abi 的安排 |

**矩阵是数据。** 一份表列出 `身份 × 主机 × {构建, 静态链接, 动态链接, import std, 运行, 测试, 打包, 映像}` 的期望
（通过、拒绝并给出原因词、不适用）。夜间作业对全表运行两个金丝雀，产出覆盖报告；报告是 CI 的产物。"十八个目标全部
通过"这类句子从此引用报告的运行号。

**顺序。** 不变量测试（295、299 一类）在功能测试之前运行，失败则后者不运行。能力词由 CI 作业预装满足；一个脚本要求的
能力没有任何作业提供，覆盖检查失败——这条已有，补上的是"删除豁免需要引用一次真实运行"。

### 5.8 openkal 侧

| 项 | 内容 |
|---|---|
| 环境的三类 | 2026-11-10 方案分了两类（内核 ABI 稳定、libc 才是稳定 ABI）。增加第三类：**单任务环境**（UEFI、DOS、引导链）——没有调度器，启动的程序运行到结束后启动者才继续。规范文本没有禁止这样的实现，并发相关的能力已是可不声明的属性（T9）；需要补的是一句明示与一致性套件的覆盖。它有三个使用者，先于其中任何一个的实现 |
| K7 提前 | 32 位一类目标从"设计讨论"提为正式阶段。i686 Linux、SVR4、32 位 DOS、armv7 都卡在它上面；先做 `i686-linux-musl`，因为它有 qemu-user 可以立刻验证 |
| 运行器统一 | 各实现的开发用虚拟机脚本收敛到 dirun；实现仓库只留控制台驱动词 |
| 接口声明的三方核对 | 清单的 `provides-interfaces`、`kal_interfaces()` 的回答、实际导出的名字，一致性套件核对（K1 的配套项，确认是否已全部落地） |
| 探针的跳过条件 | openkal-emscripten 的 longjmp 探针靠匹配引擎的报错文字来判断跳过；改为读引擎版本 |

### 5.9 测试体系的收敛：e2e 与 bench 归到 mtest 的 C++ 用例

**现状〔测〕。** e2e 是 762 个 bash 脚本、约 9 万行，作为 mtest 的 0 级程序运行（一个脚本一个结果）。一次 PR 运行是
72 个作业、518 作业分钟、墙钟约 45 分钟（运行 43146150459）。

| 事实 | 数值 | 含义 |
|---|---|---|
| 同一批 189 个测试，Windows 与 macOS 的耗时 | 71.0 分钟对 21.0 分钟，3.4 倍 | Windows 上 bash 的进程创建是主要开销之一 |
| Windows 的耗时分布 | 219 个测试共 79.7 分钟；耗时最长的 18 个占一半 | 先治长尾，而不是平均用力 |
| 要求 `unix-shell` 的脚本 | 154 个 | 两成的套件在 Windows 上不运行，原因是写法而不是被测行为 |
| 要求 `python3`、`jq` 的脚本 | 99、11 个 | 测试依赖宿主工具，与 P9 不符 |
| 不调用构建、运行、测试、打包的脚本 | 81 个 | 这些是解析与清单层面的断言，不需要是端到端测试 |
| Linux 的 8 个分片在这次运行里的测试时间 | 0.8、1.0、7.3、0.0 分钟…… | 分片数固定，作业的准备时间超过了它运行的测试 |
| 单元测试（168 个文件）在 Windows 上 | 构建 270 秒，运行 11 秒 | C++ 测试的成本在编译，不在运行 |

**方向。** 收敛，但不是逐个翻译。脚本按三类处理：

| 类 | 判据 | 去向 | 估计占比〔析〕 |
|---|---|---|---|
| 下沉 | 断言的是解析、清单、选择规则的回答，不需要真实工具链 | 所属模块的单元测试（`modules/<x>/tests/`），毫秒级，每个宿主都运行 | 一成到两成 |
| 合并 | 构建一个小工程再断言输出 | 按子系统合成 mtest 的 `E2E` 对象；同一对象的用例共用预热的 home 与夹具工程；原脚本名的句子成为用例名，原编号留作标签 | 七成 |
| 保留 | 断言的是机器状态：全新安装、升级、容器内无宿主工具链、模拟器 | 仍是 0 级脚本，数量由基线文件持有，只许减少 | 一成 |

**迁移的规则。** 沿用 2026-11-10 方案第 16 节：保留每一条断言，不能迁移的在 PR 中点名；每个子系统先以原脚本验证，再以新
用例验证，两次运行都引用。迁移按子系统分批，一批一个 PR。编号标签与映射表使"旧脚本的断言去了哪里"可查。

**测试支持层。** `tests/support/` 下一个小模块，建立在 `mcpplibs.mtest.e2e` 之上：声明式的夹具工程（文件表到目录树）、
`mcpp(...)` 调用（选择共用的预热 home 或全新 home）、对 `build.ninja` 的行与 JSON 文档的读取、对 ELF/PE/Mach-O 头的
读取（引擎的打包模块已有这些读取，不再调用 `readelf`、`file`、`llvm-readobj`）。失败时打印可以直接粘贴到 shell 的命令行，
保住脚本"读起来就是一次会话"的优点。

**对 mtest 的升级要求。** mtest 已有的〔读〕：集合（`smoke`、`regression`、`pr`、`full`、`release` 与自定义）、按改动选择
（`--since`、覆盖图、`file:` 产物、程序的 `sources`）、按历史分片（`--shard`）、预算（`--budget`）、资源与运行级夹具、
`skip_if`、bench 的判定策略、`gate`、`ci report` 与 `ci timeline`。需要补的：

| # | 能力 | 取代什么 |
|---|---|---|
| M1 | 能力词的探测写在 `mtest.toml`（探测命令到能力词），引擎逐机器求值；"某能力词无任何作业提供"由引擎报告 | `run_all.sh` 里的探测与白名单；`check_e2e_coverage.py` |
| M2 | 0 级程序的跳过约定（一个专用的退出码），使保留类脚本的跳过也是独立结果 | 脚本里的 `echo PASS (skipped)` |
| M3 | e2e 模块：环境、工作目录、标准输入、超时；输出匹配器；失败时的会话记录与保留的目录 | 脚本里的 `grep`、`sed`、`jq`、`tail` |
| M4 | 交互会话：对伪终端或管道的 expect/send（D23：伪终端在 `mcpplibs.os`） | dirun 的控制台模块；终端类脚本 |
| M5 | 由数据展开的参数化用例；长时间 bench 的续跑 | `bench/matrix.json` 加 `run-standard.sh` 加 `report.py` |
| M6 | `mtest ci plan`：由选择与历史给出每个宿主的作业矩阵（是否有工作、分片数、每片的预计时间） | 固定的分片数；固定的作业集合 |

M1、M2、M3 是迁移的前置；M4、M5、M6 随用到它们的批次。每项实施前先核对 mtest 的现状，已有的不重做。

**bench。** `bench/` 有两部分。引擎对比的 harness 是一个 C++ 程序，自带协议、日志、注册表与运行器，外加 `run-standard.sh`、
`harness.sh`、`report.py`；`bench/tests/engine.cpp` 已经是 mtest 的 Bench 用例。收敛为：各引擎的适配器留作夹具代码，
矩阵由 M5 展开为参数化的 Bench 用例，日志与续跑交给 mtest 的存储，"不可发布"的判定交给 `mtest gate`，报告由
`mtest report` 生成。`proto-bmi-release/` 是已结束的实验，移入结果目录。

**CI 的触发与编排**见 5.11。

**不做的。** 不为了统一而翻译"保留"类脚本；不在迁移中顺手改被测行为；不在第 10 节的 S1（纠正）完成之前开始迁移。

### 5.10 dirun 的形状

dirun 是 5.5 中 `machine` 类运行器的唯一实现，所以它的形状属于本方案。

**现状〔读〕。** 产品代码约 1,300 行，分在四个工作区成员（protocol 95 行、console 246 加 pty 212 行、runner 418 行、
testing 106 行）与根包（cli 131 行、main 57 行）；另有约 1,100 行的 Python 参考实现与它的测试；README 约 150 行。

| 问题 | 说明 |
|---|---|
| 拆得过细 | 四个包各自的清单、版本与依赖声明，服务于一千余行代码；包的边界应当对应"有第二个使用者的库"，现在没有 |
| 重新实现了生态已有的库 | `modules/testing` 对应 `mcpplibs.mtest`；`src/cli.cppm` 手写参数解析，对应 `mcpplibs.cmdline` |
| 两份实现 | Python 参考被称作"冻结的规范"，但它是第二份要维护的实现；合同应当是条款加测试 |
| "与客体系统无关"只成立一半 | 标记协议的包装（`stty -echo`、`rc=$?`、单引号转义）是 POSIX shell 的；`--machine` 到架构的映射写在代码里。客体是 DOS 或 Windows 时两者都不成立 |
| Windows 宿主 | pty 是桩。串口接到标准流时未必需要伪终端：用管道加带超时的读取，三个宿主是同一份代码〔析〕 |
| README | 定位、用法、内部机制（标记协议细节、FAT 工具的回落）、未来计划混在一处 |

**建议的形状。**

```
dirun/
  README.md        一句定位 · 三行上手 · 退出码表 · 指向 docs/ 的链接（五十行以内）
  mcpp.toml        一个包；依赖 mcpplibs.os、mcpplibs.cmdline、JSON；开发依赖 mcpplibs.mtest
  src/             main.cpp · cli.cppm（cmdline 的声明）· runner.cppm · protocol.cppm · console.cppm
  profiles/        内置的缺省客体描述（POSIX 登录式）
  tests/           mtest：单元用例 · 合同条款（cts）· 一个真实引导的 E2E（要求 qemu 能力词）
  docs/            contract.md · profiles.md
```

- **客体描述是数据。** 引导脚本、命令的包装模板、取状态的写法、转义规则、挂载文件盘的命令，合成一份描述文件，随
  `<system>-disk-image` 资产一起发布。dirun 的核心只有 expect/send、标记切分、覆盖盘与退出码。探针 T4 是一个实例：
  DOS 的命令解释器取状态的写法与 POSIX shell 不同。
- **两种方式，一份核心。** "客体"方式启动一个系统并在其中运行产物；"载荷"方式里产物本身就是被启动的东西（固件应用、
  裸机程序），状态的读法由板级包的描述给出（5.12）。两者共用串口、超时与清理。
- **控制台模块的归属。** expect/send 是通用能力，第二个使用者是 mtest 的交互会话（M4）。伪终端属于 `mcpplibs.os`，
  expect/send 属于 mtest 的 e2e 模块；dirun 依赖它们。迁出之前留在 `src/console.cppm`。
- **生态库不够用时升级生态库。** `mcpplibs.cmdline` 若缺少可重复选项或 `--` 之后原样传递，补在 cmdline 里。这条对
  生态内的每个项目成立：项目内重新实现是对库的缺陷报告没有被提交。
- **定位一句话。** dirun 在一个引导起来的磁盘镜像里运行一条命令，返回它的输出与退出码；它之于一台虚拟机，如同
  qemu-user 之于一个异架构程序。它不构建镜像、不管理虚拟机、不做配置。

### 5.11 CI 的触发模型

收敛到 mtest 之后，"这次运行跑什么"由三个轴决定，每个轴都是数据：**事件**（什么时候）、**集合**（跑哪些用例，mtest 的
集合与按改动选择）、**宿主**（在哪里跑，由 `mtest ci plan` 给出）。

**事件对集合。**

| 事件 | 集合 | bench | 宿主与作业数 |
|---|---|---|---|
| PR 的每次推送 | `pr`：改动影响到的用例，加 `smoke`、`regression`、不变量 | 不跑 | 只有选择非空的宿主；分片数随工作量 |
| PR 带标签 `ci:full`，或手动触发并选 `full` | `full` | 不跑 | 全部宿主 |
| PR 带标签 `ci:bench` | `pr` | 引擎自身开销的 Bench 用例，与 main 的基线比较 | 一台 Linux |
| 合入 main | `full`；更新存储（历史、覆盖图、bench 基线） | 引擎自身开销 | 全部宿主 |
| 夜间 | `full`、金丝雀矩阵、保留类脚本、基座准入的抽查 | 引擎自身开销的趋势 | 全部宿主 |
| 发布 | `release`：`full` 加 bench 判定（`mtest gate --set release`） | 判定 | 全部宿主 |
| 手动触发 | 输入：集合、宿主、用例的模式、是否带 bench | 按输入 | 按输入 |

- **bench 分两种。** 引擎自身开销的 Bench 用例（`bench/tests/engine.cpp`）便宜，现在随每次 CI 的 Linux 单元测试作业运行；
  改为只在 main、夜间、发布与 `ci:bench` 运行。引擎对比的标准数据集要数小时，只由手动触发，不挂在任何事件上。
- **全量可以手动。** `workflow_dispatch` 的输入就是 `mtest run` 的选择参数；本地 `mtest run --set full` 与 CI 用同一份集合
  定义，所以"CI 跑了什么"在本地可以原样重复。
- **按改动选择的安全边界。** 覆盖图不认识的用例视为受影响；覆盖图过期（`max_age`）时全部视为受影响；内置数据文件
  （`builtin.toml`）的改动影响全部目标类用例；不变量与 `smoke` 永远在 `pr` 里。选择只会多跑，不会漏跑。

**依赖与并行。**

```
 changes ──► plan（mtest ci plan：每个宿主的选择、分片数、预计时间；无构建，约一分钟）
    │
    ├─► build(linux) ──► gate(linux) ──┬─► unit · e2e 分片 × N(linux)
    ├─► build(windows) ─► gate(windows) ┼─► unit · e2e 分片 × N(windows)
    ├─► build(macos) ──► gate(macos) ──┼─► unit · e2e 分片 × N(macos)
    └─► build(linux-arm) ─► gate ──────┴─► 需要多个构建的作业：交叉、目标矩阵、升级、openkal
```

- **构建立即并行开始。** 构建是每个宿主的长杆（Linux 约 16 分钟），不排在任何闸的后面。
- **每个宿主一道闸。** 构建完成后先跑该宿主的 `smoke` 与不变量（预算 2–3 分钟），通过才扇出该宿主的分片；任一宿主的闸
  失败，取消整次运行。绿的路径不增加等待，红的路径在第一个闸处停下。
- **测试程序随构建产出。** 构建作业同时编译被选中的测试程序，与 mcpp 一起作为产物下发；分片不编译。
- **作业内并行靠资源声明。** 用例声明它独占的东西（一个 home、整台机器），其余并行；全局的 `E2E_JOBS=2` 取消。分片只在
  一个宿主的预计时间超过预算时才出现：`分片数 = ⌈预计时间 ÷ 每片预算⌉`。
- **夹具只建一次。** 预热的 home 与模块缓存是运行级夹具，一个作业建一次，用例声明使用它。

**时间成本的账。** 现状（PR 运行 43146150459）：72 个作业、518 作业分钟、墙钟约 45 分钟；其中 Windows e2e 的测试时间约
80 分钟，最长的 18 个占一半。目标〔析，落地时以测量校正〕：PR 墙钟 30 分钟以内，作业分钟减少三成以上，Windows e2e 的测试
时间 35 分钟以内，失败的推送在闸处停下（数分钟的测试成本，不含已开始的构建）。`mtest ci timeline` 每夜产出一份成本
报告：作业分钟、关键路径、最慢的用例；集合的预算被突破时由 `gate` 报告。

### 5.12 固件与裸机

**已有的〔读〕〔测〕。** docs/40 的分层是：引擎持有 ISA 档与 freestanding 的链接行，目标持有编译器与 C 库，**板级支持包**
（一个平台包）持有启动对象、链接脚本与模拟器调用。十余个裸机行是内置数据；RISC-V 与 Cortex-M 的构建与 qemu 运行在 CI 里；
openkal-opensbi 是写在 SBI 上的实现，提供核心三个接口加 `time` 与 `env`，如实缺席 `fs`、`process`、`task`。

**这次测到的。** UEFI 不需要引擎认识它（探针 P5）：一个三十行的平台包用 `[[platform.define]]` 定义 `x86_64-uefi`
（`clang-triple = "x86_64-unknown-uefi"`、`object-format = "pe"`、`execution = "uefi"`、`exe-suffix = ".efi"`），
已发布的 2026.11.10.2 构建出 EFI 应用，在 qemu 加 OVMF 下打印并返回状态，墙钟 2 秒。

**归属（P16 的应用）。**

| 事实 | 归属 | 不归属 |
|---|---|---|
| ISA、对象格式、产物后缀、执行系统 | 行（数据） | 引擎的分支 |
| 入口符号、子系统、链接脚本、内存布局 | 固件或板的平台包 | mcpp、openkal |
| 设备地址、模拟器的机器型号与参数、固件文件 | 板级包；固件文件是 xim 资产 | mcpp、openkal |
| 状态怎样回到宿主（调试端口、semihosting、测试设备、输出里的标记） | 板级包：它既给程序一侧的出口，也给运行器一侧的读法 | 引擎、dirun 的核心 |
| 固件提供的服务到 `kal_*` 的翻译 | 每种固件接口一个 openkal 实现（openkal-opensbi 已有；UEFI 的启动服务是下一个） | openkal 规范（规范不认识任何固件） |
| 程序用到哪些接口、没有时怎么办 | 程序 | 生态 |

**三点设计。**

1. **固件环境是平台包，不是内置行。** UEFI 先以平台包定义自己的行（今天就能做）；出现第二个要用同一身份的平台包时，
   再把行升为内置数据。板与固件的差异永远在包里。
2. **状态的出口由板级包两头负责。** 探针里 x86 的调试端口把状态变成 `状态×2+1`，RISC-V 的测试设备与 ARM 的 semihosting
   各有约定。这些都不进引擎：板级包给程序链接一个出口实现，并在运行器陈述里写出读法。dirun 增加"载荷"方式（产物即
   被启动的东西），读法来自描述文件，与"客体"方式共用串口、超时与清理。
3. **固件属于单任务环境。** UEFI 的 `StartImage` 与 DOS 的 EXEC 一样，被启动者结束后启动者才继续。5.8 的规范问题因此有
   三个使用者（DOS、UEFI、未来的引导链），值得在规范里回答一次。规范文本没有禁止这种实现，并发相关的能力（通道、终止）
   已经是可不声明的属性〔读〕；缺的是一句明示与一致性套件的覆盖。

**收益。** openkal 的 UEFI 实现之上是同一个 openkal-musl 与同一个 C++ 运行时：UEFI 应用可以用 C++23 模块与 `import std`
编写，在 CI 里两秒跑完。这对引导加载器、固件工具与教学是直接可用的。

### 5.14 实施期间并入的缺陷（2026-11-12 追加）

负责人在实施期间追加：两份外部报告若属于 openkal 生态的缺陷，并入本轮一起修复；不是缺陷的、与规范立场不符的建议排除。
两份报告的说法逐条对照 main 的源码核对，并各以一个在未修改的源码上失败的测试复现。

| 来源 | 核对结果 | 处置 |
|---|---|---|
| openkal-linux#53：`kal_net_close`、`kal_net_close_listener`、`kal_datagram_close` 先关闭描述符、后退役句柄 | 成立。内核把刚关闭的编号交给任何上下文的下一次打开；窗口内另一上下文打开的文件带着旧世代号打包，随后被这次退役作废。测得 340 万次打开中 94 次读到的不是该文件 | 修复。释放收敛为一个函数（先退役、后关闭），五处释放都调用它 |
| 同上，第二点：世代号的读与增不是原子操作 | 成立（数据竞争） | 修复。读经原子操作；增是从句柄所带世代号出发的比较并交换，所以一次释放只关闭一次，第二次释放不关闭任何东西 |
| 同上，第三点：`kal_fs_stream`、`kal_net_stream` 对解不开的句柄回答 0 | 成立。流在该实现上是裸描述符，0 是标准输入；规范 6.7 要求不把已释放的句柄当作有效 | 修复。回答一个没有描述符取到的字，其上的传输报告 `kal_err_invalid` |
| 同上，现象之一：描述符耗尽时 `open` 报 EIO 而非 EMFILE | 不是缺陷。openkal 的条件是闭集，其中没有"句柄耗尽"；报告中的耗尽是上面的泄漏造成的 | 排除，在回复中说明 |
| 同一构造在其他实现 | openkal-macos 与 openkal-windows 的三个释放是同样的顺序；openkal-freebsd、openkal-posix 不用世代号 | 一并修复（P17 在仓库之间的对应：一个事实，三处实现，同一修法、同一测试） |
| openkal-musl#52：`poll` 之后的 `recv` 只交回一个字节 | 成立。`read` 的路径已经把预取的字节与已到达的其余部分一起交回，`recv`、`recvfrom`、`recvmsg` 的路径没有。测得 1000 字节 1000 次调用 | 修复。交付收敛到 `okm_take_ahead` 一处，两条路径都调用它；数据报不受影响（预取的是整条报文） |

发布链：三个实现各发补丁版本 → 索引 → openkal-musl 0.29.4（抬高三个实现的下界）→ openkal-platform 0.27.1 → mcpp 钉 0.27.1。
openkal-windows 的修正发在家族所在的 0.21 线上（0.21.1）；0.22.1 同时存在于索引，是 0.22 线的头，带着此前已合入而未入索引的
0.22.0（节点的单一身份、关闭的衰减归还位置），等家族整体迁移时采用。openkal-musl 0.29.3 曾写 `^0.22.1`，由 0.29.4 改回。

## 7. 验证工程对生态的要求

验证工程是一个 C89、只依赖 POSIX libc 的命令解释器，从同一组源码产出两个程序。把它对生态的要求抽成与它无关的十条，
即 `canary-c` 的断言：

| # | 要求 | 对应的通用能力 | 状态 |
|---|---|---|---|

| V2 | 两个程序共享源码，各有入口与宏 | E2 | ✅ |

### 7.1 通用设施就绪后，验证工程能到什么程度

"就绪"指第 10 节的 S1–S4 完成；S5、S6 的内容单独标出。层级的划分是推断〔析〕，依据是第 2 节的台账、本地报告与第 8 节的探针。

| 层级 | 内容 | 身份数 | 取决于 |
|---|---|---|---|
| 一：每次提交构建并运行 | Linux（x86_64、aarch64 的 musl 与 gnu）、Windows（gnu、musl，wine 与真机）、macOS（两个架构的 musl，真机运行）、FreeBSD（四个身份，dirun）、Android（两个，模拟器）、Web（node）、ok 映像（两个架构，在四种宿主的 okrun 上） | 18 个身份，约 14 个运行环境 | S1–S4 |
| 二：每次提交构建，夜间运行 | NetBSD；OpenBSD、Haiku、GNU/Hurd（A 路线，okrun 在 openkal-posix 上） | 再加 5–7 个 | S6；各系统官方镜像可再分发 |
| 二甲：每次提交构建并运行 | DOS 32 位（DJGPP 加 DOSBox；它的 74 个源文件今天有 70 个不改即过，T5） | 1 个 | S5；程序补作业控制、多路等待、优先级三处 |
| 三：不进门禁 | System V（i386）：K7 之后可做一次手工验证；DOS 16 位：程序先要拆掉超过 64 KB 的结构体（T7）；PureDarwin：无法验证 | — | 第 8.3、8.4 节 |

**它得到的。**

- **一份清单覆盖全部身份。** 资源脚本无条件书写（G3 之后），共用入口的两个程序不需要包装文件（E2 已落地）。源码侧
  剩下的是取自身路径的 4 行守卫——这是程序自己的平台探测，改为按 C 库选择后可以提交给它的上游。
- **一台 Linux 机器上的全部验证。** `mcpp test --target <身份>` 经运行器描述到达每个层级一的环境；它自己的 CI 不需要
  Windows、macOS、FreeBSD 的机器就能断言行为同构，真机运行留给发布前。
- **一条命令的发布矩阵。** 各身份的原生程序、一份多架构的 ok 映像、覆盖 Linux、macOS、Windows、FreeBSD 的多系统
  单文件；经 xim 成为 xlings 支持的每个宿主上可安装的包。
- **新代码可以用 C++23 模块。** C89 内核不动，新功能在支持 `import std` 的身份上用模块写，其余身份回落到 C 入口。

**通用设施给不了的（语义面，属于程序）。**

| 方面 | 说明 |
|---|---|
| 进程模型 | DOS 没有并发的子进程与管道，Web 没有进程；管道在这些环境里要由程序用临时文件实现，或者如实不支持 |
| 终端 | 行编辑依赖终端的原始模式；浏览器里的终端界面是程序自己的工作，设施只保证 node 下的行为 |
| 系统的原生语义 | Windows 上的路径写法与命令行原样传递使它按 P4 默认走 A 路线；B 路线的 Windows 程序是可选项 |
| 16 位的体量 | 一个超过 64 KB 的上下文结构体（T7）与 54 KB 的消息表（T6），只能由程序改数据布局、裁语言集合 |
| 不能再分发的系统 | 没有可再分发镜像的系统（System V）进不了 CI，只能有一次性的手工验证 |

**对它上游的含义。** 它现在手工维护多套构建描述（Makefile、CMake、Meson、xmake、Gradle、Visual Studio 与两种 IDE
工程）。设施就绪后，一份 `mcpp.toml` 在覆盖面上超过它们的并集。是否采用是它上游的决定，不在本方案范围内。

本节的每个"测"都是 2026-11-12 在一台 x86_64 Linux 主机上做的本地测量（无 KVM），命令与摘要在 `okexp/t3/PROBES.md`；
它们不是门禁。未测的部分仍标〔析〕。

### 8.1 探针

| # | 探针 | 结果 | 说明了什么 |
|---|---|---|---|
| T1 | 已发布的 2026.11.10.2，`--target i686-none-elf`，不带 C 库，经 `int 0x80` 写一行后退出 | ELF32；`qemu-i386` 下输出一行，退出码 42〔测〕 | 32 位一类的编译、链接、运行路径在引擎里已经通；K7 缺的是 C 库与运行时，不是引擎 |
| T2 | DJGPP（GCC 12.2）编 C 程序，DOSBox Staging 无显示运行 | 输出与退出码 42 如实；墙钟 0.33 秒〔测〕 | DOS 的运行器是"接口的宿主实现"，与 wine 同类，不需要磁盘镜像，可以进每次提交的门禁 |
| T3 | 同上，C++23 | `import std` 没有，`<print>` 没有〔测〕 | 这条路线是"C 与旧标准 C++"的行 |
| T4 | DOSBox 的命令解释器不展开 `%ERRORLEVEL%` | 要用 `if errorlevel N`〔测〕 | 客体的包装必须是数据（D22） |

| T8 | 三十行的平台包定义 `x86_64-uefi`，已发布的 2026.11.10.2 构建，qemu 加 OVMF 运行 | PE32+ EFI 应用；串口输出一行；状态经调试端口回到宿主；墙钟 2 秒〔测〕 | P15 对固件成立：引擎零改动 |
| T9 | 对照 openkal 规范检查 `openkal.process` | 文本未禁止"启动即等待"；通道、终止等并发相关能力已是可不声明的属性〔读〕 | 单任务环境可以提供该接口，缺一句明示与一致性覆盖 |

没有做的：DOS 的 B 路线（需要 K7 的 i386 C 库）；gcc-ia16（没有预编译的发布物）；System V 与 PureDarwin（没有可用的
镜像）。

### 8.2 DOS，32 位

| 身份（名字待定） | 路线 | C 库 | C++ | 引擎需要什么 | 状态 |
|---|---|---|---|---|---|
| `i386-dos-djgpp` | A | DJGPP 的 libc | libstdc++ 12，无模块 | 零：GCC 族的一个新载荷加一条提供者 | 工具链与运行器已测（T2、T5）；经 mcpp 构建未测〔析〕 |
| `i386-dos-musl` | B | openkal-musl（i386） | openkal-llvm-runtime，可以有 `import std` | 零，若 P15 成立 | 〔析〕；前置是 K7 |

**B 路线**由四个包组成：编译与链接沿用 `i686-none-elf` 行的做法（T1）；内核层实现 openkal-dos 经 DPMI 的实模式中断模拟
调用 `int 21h`，如实提供核心三个接口、`env`、`time`、`fs`、`terminal`、`region`，缺席 `task`、`net`、`datagram`、
`space`、`map`、`random`；容器用平台包的 `[platform.link] seal`（链接后对产物执行的命令序列）把 ELF 包进带 DPMI 入口桩
的 MZ 文件，与 ok 映像的 `okld` 封印同一机制；运行器是 DOSBox。

**A 路线**是先做的那条：它不检验 openkal，但工具链、运行器、验证工程的源码三者今天就对得上（T2、T5）。

### 8.3 DOS，16 位

| 方面 | 事实 | 后果 |
|---|---|---|
| 编译器 | LLVM 没有 8086 后端〔析〕；Open Watcom 可用（T7），是自己的命令行；gcc-ia16 是 GCC 命令行，没有预编译发布物 | 不可能有 C++23 与模块；这一行是"仅 C"的行 |
| C 库 | musl 假定平坦的 32 位以上地址空间〔析〕 | 没有 B 路线，没有 openkal，没有映像 |
| 程序 | 一个超过 64 KB 的结构体（T7）；消息表 54 KB（T6） | 先要程序改自己的数据布局与语言集合；这之前工具链帮不上 |
| 引擎 | Watcom 需要一种新的驱动方言；gcc-ia16 需要"按能力探测旗标"——旧编译器不接受引擎缺省给的某些旗标〔析〕 | 后者是通用机制，第二个使用者是 avr、msp430、m68k 一类老的 GCC 交叉链 |

结论：16 位 DOS 在设施一侧只值得做"按能力探测旗标"这一个通用机制，而且要等出现第二个使用者；它本身的可行性由
程序决定。不立项。

### 8.4 32 位一类、System V 与 PureDarwin

- **32 位一类（K7）。** T1 说明引擎一侧没有缺口。工作全在 openkal 家族：规范的 32 位约定、openkal-linux 的 i386 系统调用层、
  musl 与 C++ 运行时的 32 位构建、32 位映像。先做 `i686-linux-musl`，它有 qemu-user，可以进门禁。
- **System V（i386）。** K7 之后是一个 openkal 实现加一个平台包。没有可再分发的镜像，进不了 CI；只能有一次性的手工
  验证，结果写进记录而不是门禁。
- **PureDarwin。** macOS 的 B 路线产物只依赖 libSystem〔读〕，推断可以直接运行；没有 Mach-O 的宿主运行器，也没有可用
  镜像，无法验证。不投入。

## 9. 辐射范围与收益

通用设施的使用者不限于验证工程。每一行的"收益"是在该设施落地后不需要额外引擎工作即可得到的。

| 领域 | 用到的平面 | 收益 |
|---|---|---|
| **生态自举** | ①②③ | mcpp 与 xlings 自身经 B 路线产出 FreeBSD 等系统的静态程序，包管理器与构建工具的宿主范围随 openkal 实现的增加而扩大；新宿主上的第一份 mcpp 不需要在该宿主上编译 |
| **库作者的跨系统测试** | ③④ | mcpplibs 的任何库在一台 Linux CI 机器上对 Windows（wine）、FreeBSD（虚拟机）、Android（模拟器）、aarch64（qemu）运行自己的 `mcpp test`；今天这需要四种 CI 机器或手写胶水 |
| **命令行工具的发布** | ①②，oke | 一份映像或一个多系统单文件覆盖各系统；构建可复现（两次打包字节相同已在本地测得），可以作为供应链证明的基础 |
| **嵌入式与固件** | ①②③ | 裸机行已有十余个；金样测试与运行器陈述同样服务它们。UEFI 应用由一个平台包给出（T8，已测），其上接 openkal 的实现后可以用 C++23 模块与 `import std` 写引导加载器与固件工具；"按能力探测旗标"（8.3）覆盖 avr、msp430 一类老的交叉链 |
| **图形与游戏** | ②（基座） | #913：GUI 工程在三种宿主上产出 Windows PE；基座准入契约保证这类载荷的 C++ 与 `import std` 可用 |
| **教学** | ①③④ | 操作系统与编译课程：同一份作业在多个系统的模拟器里运行并自动比对输出；环境由 xlings 一条命令给出 |
| **非 mcpp 用户** | ②，xim | 基座包与磁盘镜像是普通的 xim 资产，CMake、xmake 用户同样可以把 `aarch64-linux-gnu-sysroot` 当作 `--sysroot`；dirun 不含生态词汇，任何 CI 可用 |
| **复古与长尾系统** | 全部 | DOS、SVR4、Haiku 的准入成本由 P15 界定：数据加包。每接入一个，就多一次对"引擎零改动"的验收 |
| **IDE 与语言服务** | ① | 行、系统表与运行器描述是数据，mcpp-ide 可以直接列出"此工程可去的身份、每个身份怎样运行"，不需要自己的表 |
| **自动化代理** | ②④ | 密封的工具链与机械门禁使代理的改动可以被检查拦下；本次审计发现的问题大多属于"门禁本可以拦下" |

## 12. 风险

- **schema 变更。** 第二版把新增压到两个键（`uname`、`system-headers`）加平台 `runner.hosts` 的一个字段；平台包的最低
  mcpp 版本仍随之上升。旧平台包没有这些数据时，引擎对内置系统的回答与今天相同（数据的缺省，不是代码分支）。
- **加载器规则改变交叉产物的运行方式。** 采纳 D3 后，交叉 glibc 产物在构建机上不能直接启动，必须经运行器。这是正确
  的语义，但与"构建完马上能跑"的直觉不同，诊断要说清楚。
- **K7 跨六个仓库。** 它是 S5、S6 多数内容的前置；若推迟，DOS 的 B 路线、SVR4 与 i686 一起推迟，A 路线与 UEFI 不受影响。
- **准入契约拉长索引 PR 的周期。** BP3–BP7 需要已发布的引擎认识被测的载荷；引擎与载荷同时变化时有先后问题——载荷先
  以候选修订进入，引擎发布后再转正。
- **e2e 迁移改写九万行。** 风险是迁移中丢断言或改了被测行为。对策已在 5.9：先原脚本后新用例、映射表、一个子系统一个 PR。
  在 M1–M3 就绪之前不开始；第一批选耗时最长而断言最少的子系统，用它校正 5.11 的目标数字。
- **按改动选择漏跑。** 对策是 5.11 的安全边界与 main 上每次合入的 `full`：PR 漏掉的，合入后的那次运行会抓到。
- **范围。** 本方案有七个阶段与一次测试体系迁移。S1 与 S2 是不可分的最小切片；S3 之后的每一项都应当在前一项的门禁
  绿了之后才开始，同一时间进行中的阶段不超过两个。
- **探针不是门禁。** 第 8 节的测量是一台主机上的一次运行。它们回答"路是否通"，不回答"是否稳定"。

### 14.3 仍然没有把握的

- **第 5.9、5.11 的占比与目标数字**是估计。迁移的三类各占多少要靠一次逐脚本的清点；PR 墙钟与作业分钟的目标要靠第一批
  迁移后的测量。
- **mtest 的现状**只读了文档。M1–M6 里可能有已经存在的，实施前逐项核对。
- **`mcpplibs.cmdline` 的能力**没有核对；dirun 改用它之前先确认可重复选项与 `--` 之后原样传递。

## 16. 工具链载荷即数据（2026-11-13 补充）

### 16.1 现状（测）

**版本已经是数据。** 发布的引擎（2026.11.10.2）：`--toolchain gcc@16.1` 解析为 `xim:gcc@16.1.0`，`xim:gcc@16.1.0` 原样可用，
`gcc@16.9.0` 被拒绝并说明索引里没有该包。因此 xim-pkgindex 发布 `gcc 16.2.x` 之后，`[toolchain] default = "gcc@16.2"`（该系列在
索引中的最新者）或 `"xim:gcc@16.2.0"` 不需要改动引擎即可使用。默认版本由内置行固定，改变默认需要发布引擎，使用则不需要。

**名字不是数据。** 三处把载荷写在代码里：

| 位置 | 写死的内容 |
|---|---|
| `compat::normalize_spec` | 可接受的名字：`gcc`、`llvm`、`msvc`、`emsdk`、`android-ndk` 与别名 `clang`、`musl-gcc`、`mingw*`、`<triple>-gcc`；其余名字（含 `xim:` 前缀）被拒绝 |
| `to_xim_package` | （家族，目标，宿主）到包名的分支：gcc 到 `gcc`、`musl-gcc`、`mingw-gcc`、`mingw-cross-gcc`、`<gcc-triple>-gcc`；llvm 到 `llvm`、`emsdk`、`android-ndk`；每个分支各写前端候选与前端目录 |
| `identify_xim_payload` | 上一项的反向映射，供 `toolchain list` 与 `doctor` 枚举 |

新增一个工具链发行版（厂商的 clang、`riscv64-elf-gcc`、icx）因此仍要改引擎，与 R1"行是数据，读行的代码不是"不一致。已经数据化的
部分是三项：载荷的描述文件 `.mcpp-toolchain.json`（schema 1：`frontend`、`platform_floor`、`std_module_defines`、`runner`），
按路径命名的工具链（`path:<dir>` 与清单的 `[toolchain]` 路径表，家族由目录里的驱动判定），以及行的 `gcc-triple`。

### 16.2 原则

**家族是引擎的词汇，载荷是数据。** 家族回答"编译器说哪一套选项"（gcc、llvm、msvc），引擎为每一套各有一份实现，它保持封闭。
载荷回答"哪个包、前端在哪里、带哪些工具"，它是包的事实，由包陈述。

### 16.3 方案

**T1 描述文件 schema 2 即路径表。** `.mcpp-toolchain.json` 增加清单 `[toolchain]` 路径表的键：`family`、`prefix`、`sysroot`、
`tools`（角色到程序），路径相对载荷根。一个载荷对自身的陈述与一个项目对本机目录的陈述是同一张表，读同一个结构
（`LocalToolchain`）。schema 1 的四个键不变；没有描述文件的已发布载荷按原样工作。

**T2 `xim:<name>@<version>` 接受任何名字。** 名字在家族词汇（含别名）之外时，它指一个载荷：安装该包，读它的描述文件，然后按
`path:<载荷根>` 加描述文件的表解析——家族由驱动判定（与表中的 `family` 不一致即拒绝），目标由驱动回答。描述文件缺失时拒绝，
指出缺少的文件与键。不带 `xim:` 的未知名字仍被拒绝：命名空间是"这是一个包"的唯一说法。平台的 `toolchain` 键因此可以直接写
任何载荷，平台定义的行不需要新键。

**T3 默认映射是表。** 裸名（`gcc@16.1.0`、`llvm@23.1.3`）是简写：（家族，目标，宿主）经一张规则表得到包名、前端目录、前端候选与
glibc 修正，规则按序匹配，取第一条。表在 toolchain-model 的数据文件里，`to_xim_package` 与 `identify_xim_payload` 都读它，
正反两个方向不再各写一遍。别名（`clang`、`musl-gcc`、`mingw*`）保持兼容提示。

**T4 验收：引擎零改动。** 新增一个工具链即发布一个带描述文件的 xim 包；以本轮的 gcc 16.2.0 验证版本开放，以一个词汇外名字的
载荷验证 T2（e2e：仓库内的假载荷，带 schema 2 描述文件）。

**T5 机械门禁。** 统计 `src/` 中载荷名（`emsdk`、`android-ndk`、`musl-gcc`、`mingw-gcc`、`mingw-cross-gcc`）在规则表之外的出现次数，
与基线文件比较，多于基线即失败。

### 16.4 本轮的 gcc 16.2.0 与 17 的主干快照

默认仍为 gcc 16.1.0，xim 的 `latest` 仍指向正式版。xim-pkgindex 以 `tools/res/build.sh gcc` 从源码构建，两种来源：

| 版本 | 来源 | 来源核对 | 平台 |
|---|---|---|---|
| `16.2.0` | GNU 的发布包（`ftpmirror.gnu.org`） | GNU 签名已核对（RSA 7F74F97C103468EE5D750B583AB00996FC26A641），摘要为实测 | Linux x86_64、aarch64 |
| `17.0.0-20261108` | GCC 的快照目录（`gcc.gnu.org/pub/gcc/snapshots/17-20261108/`） | 上游不签快照，摘要为加入时实测；源码自述 `BASE-VER 17.0.0`、`DATESTAMP 20261108`、`DEV-PHASE experimental` | Linux x86_64、aarch64 |

**主干快照的版本写法是 `<major>.0.0-<YYYYMMDD>`。** 它就是快照的编译器对自身的陈述（`17.0.0 20261108 (experimental)`），与上游
快照名 `gcc-17-20261108` 一一对应。按 xpkg 版本的次序，日期段是预发布段：快照排在 `17.0.0` 与首个正式版 `17.1.0` 之前，
快照之间按日期排序。等值匹配要求预发布段相同，因此 `gcc@17` 与 `gcc@17.0` 不选中快照，只有写全
`xim:gcc@17.0.0-20261108`（或 `gcc@17.0.0-20261108`）才使用它：前沿的使用者显式选择，其余使用者不受影响。一个日期是一份不变
的源码，锁文件、指纹与缓存因此可复现；不设滚动版本。索引只保留一个快照（本轮为 20261108），换新快照时替换条目，xlings-res 的
资源保留。

构建与正式版相同：C 程序与使用 `import std` 的 C++23 程序构建并运行，`--version` 报告所写的版本，二进制只依赖 glibc 的库；
`res-build` 的 `only` 接受 `what@version`，新版本的构建不重建已发布的版本。产物发布到 xlings-res 并以 gtc 镜像到 GitCode，
`pkgs/g/gcc.lua` 增加两个版本。

验证项：`gcc@16.2`、`xim:gcc@16.2.0`、`xim:gcc@17.0.0-20261108` 的解析、安装与构建（含 `import std`），`gcc@17` 不选中快照，
`[toolchain] default` 与 `--toolchain` 两种写法，`toolchain list` 与 `doctor` 的枚举，默认（16.1.0）不变。

## 17. 工作区的并发、升级后的重编与构建目录的体积（2026-11-13 补充）

### 17.1 现状（测）

**并发的契约。** 一个配置一个构建目录，一把锁（`dirlock`），只在写目录时持有：清单、解析、网络、工具链与扫描不持锁，
`mcpp test` 在第一个测试运行之前释放，`mcpp run` 在程序启动之前释放。同一配置的两个命令只在编译与链接时排队，等待方显示
持有者；不同配置（profile、目标、选择）是不同的目录，互不等待。一个配置只有一份 `build.ninja` 与 ninja 状态，两个 ninja 同写
即互相破坏（mcpp#839），因此锁的粒度是配置而不是成员。

**升级后的重编。** 两个成员的工作区（一个库成员带 mtest 测试，一个程序成员），以 2026.11.10.2 构建并测试，再以 2026.11.12.1
构建：153 个目标文件与 BMI 中 18 个重编，即两个成员与 mtest 的全部；全局缓存供给的依赖未重编。原因不是指纹的内容：
锁文件的哈希不在指纹中（该字段为空），同一谱系的新指纹接管旧目录（2026-10-31 §8，目录改名而非复制）。原因在命令中的两个
路径：

- 目录的名字：编译命令含绝对的输出路径，链接命令含目录内的 specs 路径，路径含指纹，目录改名使这些命令全部改变；
- 引擎的路径：图在命令中运行引擎（`$mcpp __compiler-cap … -- <编译器>`、BMI 比较、链接包装、暂存、模块绑定），
  `$mcpp` 是引擎的绝对路径，经 xlings 安装时含版本（`xim-x-mcpp/<版本>/bin/mcpp`）。只改目录名之后仍是 18 个重编（实测）。

ninja 按命令重编。随后的警告"fingerprint changed, full rebuild"不区分"接管并按命令重编"与"新目录"。

**体积。** 已有：`-ffunction-sections -fdata-sections` 与测试程序链接的 `--gc-sections`，ELF 上的 `-gz=zlib`（mcpp#874），
开发 profile 的拆分 DWARF（`.dwo`），`mcpp clean --report`（每个配置的 obj、bmi、bin），构建后的过期清扫（`[build] keep_days`）
与 `[build] target_budget`。`debug` 只有开与关。程序与测试链接目标文件，不经静态库：构建目录中的 `.a` 只是库成员的交付物
（`bin/`），mcpp 自身的两个构建目录（638 MB、466 MB）中归档为零。

### 17.2 方案

**W1 构建目录以配置的谱系命名。** 目录名是谱系（编译器家族、目标、标准库家族、语言标准、配置的选项；2026-10-31 §8.2）的哈希，
演进的部分（编译器的版本与驱动、标准库的版本、mcpp 的版本、运行时契约）记在目录内：`toolchain` 已有，完整指纹另记于
`fingerprint`。于是：

- mcpp 或依赖升级不改变任何路径，ninja 只重编命令真正改变的边；
- 图经构建目录自己的引擎链接运行引擎：`<目录>/engine/epoch-<N>/mcpp`，硬链接（不能时复制）到当前引擎，规划者在目录锁下
  使之为当前引擎；一条命令只随编译器、选项与文件改变。链接的路径含 `kCacheEpoch`：引擎各步所写内容的含义改变的版本提升它，
  各边随之重新运行，与依赖缓存以 epoch 而不以版本号为键是同一原则。快速路径接受指向本引擎的链接。自包含的家目录由引擎的位置
  推出，经链接运行的子命令推不出，因此此时 mcpp 为其启动的程序陈述 `MCPP_HOME`；
- 编译器的构建改变时，目录的内容在原处替换（锁文件除外），与现在"移除前任"的结果相同，状态行不变；引擎或演进部分改变时，
  编译器的在途记录（`.sched`）删除，与接管时相同；
- 以指纹命名的既有目录由现有的接管逻辑按谱系文件接管一次，此后路径稳定；
- 快速路径的记录保存完整指纹，入口检查读目录内的 `fingerprint`，不再比较目录名；
- 警告只在谱系改变（配置改变，新目录、全量构建）时出现，并说明是哪一项改变；同一目录的继续不发警告，重编的内容由 ninja 的
  进度说明。

指纹本身不变，仍是键（打包的 `buildKey`、`--print-fingerprint`）；改变的只是它不再兼作路径。实测（同一工作区，引擎只改版本号）：
重编由 153 个中的 18 个降为 0，构建 0.22 s，测试 0.43 s；源码改动、profile 切换与 `debug = "lines"` 仍按预期重编或新开目录。

**W2 被取代的目录。** 不另立机制。升级本来就不复制目录（接管），W1 之后连改名也没有；配置的改变产生的新目录是开发者会切回的
目录，按 `keep_days` 清扫。

**W3 时间与体积可见。**

- 等待构建目录的时间进入 `Finished` 的分解（`waited 1m30s for the build directory`），从"plan"中扣除；
- `mcpp clean --report` 增加一列 `debug`，即拆分出的调试信息（`.dwo`）。

**W4 契约成文。** 17.1 的并发契约写入 `docs/07-workspace.md` 与 `docs/08-testing.md`（中英），包括"测一个成员、同时改另一个
成员"的可行性与等待的条件。

**W5 调试级别 `"lines"`。** `[profile.<name>] debug = "lines"` 只保留行表：GNU 与 LLVM 方言为 `-g1`（clang 即
`-gline-tables-only`），回溯与 sanitizer 报告仍有文件与行号，没有变量与类型信息。cl.exe 没有只含行表的级别，`"lines"` 在其上即
`/Z7`。其余字符串被拒绝。默认不变；配置字符串中 `debug=1` 不变，`"lines"` 为 `debug=lines`，既有目录的身份不变。

**W6 薄归档：测后不采纳。** 构建内的链接输入是目标文件，归档只作交付物，薄归档引用构建目录中的路径，作为交付物是错的；
可节省的体积为零。

### 17.3 推荐的做法（文档，不改引擎）

写入 `docs/08-testing.md` 与 `docs/04-mcpp-toml.md` 的 profile 一节：

1. 全量测试与 CI 使用单独的 profile，例如 `[profile.ci]` 写 `debug = "lines"`（或 `false`）与 `strip = true`。日常开发保留完整的
   调试信息。
2. 测试多的包使用 `[test] programs = "directory"`：一个目录一个程序，链接次数由文件数降到目录数。
3. 模块的实现放在实现单元（`module X;`）：函数体的改动不改变 BMI，导入方不重编。
4. 成员分层：逻辑放在不依赖 UI 与渲染的成员中，多数测试只链接逻辑层。
5. 体积以 `mcpp clean --report` 读取，以 `mcpp clean --stale` 回收。

### 17.4 考虑过、不采纳

- **测试程序默认以共享库链接成员的闭包。** 它去掉闭包的重复链接，但牵涉 Windows 的 DLL 导出语义与模块的符号导出，跨平台的
  代价大，不能作为通用的默认。
- **默认剥离测试程序的符号表。** 调试器、sanitizer 与回溯依赖符号表；由 profile 的 `strip` 选择。

## 18. 大工作区的测试反馈（mcpp-community/mcpp#927，2026-11-13 补充）

反馈来自一个 143 个成员、339 个测试程序的工作区（2026.11.12.1、mtest 0.7.1、Linux x86_64、gcc 16.1.0、`dev`）。六项中，
项目自身的部分不在此列：测试文件的放置、成员的分层、CI profile 的采用，以及测试本身 43 分钟的运行时间。

### 18.1 归属与现状（代码核对）

| 项 | 属于 mcpp 的部分 | 现状 |
|---|---|---|
| 1 `programs = "directory"` 对 `tests/` 根下的文件无效 | 语义的表达与提示 | 设计如此：固定目录下的子目录各成一个程序，直接位于固定目录中的文件仍各为程序；设置不改变任何程序时没有任何提示，`--strict` 亦然 |
| 2 `mcpp test -p` 解析两遍、汇总有一段无名 | 一次调用的规划次数与时间的归属 | 测试先以 `mcpp build` 的方式构建包的程序（`MCPP_BIN_<NAME>`），其快速路径的条件要求 `package_filter` 为空，故 `-p` 必走完整的 `prepare_build`；随后带 dev 依赖再 `prepare_build` 一次。汇总只列 build 与 run |
| 3 两个进程并发时一次 `no local package index` | 索引刷新与读取的并发 | 刷新锁是非阻塞的：拿不到锁的进程跳过刷新并立即读取。mcpp 拥有的索引在暂存目录取回后交换；文件系统不支持原子交换时退化为"旧目录移开、新目录改名"，其间索引不存在；provider 自己的索引原地刷新。两者都是读者可见的窗口 |
| 4 测试程序占配置体积七成 | 调试信息的级别、链接形式、程序的粒度 | §17 已有 `debug = "lines"`；`dependency_linkage = "shared"` 按 profile 可写，实测对工作区成员生效（成员依赖成为共享库，放在产品目录中）；开发 profile 默认拆分并压缩 DWARF；文档未把它们组织为"开发时的测试体积"一节 |
| 5 升级后 88 分钟全量重编 | 构建目录的身份 | §17 W1 已解决：目录以谱系命名，图经目录的引擎链接运行 mcpp；实测只改版本号的引擎重编 0 个 |
| 6 `clean --stale` 需要人记得 | 被取代目录的回收 | W1 之后升级不再产生目录，编译器改变时原处替换；构建后的清扫（`keep_days`，默认 3 天）与 `target_budget` 已有。剩下的是：配置改变新开目录时，警告不说旧目录的大小 |

### 18.2 方案

**P1 测试程序的粒度：`programs = "package"`，与 `"directory"` 的提示。** `[test] programs` 是测试程序的粒度：`"file"`
（默认）、`"directory"`、`"package"`。`"package"` 使一个包所发现的全部文件成为一个程序，以第一个 glob 的固定目录命名
（`tests`），规则与 `"directory"` 相同：定义 `main` 的文件至多一个，否则拒绝并指出两者；按测试协议运行时仍是每个文件一个进程
（`tests/<file>`），隔离与并行不变，链接一次。`"directory"` 的语义不变，并在设置留下了直接位于固定目录中的文件时说一行：

```
note: [test] programs = "directory": 12 files directly in tests/ stay programs of their own; "package" makes the suite one program
```

设置不改变任何程序时，`--strict` 拒绝。文档写明三种粒度与固定目录的含义。它同时是第 4 项的主要手段：程序数由测试文件数降为
目录数或包数，闭包的重复链接随之减少。

**P2 一次调用，每个配置规划一次；汇总给出每一段。**

- 程序的预构建对 `-p` 与工作区选择也取快速路径：按所选成员的配置组匹配记录，与 `try_fast_workspace_build` 相同；
- 需要规划时，同一次调用内的第二次 `prepare_build` 复用第一次的依赖解析与工具链解析（以清单、锁文件与覆盖项为键的进程内结果），
  不再解析与打印第二遍。`mcpp run --format`（构建后打包）同样受益；
- 测试的汇总与 `Finished` 一致地分解：`finished in 7.77s (plan 2.10s · programs 1.73s · build 1.60s · run 2.34s)`，各段之和
  为总时长，等待构建目录时另列 `waited`（§17 W3）。

**P3 索引：刷新可以跳过，读取不读替换中的树。** 刷新分两段：取回在暂存目录中进行，不阻塞任何人；交换在索引锁下进行，只持有
毫秒。读取在索引的共享锁下进行，因此不会落在交换的窗口中（包括不支持原子交换的文件系统）。provider 自己的索引也按此取回到
暂存目录再交换（`sync_index` 已接受目标目录），不再原地改写。拿不到刷新锁的进程仍跳过刷新，但它的读取等待交换完成。

**P4 开发时测试的体积：已有能力的组织与文档。** 不新增引擎键：

- `[workspace.profile.<name>] debug = "lines"`（§17 W5）：回溯与 sanitizer 仍有文件与行号；
- `[workspace.profile.<name>] dependency_linkage = "shared"`：一个成员的测试链接其余成员的共享库，闭包在磁盘上只有一份；
  这是可选的 profile，不是默认（§17.4 的理由不变：Windows 的 DLL 导出与模块符号导出）；
- P1 的程序粒度。

`docs/08-testing.md` 的"测试构建的体积"一节按上述顺序给出开发与 CI 两个 profile 的写法。

**P5 升级。** 由 §17 W1 解决，不另立机制；`mtest` 升级只重编导入 mtest 的单元与重链接测试程序，这是必要的。

**P6 新目录的提示。** 配置改变新开目录时，警告给出旧目录的大小与回收它的命令：

```
warning: the configuration changed (debug 1 → lines): 7a72… is built in full beside ed03… (2.1 GiB); `mcpp clean --stale` drops it once no build uses it
```

### 18.3 实施记录（2026.11.13.1）

| 项 | 实施 | 持有它的检查 |
|---|---|---|
| P1 | `programs = "package"`：一个包一个程序，以第一个 glob 的固定目录命名，定义 `main` 的文件至多一个；按文件运行的各部分以文件在程序目录（其文件的公共目录）之下的路径命名，不同子目录中的同名文件因此不冲突（目录模式下即文件名，与此前相同）；`"directory"` 留下固定目录中的文件时给出 note，不形成任何组时为 `degraded`（`--strict` 拒绝） | mcpp `test_targets.cppm`；e2e 的 C++ 用例 |
| P2 的汇总 | `finished in X (plan · programs · build · run)`：plan 为总时长减去其余各段，programs 不足 5 ms 时不列 | mcpp `execute.cppm`；`tests/e2e/test/streams.cpp` |
| P3 | 拿不到刷新锁、且所声明的索引目录有缺失的进程，等待刷新锁（显示 `Waiting`）后再读；索引完整时仍跳过刷新、立即读取 | mcpp `xlings.cpp` |
| P4 | 文档：`docs/08-testing.md` 的"测试构建的体积"一节（中英） | — |

**P3 的范围比 18.2 小。** 18.2 的方案是读取持共享锁、刷新在暂存目录中进行后交换。#927 报告的现象只在"索引目录不存在"时出现：
索引存在时，刷新以交换替换整棵树，读取者读到的是交换前或交换后的一棵完整的树。因此实施只关闭这一个窗口，读路径不加锁。
不支持原子交换的文件系统上，"移开、改名"之间的窗口与目录不存在是同一情形，读取者同样等待。

与键），在本轮之外；当前代价是 `-p` 多一次完整规划。

**用户裁决。** P1、P2、P3、P6 的取舍向负责人提出过，未得到答复；以上按本文的推荐实施。

### 18.4 不采纳

- **`[test] debug = "lines"`，测试专有的调试级别。** `mcpp build` 与 `mcpp test` 是同一配置（2026.11.8.1），被测代码的目标文件
  由两者共用。测试专有的级别要么只作用于测试自己的翻译单元，体积几乎不变；要么使测试成为另一配置，切换即全量重编。级别由
  profile 决定。
- **默认只剥离符号表而保留调试信息。** 符号表是调试器、性能分析器与回溯在没有 DWARF 时的依据，开发构建不默认去掉；需要时由
  `strip = true` 的 profile 选择。

## 19. UEFI 收敛到 openkal：实施中测到的与据此的设计（2026-11-13 补充）

本节记录"UEFI 收敛到 openkal"（第 5.12 节，用户决定：openkal-platform 接管 `x86_64-uefi` 行与载体，uefi-platform#1 关闭）
实施时测到的三处缺口，以及按 P16（归属）与"不硬编码系统名"的规则给出的解法。

### 19.1 测到的

| 项 | 测到的（2026-11-13，llvm 23.1.3） | 缺口的归属 |
|---|---|---|
| C 环境的实现 | openkal-musl 声明 `presents = "posix"`、`data-model = "arch-default"`；对 `x86_64-uefi` 的构建被拒："this OS is outside the mapping table"。`cenv` 的映射以系统名为键（`windows`、`linux`、`macos`） | mcpp：映射的键应是行的容器格式 |
| 包对 PE 的选择 | musl 与 llvm-runtime 的 PE 部分（setjmp 的记录、`.ctors` 的遍历、compiler-rt 的 PE 源、libunwind 的 PE 分支）以 `cfg(windows)` 选择；UEFI 是 PE 而不是 Windows | mcpp 缺少按容器选择的 cfg 键；包把"PE"写成了"Windows" |
| 链接 | 以 `--target=x86_64-pc-cygwin` 编译的目标文件在 `lld-link`（MSVC 方式）下没有 `__CTOR_LIST__`；`ld.lld -m i386pep --subsystem efi_application` 链接出 EFI 应用（子系统 10）；openkal-platform 的 `[platform.link]` 与 `[platform.build]` 是 ok 镜像的 | 提供者的 `link`、`layers` 已由 `provider_view` 并入（SPEC-016 §3）；平台顶层的 `runner` 仍压过提供者自己的运行器 |

### 19.2 方案

1. **`cenv` 以容器为键（mcpp）。** 实现"呈现 POSIX"的代价是工具链对容器的约定：PE 为 LLP64、16 位 `wchar_t`，以 Cygwin 身份的
   替换得到 LP64 与 `__unix__`；ELF 已有 `__unix__`；Mach-O 加 `-D__unix__`。`realise` 增加容器参数（由
   `Triple::object_format()` 给出，平台定义的行亦然），系统名只用于消息。内置行的行为与命令行不变（单元测试 21 例，含新增的
   "平台定义的 PE 行取 PE 的实现"与"未知容器被拒并指名"）。已实现。
2. **`cfg(object-format = "...")`（mcpp）。** 三元组键增加 `object-format`，值为行数据的拼写（`elf`、`pe`、`mach-o`、`wasm`、
   `coff`）；特异性为一个分量，低于 `os`。包需要的是同一容器的各系统共有的约定时按它选择。已实现，文档 docs/22（中英）。
3. **一个平台按行给出约定（openkal-platform，数据；mcpp 一处）。** 提供者的 `link` 已在它服务的身份上取代平台的
   `[platform.link]`：`x86_64-uefi` 的提供者陈述 `driver = "lld"`、`flags = ["--subsystem", "efi_application",
   "--gc-sections"]`、`start = "efi_main"`、`exe = "{name}.efi"`、`inputs = []`、`seal = []`，行的
   `link-emulation = "i386pep"` 选择 MinGW 方式的 COFF 链接；ok 镜像的编译约定移入 `[platform.build.'cfg(os = "openkal")']`。
   mcpp 的一处：提供者陈述了 `runner` 时，`provider_view` 以它取代平台顶层的 `runner`（顶层的运行器属于 `[platform]
   targets` 这个提供者），与 `link`、`layers` 的取代一致。
4. **包按容器选择（openkal-musl 0.29.6、openkal-llvm-runtime 0.20.3）。** PE 共有的部分改为 `cfg(object-format = "pe")`，
   私有宏为 `OKM_TARGET_PE`、`OPENKAL_TARGET_PE`；Windows 独有的部分（openkal-windows 依赖、`okw_start` 入口、`.exe` 的重试、
   Windows 的链接词）仍为 `cfg(windows)`。安装的头文件不读系统名：musl 的 PE 记录放在只在 PE 行上进入包含路径的
   `musl-generated/x86_64-pe`，llvm-runtime 以只在 PE 行上进入包含路径的 `port/include-pe/__openkal_target_pe.h` 标记容器。
   两包的引擎下限为 2026.11.13.1。
5. **openkal-uefi 0.10.0 的 `standalone`。** 与 openkal-windows 相同：`efi_main` 记录固件表与参数，交给 C 库的
   `__libc_start_main`，初始化由 C 库完成；无 C 库时保持 0.9.0 的行为。openkal-musl 在 `cfg(os = "uefi")` 下以
   `standalone` 依赖它，与其余系统的写法一致。
6. **运行器。** xim 的 `ovmf` 9.2.4-1 携带 dirun 描述文件（`{profile-dir}`，dirun 0.3.2），运行器陈述只写
   `dirun --payload {} --profile {pkg:ovmf}/dirun.toml --emulator {pkg:qemu-x86}/bin/qemu-system-x86_64`。

7. **可选接口按实现的陈述（openkal-musl、openkal-llvm-runtime）。** 两包的 `OKM_HAS_FS/PROCESS/TASK`、`OPENKAL_HAS_TASK`
   原以目标为代理（`os = "none"` 为 0）；现以 `cfg(not(interface = "openkal.fs"))` 等读实现的 `provides-interfaces`
   （ok 镜像仍在运行时询问）。`pthread_getattr_np` 对 `kal_task_stack` 的直接调用改经可选接口的接缝。
8. **行可以只陈述链接的仿真而不陈述机器（mcpp）。** `defined_spec` 原要求 `march`；`x86_64-uefi` 只陈述
   `link-emulation = "i386pep"`，处理器取 clang 三元组的默认。

**测到的结果（2026-11-13，本地各仓库的工作树）。** `import std` 的 C++ 程序（`std::println`、`std::ranges::sort`）以
`--target x86_64-uefi` 构建：release 产物 1.2 MB 的 PE32+ EFI 应用（子系统 10），在 OVMF 下经 dirun 与 ovmf 的描述文件运行，
输出正确，状态 42 经调试端口回到宿主，墙钟 0.8 秒。

### 19.3 载体：经 okrun 运行时测到的三处缺口（2026-11-13）

载体是一个 `x86_64-uefi` 的 EFI 应用，它在固件中运行一个 openkal 映像。经 dirun 在 OVMF 下运行时，载体先是不输出任何内容直到
超时。逐项测得：

| 现象 | 原因 | 修正 |
|---|---|---|
| 2 GiB 时 `_mi_page_map_register` 中的 #GP | mimalloc 3.6.1 的页映射依赖"保留而未提交的内存读为零"；无区域的实现（UEFI）上，保留即分配，OVMF 以 0xAF 填充池 | openkal-musl 的 mimalloc 原语：无区域时，未提交的保留清零，`is_zero` 如实陈述 |
| 512 MiB 时中止 | mimalloc 的 arena 以 256 MiB 对齐；`kal_alloc` 以超额分配实现对齐，32 MiB 的 arena 成为 288 MiB 的请求 | openkal-uefi：一页及以上的对齐读内存映射，在对齐的空闲范围以 `AllocateAddress` 分配页；openkal-musl：无虚拟保留时 arena 的预留为 1 GiB 的四分之一 |
| 中止的消息不可见 | OVMF 的 StdErr 不写串口 | openkal-uefi 的弱钩子 `okuefi_board_errors_to_console()`：板子定义它，标准错误即 ConOut |

载体与映像是两个分配器，各需要一个 256 MiB 对齐的 arena，因此 openkal-platform 的 UEFI 运行器给出 `--memory 2048`。测得：
映像打印、写标准错误、抛出并捕获异常，以状态 7 返回，1 GiB 与 2 GiB 下均为 0.4 秒。

### 19.4 不采纳

- **为 UEFI 在包里加 `cfg(os = "uefi")` 的 PE 分支。** 每增加一个 PE 系统就要再改一次包；容器是这些分支真正问的事实。
- **引擎为每个构建广播容器宏。** 改变所有目标的每条编译命令（升级即全量重编），而安装的头文件可由清单选择的包含目录回答。
- **行声明 `family = "windows"`。** UEFI 不是 Windows 家族；`cfg(windows)` 下的 Windows 依赖与入口会被错误地选中。
